## 3. 설계

### 3.1 API와 응답

- 주문 요청에 `promotionId`(선택)를 더한다. 없으면 지금의 일반 주문 경로 그대로다
- 동기 `POST /api/v1/order`, 비동기 `POST /api/v1/order/async` 둘 다 받는다

| 결과 | 동기 | 비동기 |
|---|---|---|
| 성공 | 200 + 주문 id | 202 + Location (저장은 나중, 결과는 SSE·폴링) |
| 매진 | 409 + `{"code":"SOLD_OUT"}` | 메모리 방식: 접수에서 즉시 409 / DB 방식: 202 뒤 `FAILED(SOLD_OUT)` (워커에서 판정) |
| 이미 참여 | 409 + `{"code":"ALREADY_JOINED"}` | 메모리 방식: 접수에서 즉시 / DB 방식: 워커에서 |
| 이벤트 시간 밖 | 409 + `{"code":"NOT_OPEN"}` | 같음 (접수에서 즉시) |
| 대기 자리 없음 | — | 429 + Retry-After (기존과 같음) |

- **409를 고른 이유:** "요청은 맞지만 지금 상태와 충돌한다"는 뜻이다. Tomcat 10.1.34는 400·408·411·413·414·500·501·503 응답 뒤에만 연결을 끊고 409는 연결을 유지한다(바이트코드로 확인). 매진 응답이 초당 수천 건 나오므로 연결을 끊지 않는 코드여야 한다(503 조사, P2 7절)
- 비동기 DB 방식의 접수는 지금처럼 DB를 쓰지 않는다. 그래서 매진을 나중에 `FAILED`로 알게 되며, 이것이 이 비교군이 보여 줄 대가다

### 3.2 데이터

| 테이블 | 열 | 쓰는 방식 | 역할 |
|---|---|---|---|
| `promotions` (신규) | id, name, total_stock, remaining_stock, starts_at, ends_at | 전부 (remaining_stock은 행 하나 방식만) | 이벤트 정의 |
| `promotion_stock_buckets` (신규) | promotion_id, bucket_no, remaining. **기본 키 (promotion_id, bucket_no)** | 여러 행 방식 | 재고를 20행으로 나눈다(행마다 5,000개) |
| `promotion_tickets` (신규) | promotion_id, ticket_no. **기본 키 (promotion_id, ticket_no)** | 메모리 방식 | 번호표 1~10만. 이벤트를 만들 때 한 번에 채운다 |
| `promotion_participations` (신규) | promotion_id, user_id, order_id, ticket_no(메모리 방식만), created_at. **기본 키 (promotion_id, user_id)**, **유니크 (promotion_id, ticket_no)**, **외래 키 (promotion_id, ticket_no) → promotion_tickets** | 전부 | 할인 주문 한 건 = 한 행. 1인 1회와 번호표 중복·범위 초과를 DB가 마지막에 막고, "결과 모름"을 확인할 때 이 행이 있는지 본다 |
| `orders` | 변경 없음 | — | 일반 주문 저장 비용에 영향을 주지 않으려고 할인 정보는 참여 테이블에 둔다 |

- 번호표 안전망: 참여 행의 번호표는 유니크라 두 주문이 같은 번호를 쓸 수 없고, 외래 키라 1~10만 밖의 번호는 들어갈 수 없다. 메모리 쪽에 버그가 있어도 할인 주문은 10만 건을 넘을 수 없다. 외래 키 확인은 부모 행(번호표)에 공유 잠금을 거는데, 주문마다 번호가 달라 서로 기다리지 않는다
- DB 방식에서 `ticket_no`는 NULL이다(NULL이면 유니크·외래 키 검사를 하지 않는다)
- 할인 주문 트랜잭션: `검증 SELECT → 주문·메뉴 INSERT → 참여 INSERT → (DB 방식만) 재고 UPDATE`. 참여 기본 키가 겹치면 이미 참여이므로 롤백한다

### 3.3 재고 처리: 세 방식

**① DB 행 하나**
1. 잠그지 않는 조회로 `remaining_stock = 0`이면 바로 매진
2. 트랜잭션 마지막에 `UPDATE promotions SET remaining_stock = remaining_stock - 1 WHERE id = ? AND remaining_stock > 0`
3. 바뀐 행이 0이면 매진 → 롤백
- DB가 원자성을 보장하므로 보상 로직이 없다. 대신 모든 할인 주문이 이 행의 잠금을 커밋까지 쥐므로 **할인 주문 커밋이 하나씩만 된다.** 잠금 시간을 줄이려고 UPDATE를 마지막에 둔다(이 방식의 가장 좋은 형태로 비교)

**② DB 여러 행 (쪼개기)**
1. 재고를 20행(= 워커 수)으로 나눈다. 행마다 5,000개
2. 시작 행을 고른다. 동기는 `사용자 id % 20`, 비동기는 워커마다 자기 행(워커 번호)
3. 잠그지 않는 조회로 남은 행을 보고, 트랜잭션 마지막에 그 행에 조건부 UPDATE. 0이면 다음 남은 행으로
4. 모든 행이 0이면 매진
- DB 안에서 해결하므로 보상 로직이 없다. 경합은 약 1/20이고, 비동기는 워커와 행이 1:1이라 행이 남아 있는 동안 경합이 거의 없다
- **이 경로만 READ COMMITTED (구현 중 확정):** 기본 격리 수준(REPEATABLE READ)에서는 조건부 UPDATE의 조건이 안 맞아도(빈 행) 그 행의 잠금이 커밋까지 남는다. 동시 폭주 테스트에서 트랜잭션 1이 행 A를 쥔 채 B로, 트랜잭션 2가 B를 쥔 채 A로 가는 교착이 실제로 났다(전체 테스트 2회 중 2회, MySQL 교착 기록으로 확인). READ COMMITTED는 조건이 안 맞는 행의 잠금을 바로 풀고, 다른 트랜잭션이 쥔 행도 최신 커밋 값이 조건에 안 맞으면 기다리지 않고 넘어간다(semi-consistent read). 차감에 성공한 트랜잭션은 그 행 하나만 쥐고 곧 커밋하므로 교착 고리가 생기지 않는다. 수정 뒤 전체 테스트 3회 연속 통과. 격리 수준 전환 명령(주문당 약 3개)이 붙는 대가는 측정에 그대로 포함된다

**③ 메모리 번호표 (트랜잭션 밖 판정)**
1. 번호표 발급기에서 번호 하나를 받는다. 돌려받은 번호가 있으면 그것부터, 없으면 다음 새 번호(1~10만). 둘 다 없으면 바로 매진. 발급기는 10만을 넘는 번호를 만들지 않는다
2. 같은 사용자의 예약이 이미 있으면 바로 이미 참여(메모리 집합). DB 기본 키가 최종 안전망
3. 번호표 예약을 주문 트랜잭션에 넘기고, 참여 행에 번호를 적는다. 트랜잭션 결과에 따라 번호를 확정하거나 돌려준다(3.4)
- 할인 주문끼리 기다리는 DB 행이 없다. 보상 규칙이 필요하고, 초과 판매는 DB 제약(유니크·외래 키)이 막는다

**비동기에서의 위치**
- 메모리 방식: 접수 단계에서 `대기 자리 예약 → 번호표 예약 → 202`. 매진이면 대기 자리를 돌려주고 409. 저장은 워커
- DB 방식(행 하나·여러 행): 접수는 DB 없이 202. 재고 처리는 워커 트랜잭션에서 한다

### 3.4 오류와 보상 규칙 (메모리 방식)

원칙: **번호를 돌려주는 조건은 "주문이 DB에 확실히 없다"뿐이다.**

Spring은 트랜잭션이 끝날 때 결과를 `TransactionSynchronization.afterCompletion(status)`로 알려 준다. spring-tx 6.2.1 코드로 확인한 동작:
- 정상 커밋 → `STATUS_COMMITTED`
- 커밋 전 예외로 롤백 → `STATUS_ROLLED_BACK`
- 커밋 호출 자체가 실패(`TransactionException`, 기본 설정) → `STATUS_UNKNOWN`
- 커밋 중 그 밖의 예외 → 롤백을 시도해 성공하면 `STATUS_ROLLED_BACK`, 롤백도 실패하면 `STATUS_UNKNOWN`

| 경우 | 주문 | 번호 처리 |
|---|---|---|
| 매진·이미 참여·시간 밖 (예약 전 판정) | 없음 | 예약하지 않았으니 할 일 없음 |
| 예약 후 트랜잭션에 넘기기 전 실패 (예: 커넥션을 못 얻음) | 확실히 없음 | 요청 스레드가 즉시 돌려줌 (예약 핸들의 `close()`, 대기 자리 `Slot`과 같은 모양) |
| 비동기: 대기 자리 없음 (429) | 없음 | 즉시 돌려줌 |
| 검증 실패 (차단 사용자, 영업 종료 등) → 롤백 | 확실히 없음 | 돌려줌 (`ROLLED_BACK`) |
| 저장 중 예외 → 롤백 | 확실히 없음 | 돌려줌 (`ROLLED_BACK`) |
| 참여 기본 키 중복·번호 제약 위반 → 롤백 | 확실히 없음 | 돌려줌 (`ROLLED_BACK`). 번호 제약 위반은 발급기 버그이므로 경고 로그와 카운터로 드러낸다 |
| 정상 커밋 | 있음 | 확정 (`COMMITTED`) |
| **커밋 결과 모름** (커밋 도중 연결 끊김 등) | 있을 수도 있음 | **바로 돌려주지 않는다.** 확인 대기 목록에 넣고, 대조기가 `promotion_participations`에 (이벤트, 사용자) 행이 있는지 본다. 있으면 확정, 없으면 돌려줌. DB가 응답하지 않으면 다시 시도 |
| 비동기: 워커에서 실패 | 확실히 없음 | 돌려줌, 상태 `FAILED` |

- 예약 핸들은 여러 번 불려도 한 번만 반납한다(대기 자리 `Slot`과 같은 방식)
- 돌려받은 번호는 매진 전이면 다음 사람이 받는다

### 3.5 재시작과 대조

- **기동할 때 (메모리 방식):** 참여 행에서 쓰인 번호와 참여 사용자를 읽어, 나머지 번호로 발급기를 다시 채운다. DB 방식은 DB 값이 곧 상태라 할 일이 없다
- **동기 서버가 죽으면:** 커밋 안 된 트랜잭션은 DB가 롤백하므로 기동 시 계산이 그대로 맞다
- **비동기 서버가 죽으면:** 큐에 있던 주문이 사라진다. 사용자는 202를 받았지만 주문이 없다. 기동 시 계산으로 그 번호는 저절로 돌아오므로 초과 판매는 없다. 사용자 쪽 유실은 메모리 큐의 기존 한계이고 영속 큐가 필요하다(1-2 한계에 이미 적혀 있음)
- **이벤트가 끝날 때:** 확인 대기 목록을 모두 처리하고 `남은 재고 + 참여 행 수 = 10만`을 확인한다

### 3.6 설정과 지표

- 설정: `omp.promotion.stock-mode=db-single|db-bucket|memory` (기본 memory, 측정 결과로 확정), `omp.promotion.buckets=20`. 동기·비동기는 엔드포인트로 고른다
- 지표:
  - `omp.promotion.reserved`, `omp.promotion.rejected{reason}` (reason = sold_out, already_joined, not_open, not_found)
  - `omp.promotion.confirmed` (확정된 할인 주문 수. 1초마다 읽어 초당 확정 건수를 그린다. 세 방식 모두 커밋 뒤에 센다)
  - `omp.promotion.released{reason}` (reason = before_tx, worker_before_tx, queue_full, submit_failed, rollback, unknown_absent)
  - `omp.promotion.unknown.pending`, `omp.promotion.remaining`, `omp.promotion.constraint_violation`
  - MySQL `Innodb_row_lock_waits`, `Innodb_row_lock_time` (DB 방식의 행 잠금 대기)

### 4.5 측정 전 예측 (용량 재측정 반영, 2026-09-29)

**숫자로 본 기준.** 시도는 5초 동안 초당 0 → 3,000건으로 늘고(누적 7,500건) 그 뒤 초당 3,000건이라, 시도 수가 10만에 닿는 시각은 정각 + 약 36초다. 할인 주문은 일반 주문보다 명령이 많아(메모리 방식: 참여 INSERT 1개 더 → 7개, DB 행 하나: 재고 조회·참여·차감 → 9개, DB 여러 행: 여기에 격리 수준 전환 3개 → 12개) 두 방식 모두 일반 주문 용량(동기 2,680 · 비동기 3,202건/s)보다 낮다.
- ⑥ 비동기 · 메모리: 시도를 모두 받으므로(큐 70,000칸) 번호표는 정각 + 약 36초에 다 나가고 그 뒤 시도는 즉시 409. 10만 건 확정은 비동기 할인 주문 용량에 달려, 초당 3,000건 이상이면 약 36초, 2,800건이면 약 38초다
- ③ 동기 · 메모리: 성공은 동기 할인 주문 용량만큼만 나온다. 초당 2,500건이면 10만 건 확정이 정각 + 약 42초, 2,300건이면 약 45초다. 그때까지 넘친 시도 약 2만~3만 건은 즉시 429를 받는다
- ③′ 동기(빠른 거절 없음) · 메모리: 넘친 시도가 Tomcat 대기열에 쌓여 응답이 초 단위로 늦어지고, k6 VU 상한(4,000)에 닿으면 보내지 못한 요청(= 받지 못한 주문)이 생긴다. 연결이 VU 수만큼 늘어나 용량 재측정 4회차처럼 무너질 수 있다
- 그래서 ③과 ⑥의 차이는 "10만 건 확정 시각 약 5~10초 + 넘친 시도 약 2만~3만 건의 처리"로 예상한다. 최고 유입이 동기 용량보다 약 12% 높을 뿐이라 차이가 크지 않을 수 있고, 그렇게 나오면 그대로 적는다

| 비교군 | 예측 |
|---|---|
| ① 동기 · DB 행 하나 | 할인 주문 커밋이 재고 행에서 하나씩 된다. 처리량 ≈ 1 ÷ 잠금 유지 시간이고, NVMe라 초당 수백~2천 건으로 폭이 넓어 측정 전에는 모른다. 넘친 요청이 Tomcat에 쌓여 성공 응답이 느려진다. 매진 뒤 시도는 잠그지 않는 조회라 빠르다 |
| ② 동기 · DB 여러 행 | 경합이 1/20로 줄어 동기 저장 용량에 가까워진다. 매진 직전에 빈 행을 도는 재시도가 늘 수 있다 |
| ③ 동기 · 메모리 번호표 | 매진·이미 참여는 DB 없이 즉시. 성공한 주문의 저장은 동기 용량에 묶여, 성공이 몰리는 약 36초 동안 용량을 넘는 만큼 밀린다 |
| ④ 비동기 · DB 행 하나 | 접수는 즉시 202지만 워커가 재고 행에서 하나씩 처리해 저장이 밀린다. 매진을 나중에 `FAILED`로 알게 된다 |
| ⑤ 비동기 · DB 여러 행 | 워커와 행이 1:1이라 저장은 빠르다. 매진은 여전히 나중에 `FAILED`로 알게 된다 |
| ⑥ 비동기 · 메모리 번호표 | 성공·매진 모두 즉시 응답. 성공분 10만 건은 큐가 받아 30초 안에 저장 |

**주의:** ③과 ⑥의 차이는 동기 포화 용량에 달려 있다. 동기 용량이 비동기와 비슷하게 나오면 이 시나리오의 핵심 효과는 저장 흡수가 아니라 **재고 처리 방식**이 된다. 그 경우 결과를 그대로 적는다.

→ 실제로 이 경우가 나왔다(동기 용량 ≈ 비동기). 결과와 예측 대비는 9장.

## 6. 한계

- 메모리 방식은 **서버 한 대 전제**다. 여러 대로 늘리면 Redis 원자 연산 같은 공용 발급기가 필요하다(범위 밖). DB 안전망(유니크·외래 키)은 여러 대에서도 초과 판매를 막는다
- 비동기는 큐에 있던 주문이 재시작 시 사라진다. 초과 판매는 없지만 202를 받은 사용자의 주문이 사라지는 문제는 남는다(영속 큐 필요)
- "결과 모름"을 확인하는 동안 그 번호는 팔리지 않는다. 확인이 늦으면 매진 직전에 잠깐 덜 팔릴 수 있다
- 비동기 DB 방식은 매진을 나중에 알게 한다. 접수에서 알려 주려면 접수 경로가 DB를 읽어야 한다(split 구성과 같은 비용)
- 시도 시각 분포(정각 직후 1~2분)는 가정이다. 선착순 이벤트의 시간별 주문 자료를 찾으면 교체한다

## 7. 구현 기록 (2026-09-29)

- **테스트 28개(79개 중):** 발급기 단위 8개, 세 방식 × 동기·비동기 동시 폭주(재고 100, 사용자 300명) 7개, 보상 규칙 11개, 커밋 결과 모름 2개. 5장 표의 항목을 모두 다룬다
- **DB 여러 행은 READ COMMITTED:** 3.3 참고. 테스트가 찾은 교착이 근거다
- **커밋 결과 모름 흉내:** "커밋하지 않고 예외"만 던지면 Hibernate가 JPA 규칙대로 진행 중인 트랜잭션의 EntityManager 종료를 미뤄, 잠금을 쥔 연결이 남았다. 실제로 커밋이 DB에 닿지 못하면(연결 끊김) DB가 되돌리므로 테스트도 "되돌린 뒤 예외"로 흉내 낸다
- **`rollbackOnCommitFailure`는 기본값(false) 유지:** 켜면 커밋 실패 뒤 롤백을 시도해 성공하면 "롤백됨"을 알리는데, 실제로는 커밋됐고 응답만 잃은 경우에도 그렇게 되어 번호를 돌려주면 같은 번호가 다시 나간다. 초과 판매는 참여 행의 유니크가 막지만, 그 번호를 받은 주문이 실패한다. "모름 → DB 확인"이 안전하다(이 경로는 트랜잭션 매니저가 커밋 예외를 던지게 한 테스트로만 확인했다. 실제 연결 끊김에서 Spring이 STATUS_UNKNOWN을 알리는지는 실행해 보지 않았다)
- **매진 응답은 스택 트레이스 없이:** 초당 수천 건 나오는 정상 결과라 예외 객체를 가볍게 만들고, 비동기 워커의 매진 실패는 건별 경고 로그를 남기지 않는다(P2에서 찾은 로그 폭주와 같은 문제를 막는다)
- **참여 행은 JdbcTemplate으로 넣는다:** 식별자를 직접 주는 엔티티의 `save`는 merge가 되어 SELECT를 한 번 더 한다
- **측정 준비:** k6 `benchmark/k6/03-promotion-flash.js`(시도 + 평상시 주문 동시, VU 2,000 미리 할당), `benchmark/sql/seed-users-300k.sql`(회원·장바구니 30만), `reset-round.sql`에 참여 기록 비우기, 이벤트 관리 API(`omp.promotion.admin-api=true`일 때: 생성·초기화·정합성 확인)

**결론: 결정을 둘로 나눈다**
- **결정 1. 재고 판정은 메모리 번호표로 정한다.** 근거가 가장 강하다. 매진 속도는 재고 방식이 정했다(메모리 37.9–41.0초 < DB 여러 행 52.5–56.7초 < DB 행 하나 약 90초, 비교군·회차마다 순서가 같음). 같은 재고 방식에서 동기·비동기 차이는 작다. 비동기 + DB 방식은 사용자를 기다리게 하므로(확정 7.6초·26.1초, 매진 통보 10.7초·30.4초), 비동기를 쓰려면 재고 판정은 접수에서 끝내야 한다
- **결정 2. 접수는 비동기(⑥)를 택한다.** 측정한 구성 중 매진 전 거절이 없고 요청 스레드를 묶지 않는 방식을, 확정 속도와 접수 p95 요구보다 우선해 고른 것이다(이 우선순위는 첫 측정의 1초 기록을 본 뒤 정했다). 빠른 거절 없는 동기는 서버가 거절하지는 않았지만 Tomcat 스레드 200개를 모두 쥐고 기다려 늦어졌고(평상시 주문 p95 0.74초, 요청 → 확정 평균 0.90초로 비동기 0.72초와 비슷), 빠른 거절 동기는 동시 처리가 상한을 넘는 순간 재고가 남아 있어도 거절했다(매진 전 429: 상한 130은 9,279–15,418건, 10-02에 더 잰 상한 190은 6,215–13,393건). 비동기는 큐(7만 칸)에 받아 두어 매진 전 거절 0. 대신 확정은 상한 190 동기가 빠르다(요청 → 확정 평균 0.08초 vs 비동기 0.72초, 재전송이 가장 적은 비동기 19회차도 0.31초). 성공 응답 p95는 뜻(200 저장 완료 vs 202 접수)과 회차의 TCP 재전송(상한 190 초당 1–14건, 비동기 3–78건)이 달라 우열을 정하지 않는다
- **응답 요구는 조건부로 적는다.** 접수 p95 ≤ 200ms는 네트워크 재전송이 가장 적은 회차(19회차, 24ms)에서만 지켰고, 재전송이 초당 75–78건이던 두 회차는 307·565ms로 넘었다. "요구를 지켜서 골랐다"고 쓰지 않는다

## 1-1. 리뷰 통계 갱신의 데드락과 갱신 유실을 통계 모델 분리와 원자 UPDATE로 제거

### 결과 요약

- Review INSERT와 Shop UPDATE 사이의 데드락 원인을 MySQL 락 관점에서 분석하고, 같은 구조가 갱신 유실도 일으킨다는 점을 확인
- 리뷰 통계를 `shop_review_stats`로 분리하고 이전 값을 읽지 않는 원자 증가 UPDATE로 갱신해 두 결함을 제거
- 동시 사용자 `[VUS]`명, 가게 `[SHOP_POOL]`개 집중 부하 15분에서 데드락 `[측정값: ① lock_deadlocks 증가분]`건 → 0건, 통계 불일치 가게 `[측정값: ① verify 4-a 행 수]` → 0, 성공 처리량 `[측정값: ① reviews_created]` → `[측정값: ② reviews_created]`건

### 문제 상황

- 리뷰를 저장한 뒤 가게의 리뷰 개수와 평균 평점을 갱신하는 구조. 통계 컬럼이 `shops` 테이블에 있어 리뷰 INSERT와 가게 UPDATE가 같은 트랜잭션에서 같은 행을 다룸
- 동시 리뷰 작성 부하 테스트에서 데드락으로 요청이 실패하고, 실패하지 않은 요청 사이에서도 최종 통계가 실제 리뷰와 달라지는 현상 확인
- 외래 키를 유지한 채 데드락과 유실을 모두 없애는 것이 목표

### 원인 분석

**데드락**
- Review INSERT는 외래 키 `shop_id` 검사를 위해 부모 `shops` 행에 공유 락(S)을 획득
- 같은 트랜잭션에서 `shops` 통계를 UPDATE하려면 같은 행의 배타 락(X)이 필요
- 두 트랜잭션이 각자 S락을 든 상태에서 서로 X락을 기다리면 데드락. InnoDB가 한쪽을 롤백해 500 응답

(원문 시퀀스 그림 유지)

**갱신 유실**
- 통계를 "읽고 → 애플리케이션에서 계산 → 쓰기"로 갱신하면, 두 요청이 같은 이전 값을 읽은 뒤 나중 쓰기가 앞선 쓰기를 덮어씀
- 예: 리뷰 10개·합계 30점에 5점과 4점이 동시에 들어오면 12개·39점이어야 하지만, 둘 다 10개·30점을 기준으로 계산하면 11개·35점 또는 11개·34점으로 끝남
- 데드락이 없는 겹침에서도 발생하므로 데드락만 없애면 유실은 남음

### 고려한 해결 방법

| 방법 | 장점 | 판단 |
|---|---|---|
| 외래 키 제거 | FK 공유 락 자체가 사라짐 | DB 제약이 없어져 정합성 관리 부담 증가 |
| 비관적 락 | 갱신 순서 직렬화 | 핫 가게에서 락 대기가 응답 시간에 그대로 포함 |
| 통계 행 분리 + 원자 증가 UPDATE | S락(shops)과 X락(stats) 대상이 달라 승격 경로 제거. 이전 값을 읽지 않아 유실 없음 | 선택. 통계 갱신 위치(같은 트랜잭션 vs 커밋 후)는 측정으로 결정 |

### 선택한 해결 방법

**1. 데이터 모델 분리**

가게 기본 정보와 자주 바뀌는 리뷰 통계의 책임을 나눈다. 리뷰 INSERT의 FK 검사는 `shops` 행에, 통계 UPDATE는 `shop_review_stats` 행에 락을 잡으므로 같은 행에서 S→X 승격을 기다리는 경로가 없다.

| 컬럼 | 역할 |
|---|---|
| shop_id | 가게 식별자 (PK, shops 1:1) |
| review_count | 누적 리뷰 개수 |
| rating_sum | 누적 평점 합계 |
| average_rating | 평균 평점. 매 갱신 시 `(rating_sum + r) / (review_count + 1)`로 계산해 저장 |

**2. 원자 증가 UPDATE**

```sql
UPDATE shop_review_stats
SET average_rating = (rating_sum + :r) / (review_count + 1),
    rating_sum     = rating_sum + :r,
    review_count   = review_count + 1
WHERE shop_id = :shopId
```

- 이전 값을 애플리케이션에서 읽지 않고 DB가 현재 값 기준으로 증가시키므로 실행 순서와 무관하게 결과가 같다. 동시 갱신의 덮어쓰기가 없다
- MySQL은 단일 테이블 UPDATE의 SET을 왼쪽부터 평가하고 뒤의 대입은 갱신된 값을 본다. 평균을 맨 앞에 두어야 원래 합계·개수로 계산된다 (뒤에 두면 증가분이 두 번 반영되어 5점 뒤 1점이 평균 3.00이 아니라 2.33이 됨. MySQL 8.0.36에서 확인)
- 이 방식은 stats 행의 행 락을 사용한다. "락 없이 처리"가 아니라 "락 승격 충돌 경로와 읽고-쓰기 경쟁을 없앤" 것이다

**3. 통계 갱신 위치는 측정으로 결정**

`omp.review.stats.mode` 설정으로 두 방식을 같은 코드에서 전환한다.

| 모드 | 동작 | 장점 | 대가 |
|---|---|---|---|
| sync (②) | 리뷰 INSERT와 같은 트랜잭션에서 UPDATE | 리뷰와 통계가 원자적으로 일치 | 핫 가게 stats 행 락 대기가 리뷰 응답 시간에 포함 |
| async (③) | 리뷰 커밋 후 `@TransactionalEventListener(AFTER_COMMIT)` → 전용 스레드 풀에서 UPDATE | 락 대기를 응답에서 격리 | 최종 정합성 창. 풀 포화 거절·실패 시 재처리가 없어 불일치가 지속 |

풀 포화 시 요청 스레드에서 몰래 실행하는 CallerRunsPolicy는 쓰지 않는다. 거절은 `omp.review.stats.rejected`, 실행 실패는 `omp.review.stats.failed` 카운터로 드러내고 리뷰 ID를 로그에 남긴다.

### 검증 방법

동일 조건에서 세 설계를 비교했다. 재현 브랜치 ①은 현재 코드(main)에서 통계 필드 3개와 리뷰 저장 메서드만 옛 설계로 되돌린 것으로, 스레드 풀·검증·예외 처리는 동일하다.

| 항목 | 값 |
|---|---|
| 도구 | k6 `[버전]`, closed model (`constant-vus`), 동시 사용자 `[VUS]`명, 15분, 3회 중앙값 |
| 경합 조건 | 리뷰 대상 가게 `[SHOP_POOL]`개에 집중 (결함 재현용 조건, 실제 트래픽 모델 아님) |
| 서버 | `[CPU/RAM]`, JDK 21 `-Xms2g -Xmx2g`, MySQL 8.0.36 동거, HikariCP 20 |
| 데드락 판정 | `information_schema.INNODB_METRICS.lock_deadlocks` 증가분, `SHOW ENGINE INNODB STATUS` 캡처 |
| 정합성 판정 | 종료 후 `shop_review_stats`와 `SELECT COUNT(*), SUM(rating) FROM reviews GROUP BY shop_id` 완전 일치, 평균 = ROUND(sum/count, 2) |

### 결과

| 항목 | ① shops 통계 + 같은 트랜잭션 | ② 통계 분리 + 같은 트랜잭션 | ③ 통계 분리 + 커밋 후 비동기 |
|---|---|---|---|
| 데드락 (15분) | `[측정값: lock_deadlocks 증가분]`건 | 0건 | 0건 |
| 5xx 응답 | `[측정값: reviews_5xx]`건 | 0건 | 0건 |
| 통계 불일치 가게 수 | `[측정값: verify 4-a 행 수]` | 0 | `[측정값: verify 2 행 수, = rejected+failed]` |
| 성공 처리량 (2xx, 15분) | `[측정값: reviews_created]`건 | `[측정값]`건 | `[측정값]`건 |
| 응답 p95 / p99 | `[측정값]` ms | `[측정값]` ms | `[측정값]` ms |
| 통계 반영 완료까지 | 즉시 | 즉시 | k6 종료 후 `[측정값: queued=0·active=0 까지]`초 |

- ①→②: 모델 분리의 효과. 데드락과 유실이 0이 되고 5xx가 사라진 만큼 성공 처리량이 `[측정값]`% 변화
- ②→③: 비동기의 효과. p95 `[측정값]`ms → `[측정값]`ms. 정합성은 반영 완료 후 일치하되, 거절·실패 `[측정값]`건은 불일치로 남음
- 최종 선택: `[② 또는 ③. ②→③ 차이가 p95 X ms 미만이면 ②를 택하고 "비동기 복잡도를 걷어냈다"로 서술]`

### 한계 및 후속 개선

- 제거한 것은 "리뷰 INSERT의 FK 공유 락에서 같은 행 배타 락으로 승격하는 충돌 경로"다. 다른 트랜잭션과의 락 순서까지 포함해 모든 데드락이 불가능하다고 주장하지 않는다
- 원자 UPDATE는 동시 갱신의 덮어쓰기를 막지만 이벤트 누락·중복 적용을 막지는 않는다. ③에서 거절·실패한 갱신은 재처리가 없어 **불일치가 지속**된다. 운영 확장 시 Transactional Outbox 또는 리뷰 원본 기준 재집계가 필요
- 통계 행이 없는 가게에 리뷰가 들어오면 UPDATE 영향 행이 0이다. ②는 리뷰까지 롤백, ③은 실패 카운터로 기록한다
- 부하 조건은 결함 재현을 위해 소수 가게에 집중한 것으로 실제 트래픽 분포가 아니다

### 이전 접근 (한 줄)

초기에는 리뷰 저장과 통계 갱신의 트랜잭션을 분리하고 Shop에 낙관적 락과 재시도를 두는 방식으로 접근했으나, 읽고-계산-쓰기 구조의 유실과 재시도 소진 문제가 남아 모델 분리와 원자 UPDATE로 변경했다.

### 느낀 점

- 데드락은 락의 종류와 획득 순서 문제이고, 유실은 읽고-쓰기 사이의 경쟁 문제다. 둘은 원인이 다르므로 각각 재현하고 각각 검증해야 했다
- 비동기는 성능 개선이 아니라 "락 대기를 어디서 기다릴 것인가"의 선택이고, 그 대가로 정합성 창과 실패 전달 책임이 생긴다는 점을 측정으로 확인했다

## 1-1. 리뷰 저장의 데드락과 통계 갱신 유실을 통계 모델 분리와 원자 UPDATE로 개선

기간: 초기 구현 2025.03 → 원인 재분석·재설계·검증 2026.08–10

### 결과 요약

- 리뷰 INSERT의 외래 키 검사가 잡은 공유 락이 같은 가게 행의 배타 락으로 승격되며 생기는 데드락과, 읽고-계산-쓰기로 생기는 통계 갱신 유실을 원인별로 나누고, 실행 순서를 통제한 두 시나리오로 각각 재현했다
- 통계를 `shop_review_stats`로 분리하고 원자 증가 UPDATE로 바꿔 두 원인을 없앴다. 리뷰와 통계는 같은 트랜잭션에서 함께 반영한다
- 같은 가게에 동시 작성이 몰리는 극단 조건(가게 3곳, 가상 사용자 50명, 15분)에서 개선 전 설계(재구성)는 2회 모두 요청의 약 76%가 데드락으로 실패하고(1,032,110 · 1,017,457건) 성공한 리뷰의 약 46%가 통계에서 빠졌다(152,030 · 149,939건). 개선 후 설계는 2회 모두 데드락 0, 통계 불일치 0, 성공 응답 p95 35.5–37.1ms(허용 500ms)였다
- 현실 부하(초당 20건, 가게 1,000곳에 균등, 15분)에서는 개선 전 설계도 데드락 0, 통계 누락 0이었다. 평소에는 드러나지 않다가 특정 가게에 작성이 몰릴 때 터지는 결함이라, 부하 테스트가 아니라 실행 순서를 통제한 재현 테스트로 원인을 확정했다
- 커밋 후 비동기 반영(③)은 극단 조건에서 응답 p95가 33.0–33.9ms로 약 3ms 빨랐지만, 통계 갱신의 60–62%가 큐 초과로 버려져 복구되지 않았다(워커 10·큐 2,000칸, 재시도 없는 구성). 요구사항 우선순위(원본 > 최종 정합성 > 신선도 > 응답 지연)에 따라 같은 트랜잭션 반영(②)을 채택했다. 현실 부하에서 ②와 ③의 p95 차이는 약 0.6ms(4.81 → 4.26ms, 설계별 1회)였다

### 문제 상황

- 리뷰를 저장한 뒤 가게의 리뷰 개수와 평균 평점을 갱신한다. 통계 컬럼이 `shops` 테이블에 있어, 리뷰 INSERT와 가게 통계 UPDATE가 같은 트랜잭션에서 같은 가게 행을 다뤘다
- 동시 작성 테스트에서 데드락으로 요청이 실패했고, 저장된 리뷰와 가게 통계가 어긋나는 갱신 유실도 확인했다
- 이 설계의 코드는 git 이력에 남아 있지 않다(통계가 들어간 첫 커밋 `fe6ca3e`, 2025-03부터 이미 커밋 후 비동기 + 재시도다). 그래서 현재 코드에서 통계 필드와 저장 메서드(Shop·ReviewService 2파일)만 옛 설계로 되돌린 재현 브랜치 `bench/review-before-v2`로 결함을 재현하고 측정했다(①)
- 목표: 외래 키를 유지한 채 두 결함을 원인에서 없애고, 리뷰와 통계가 최종적으로 일치하도록 보장한다

### 원인 분석

**데드락**
- 리뷰 INSERT는 외래 키 `shop_id` 검사를 위해 부모 `shops` 행에 공유 락(S)을 잡는다
- 같은 트랜잭션에서 `shops` 통계를 UPDATE하려면 같은 행의 배타 락(X)이 필요하다
- 같은 가게의 두 트랜잭션이 각자 S락을 쥔 채 X락을 요청하면, 서로 상대의 S락이 풀리기를 기다리는 순환 대기가 된다. InnoDB가 한쪽을 롤백해 500이 된다

**갱신 유실**
- 통계를 "읽고 → 애플리케이션에서 계산 → 쓰기"로 갱신해, 두 요청이 같은 이전 값을 읽으면 나중에 쓴 요청이 앞선 갱신을 덮어쓴다
- 예: 리뷰 10개·합계 30점에 5점과 4점이 동시에 들어오면 12개·39점이어야 하지만 11개·35점 또는 11개·34점으로 끝난다
- 데드락이 없는 겹침에서도 생기므로 데드락만 없애면 유실은 남는다. 두 결함은 원인이 다르다

### 고려한 해결 방법

| 방법 | 장점 | 판단 |
|---|---|---|
| 외래 키 제거 | FK 공유 락이 사라짐 | 리뷰-가게 참조를 DB가 보장하지 못해 애플리케이션에 맡겨야 하고, 읽고-계산-쓰기의 유실은 그대로 남음 |
| 부모 shops 행 비관적 락 (SELECT … FOR UPDATE) | INSERT 전에 X락을 잡아 데드락과 덮어쓰기를 함께 방지 | 리뷰 INSERT 전부터 커밋까지 같은 가게의 요청이 모두 직렬화됨. 가게 정보 수정도 같은 행을 기다림(재지 않음) |
| 커밋 후 별도 트랜잭션 + shops 낙관적 락·재시도 (초기 구현, 2025.03) | 데드락 경로를 피하고 덮어쓰기를 감지 | 경합 때 재시도가 몰리고, 재시도가 다하면 통계가 복구 없이 빠짐. 비동기라 반영 지연과 누락 경로가 생김(다시 재지 않음) |
| **통계 행 분리 + 원자 증가 UPDATE** | S락(shops)과 X락(stats)의 대상이 달라 승격 경로가 없음. 이전 값을 읽지 않아 덮어쓰기가 없음 | **채택.** 같은 가게의 통계 UPDATE끼리는 stats 행에서 커밋까지 기다리고, 통계 갱신이 실패하면 리뷰 저장도 실패함 |

### 선택한 해결 방법

**1. 통계 모델 분리**

가게 기본 정보와 리뷰에서 계산되는 통계를 `shop_review_stats`(가게 id, 리뷰 개수, 평점 합계, 평균 평점)로 나눴다. 리뷰 INSERT의 FK 검사는 `shops` 행에, 통계 UPDATE는 stats 행에 락을 잡으므로 같은 행에서 S→X로 승격하며 기다리는 경로가 없다. 같은 가게의 stats 행 UPDATE끼리의 락 대기는 남는다(집중 경합 15분에 약 189만 회, 성공 응답 p95 35.5–37.1ms).

**2. 원자 증가 UPDATE**

```sql
UPDATE shop_review_stats
SET average_rating = (rating_sum + :r) / (review_count + 1),
    rating_sum     = rating_sum + :r,
    review_count   = review_count + 1
WHERE shop_id = :shopId
```

- 이전 값을 애플리케이션에서 읽지 않고 DB가 현재 값 기준으로 증가시켜, 실행 순서와 무관하게 결과가 같다
- MySQL은 단일 테이블 UPDATE의 SET을 왼쪽부터 평가하고 뒤의 대입은 갱신된 값을 본다. 평균을 맨 앞에 둬야 원래 합계·개수로 계산된다(뒤에 두면 5점 뒤 1점의 평균이 3.00이 아니라 2.33. MySQL 8.0.36에서 확인)
- stats 행의 행 락은 쓴다. "락 없이"가 아니라 "락 승격 경로와 읽고-쓰기 경쟁을 없앤" 것이다

**3. 통계 반영 시점: 요구사항 우선순위로 판단**

| 순위 | 대상 | 요구 수준 |
|---|---|---|
| 1 | 리뷰 원본 | 유실·중복 없이 저장 |
| 2 | 통계의 최종 정합성 | 가게 평판·노출에 직결되므로 최종적으로 원본과 정확히 일치 |
| 3 | 통계 신선도 | 즉시 반영까지는 필요 없음 |
| 4 | 작성 응답 지연 | 성공 응답 p95 ≤ 500ms면 충분 |

- 커밋 후 비동기(③)가 앞서는 것은 4순위인 응답 지연뿐이고, 2순위에서는 거절·실패·재시작 때 복구되지 않는 누락이 생긴다. 그래서 같은 트랜잭션(②)을 채택하고, ②가 응답 한도를 지키는지 측정으로 확인했다
- `omp.review.stats.mode`로 두 방식을 같은 코드에서 바꿀 수 있게 두었다(기본 `sync`). ③도 풀이 차면 요청 스레드에서 몰래 실행하지 않고 거절을 카운터로 드러낸다
- ③으로 바꿀 조건: 통계 장애와 무관하게 리뷰 작성이 성공해야 한다는 요구가 생기거나, 리뷰에 딸린 후속 작업(랭킹·검색 색인·알림)이 늘면 Transactional Outbox와 재처리를 함께 도입한다. 유실 없이 비동기로 하려면 이 둘이 필요하다

### 결과

**원인 재현 (실행 순서를 통제한 두 시나리오)**
- 데드락 순서: 두 트랜잭션이 모두 리뷰를 INSERT한 뒤 차례로 통계를 갱신하면, ①은 한쪽이 데드락(MySQL 1213)으로 리뷰까지 롤백됐다(`lock_deadlocks` +1)

- 현실 부하: 개선 전 설계도 15분 동안 결함이 0건이었다. 가게 1,000곳에 균등하게 나뉜 부하에서는 같은 가게의 리뷰가 몇 ms 안에 겹칠 일이 거의 없기 때문이다. 결함은 평소 지표로는 보이지 않고 몰릴 때 터진다. ②·③도 결함 0이었고, ③의 p95는 ②보다 약 0.6ms 짧았지만(4.81 → 4.26ms) 1회 측정이라 이득으로 보지 않는다

### 한계 및 후속 개선

- 없앤 것은 "리뷰 INSERT의 FK 공유 락이 같은 행 배타 락으로 승격하는 경로"다. 다른 트랜잭션과의 락 순서까지 포함해 모든 데드락이 불가능하다고 주장하지 않는다
- 같은 가게의 stats 행 UPDATE는 커밋까지 직렬화된다. 극단 경합에서 행 잠금 대기가 15분에 약 189만 회였지만 성공 응답 p95는 35.5–37.1ms였다. 더 몰리는 조건이 확인되면 집계 방식 변경을 검토한다
- 원자성의 대가로 통계 갱신이 실패하면 리뷰 작성도 실패한다. 통계 행 누락은 가게 생성 때 통계 행을 같은 트랜잭션에서 만들어 예방한다
- 리뷰가 주문과 연결되지 않고 중복 방지가 없어, 클라이언트 재시도 때 두 번 반영될 수 있다. 주문당 1회 작성 제약과 멱등 키가 후속 과제다
- 현실 부하는 가게를 균등하게 고른다. 인기 가게로 쏠리는 실제 분포에서 결함이 얼마나 자주 나타날지는 두 조건(가게 1,000곳 균등 · 가게 3곳 집중) 사이 어딘가이며, 어느 정도 쏠림부터 나타나는지는 재지 않았다
- 부하로 비교한 것은 ①(재구성)·②·③ 세 설계다. 고려한 대안 중 비관적 락과 초기 구현(낙관적 락·재시도)은 다시 재지 않았다

### 이전 접근과의 구분

- 초기 구현(2025.03)은 데드락을 피하려고 리뷰 커밋 후 별도 트랜잭션·비동기로 통계를 갱신하고, Shop에 낙관적 락과 재시도를 적용했다. 이번에는 원인을 다시 분석해 모델 분리와 원자 UPDATE로 원인을 없앴고, 반영 방식은 요구사항 우선순위로 다시 판단했다
- 옛 nGrinder 수치(15분 처리량 2.5만 → 3.8만)는 재현하지 않으며 현재 설계의 성과로 쓰지 않는다. ①은 "기존 설계를 재구성한 결함 재현 버전"으로 밝힌다

### 느낀 점

- 데드락은 락의 종류와 획득 순서 문제이고, 유실은 읽고-쓰기 사이의 경쟁 문제다. 원인이 다르면 해결과 검증도 따로 해야 한다
- 처음의 트랜잭션 분리는 원인을 피해 간 우회책이었다. 원인을 없애자 우회책이 필요 없어졌고, 남은 선택은 성능 수치가 아니라 무엇을 먼저 지켜야 하는지로 판단해야 했다

# 포트폴리오 1-1 재작성 초안 (2026-09-24)

> 상태: **측정 전 초안.** 결과는 모두 `[측정값: 출처]`로 남긴다. 성능은 3회 중앙값과 범위, 오류·불일치는 모든 회차의 건수를 기록한다. 목표값 0을 실측값으로 쓰지 않는다.

## 1-1. 리뷰 저장의 데드락과 통계 갱신 유실을 통계 모델 분리와 원자 UPDATE로 개선

### 결과 요약

- 리뷰 INSERT의 FK 공유 락이 같은 shops 행의 배타 락으로 승격되는 데드락과, 읽고-계산-쓰기로 인한 통계 갱신 유실을 원인별로 분석
- 통계를 `shop_review_stats`로 분리하고 원자 증가 UPDATE로 갱신해 두 결함을 제거. 리뷰와 통계는 같은 트랜잭션에서 원자적으로 반영
- 초기 구현에서 데드락 회피용으로 쓰던 커밋 후 비동기 갱신은, 원인을 제거한 뒤 정합성 요구 기준으로 다시 판단해 채택하지 않음
- 같은 동시 사용자 `[VUS]`명·가게 `[SHOP_POOL]`개 집중 부하 15분에서 데드락 `[측정값: ①]` → `[측정값: ②]`건, 누락된 통계 갱신 `[측정값: ① 개수 부족분]` → `[측정값: ②]`건, 성공 응답 `[측정값: ① reviews_created]` → `[측정값: ② reviews_created]`건, ② 성공 응답 p95 `[측정값]`ms (허용 한도 500ms). **측정 후에만 결과로 확정**

### 문제 상황

- 리뷰를 저장한 뒤 가게의 리뷰 개수와 평균 평점을 갱신하는 구조. 통계 컬럼이 `shops` 테이블에 있어 리뷰 INSERT와 가게 UPDATE가 같은 트랜잭션에서 같은 행을 다룸
- 동시 리뷰 작성 테스트에서 데드락으로 요청이 실패했고, 저장된 리뷰와 최종 통계가 달라지는 갱신 유실도 확인
- 목표: 외래 키를 유지한 채 두 결함을 원인에서 제거하고, 리뷰와 통계가 최종적으로 일치하도록 보장

### 원인 분석

**데드락**
- Review INSERT는 외래 키 `shop_id` 검사를 위해 부모 `shops` 행에 공유 락(S)을 획득
- 같은 트랜잭션에서 `shops` 통계를 UPDATE하려면 같은 행의 배타 락(X)이 필요
- 두 트랜잭션이 각자 S락을 든 상태에서 서로 X락을 기다리면 데드락. InnoDB가 한쪽을 롤백해 500 응답

(원문 시퀀스 그림 유지)

**갱신 유실**
- 통계를 "읽고 → 애플리케이션에서 계산 → 쓰기"로 갱신하면, 두 요청이 같은 이전 값을 읽은 뒤 나중 쓰기가 앞선 쓰기를 덮어씀
- 예: 리뷰 10개·합계 30점에 5점과 4점이 동시에 들어오면 12개·39점이어야 하지만, 둘 다 10개·30점을 기준으로 계산하면 11개·35점 또는 11개·34점으로 끝남
- 데드락이 없는 겹침에서도 발생하므로 데드락만 없애면 유실은 남는다. 두 결함은 원인이 다르다

### 고려한 해결 방법

**결함 해결 방법**

| 방법 | 장점 | 판단 |
|---|---|---|
| 외래 키 제거 | FK 공유 락 자체가 사라짐 | DB 제약이 없어져 정합성 관리 부담 증가 |
| 부모 shops 행 비관적 락 (`SELECT … FOR UPDATE`) | 리뷰 INSERT 전에 X락을 확보해 데드락과 덮어쓰기를 함께 방지 | 락을 트랜잭션 전체 동안 보유해 같은 가게 리뷰의 INSERT까지 직렬화. 가게 정보 수정도 같은 행을 기다림 |
| 커밋 후 별도 트랜잭션 + 낙관적 락·재시도 (초기 구현) | 데드락 경로를 피하고 덮어쓰기를 감지 | 경합 시 재시도가 몰리고, 재시도가 소진되면 통계 미반영. 비동기 반영으로 반영 지연과 누락 경로가 생김 |
| 통계 행 분리 + 원자 증가 UPDATE | S락(shops)과 X락(stats) 대상이 달라 승격 경로 제거. 이전 값을 읽지 않아 덮어쓰기 방지. 직렬화 구간은 stats 행의 UPDATE부터 커밋까지 | **채택** |

**통계 반영 시점**

| 방식 | 장점 | 판단 |
|---|---|---|
| 리뷰와 같은 트랜잭션 (②) | 리뷰와 통계가 원자적으로 일치. 복구 경로가 필요 없음 | **채택.** 통계 실패 시 리뷰도 실패하고, 핫 가게의 stats 행 락 대기가 응답에 포함됨 → 허용 한도로 검증 |
| 커밋 후 비동기 (③) | 응답이 통계 갱신을 기다리지 않음. 통계 실패가 리뷰를 롤백시키지 않음 | 비교군. 거절·실패·재시작 시 누락이 복구되지 않음. 이득은 우선순위가 낮은 응답 지연 |

### 선택한 해결 방법

**1. 데이터 모델 분리**

가게 기본 정보와 리뷰에서 계산되는 통계를 별도 모델로 관리한다. 리뷰 INSERT의 FK 검사는 `shops` 행에, 통계 UPDATE는 `shop_review_stats` 행에 락을 잡으므로 기존의 같은 shops 행에서 S→X 승격을 기다리는 경로가 사라진다. 같은 가게의 stats 행 UPDATE 간 락 대기는 남는다.

| 컬럼 | 역할 |
|---|---|
| shop_id | 가게 식별자 (PK, shops 1:1) |
| review_count | 누적 리뷰 개수 |
| rating_sum | 누적 평점 합계 |
| average_rating | 평균 평점. 매 갱신 시 `(rating_sum + r) / (review_count + 1)`로 계산해 저장 |

**2. 원자 증가 UPDATE**

```sql
UPDATE shop_review_stats
SET average_rating = (rating_sum + :r) / (review_count + 1),
    rating_sum     = rating_sum + :r,
    review_count   = review_count + 1
WHERE shop_id = :shopId
```

- 이전 값을 애플리케이션에서 읽지 않고 DB가 현재 값 기준으로 증가시키므로 실행 순서와 무관하게 결과가 같다. 동시 갱신의 덮어쓰기가 없다
- MySQL은 단일 테이블 UPDATE의 SET을 왼쪽부터 평가하고 뒤의 대입은 갱신된 값을 본다. 평균을 맨 앞에 두어야 원래 합계·개수로 계산된다 (뒤에 두면 증가분이 두 번 반영되어 5점 뒤 1점이 평균 3.00이 아니라 2.33이 됨. MySQL 8.0.36에서 확인)
- 이 방식은 stats 행의 행 락을 사용한다. "락 없이 처리"가 아니라 "락 승격 충돌 경로와 읽고-쓰기 경쟁을 없앤" 것이다

**3. 통계 반영 시점: 요구사항 우선순위로 판단**

결함은 1·2로 제거되므로, 통계를 같은 트랜잭션에서 반영할지 커밋 후 비동기로 반영할지는 결함 해결과 별개의 선택이다. 리뷰 작성에서 지켜야 할 것을 우선순위로 정하고 그 순서로 판단했다.

| 순위 | 대상 | 요구 수준 |
|---|---|---|
| 1 | 리뷰 원본 | 저장된 리뷰는 유실·중복 없이 남아야 함 |
| 2 | 통계의 최종 정합성 | 가게 평판·노출에 직결되므로 최종적으로 원본과 정확히 일치해야 함 |
| 3 | 통계 신선도 | 즉시 반영까지는 필요 없음 |
| 4 | 작성 응답 지연 | 불편하지 않은 수준이면 충분. 허용 한도 성공 응답 p95 ≤ 500ms |

③이 앞서는 것은 4순위인 응답 지연뿐이고, 2순위인 최종 정합성에서는 거절·실패·재시작 시 복구되지 않는 누락이 생긴다. ③에 남는 근거인 "통계 장애가 리뷰 작성을 막으면 안 된다"는 복구 경로가 있어야 성립하는데, ②에서 통계만 실패하는 경우는 통계 행 누락 같은 데이터 결함이나 극단적인 락 대기 타임아웃 정도다. 그래서 ②를 채택하고, ②가 응답 허용 한도를 지키는지를 측정으로 검증한다.

`omp.review.stats.mode`로 두 방식을 같은 코드에서 전환할 수 있게 두고(기본 `sync`), ③은 비교군으로 측정한다. ③도 풀 포화 시 요청 스레드에서 몰래 실행하지 않고(CallerRunsPolicy 미사용) 거절·실패를 카운터와 로그로 드러낸다.

③으로 전환할 조건도 정해 두었다. 통계 장애와 무관하게 리뷰 작성이 성공해야 한다는 요구가 생기거나, 랭킹·검색 색인·알림처럼 리뷰에 딸린 후속 작업이 늘어나면 Transactional Outbox 기반 비동기와 재처리를 함께 도입한다.

### 검증 방법

재현 브랜치 ①은 현재 코드에서 통계 필드 3개와 리뷰 저장 메서드만 옛 설계로 재구성한 것으로, 스레드 풀·검증·예외 처리는 동일하다.

**부하 전 원인 재현:** 두 트랜잭션의 실행 순서를 제어해 ①에서 (a) 모두 FK 검사 S락을 보유한 뒤 X락을 요구하는 데드락, (b) 같은 이전 통계를 읽은 뒤 순차 커밋하며 덮어쓰는 갱신 유실을 각각 확인한다. **같은 실행 순서를 ②에 적용해** (a)는 데드락 없이 대기 후 완료되고 (b)는 최종 값이 맞는지 확인한다. 현재 순차 통계 테스트와 주석 처리된 동시성 테스트만으로 재현 완료를 주장하지 않는다.

**실패 경계:** 통계 행 누락을 강제하면 ②는 리뷰까지 롤백되고(원자성), ③은 리뷰를 유지한 채 실패 카운터만 오른다 (`ReviewStatsMissingRowSyncModeTest`·`ReviewStatsMissingRowAsyncModeTest`). 정상 부하 회차와 분리해 기록한다.

| 항목 | 값 |
|---|---|
| 장비 배치 | 데스크탑 k6 → 유선 LAN → 노트북 Spring Boot + MySQL. 두 장비 CPU·RAM·OS·전원 설정 기록 |
| 도구 | k6 `[버전]`, closed model (`constant-vus`), `[VUS]` VU, 15분 × 3회. 성능은 중앙값·범위, 오류·불일치는 회차별 건수 |
| 파일럿 | `VUS=50`, `SHOP_POOL=3`, 1분에서 시작. 원인·부하기 여유 확인 후 본측정 조건을 세 설계에 동일하게 고정 |
| 경합 조건 | 리뷰 대상 가게 `[SHOP_POOL]`개에 집중, 평점 1~5. 결함 재현용 조건이며 실제 트래픽 분포나 서비스 전체 용량을 의미하지 않음 |
| 서버 | 물리 4코어·RAM 16GB, JDK 21 `-Xms2g -Xmx2g`, MySQL `[실제 버전]` 동거, HikariCP `[P]` (코어 수 기반 공식 + 파일럿으로 확정). 리뷰 격리 수준·DB 주요 설정 기록 |
| ③ 통계 풀 | core = max = `[P/2]`, queue 2000, AbortPolicy. 커넥션 독점 방지 규칙으로 고정 |
| 회차 준비 | 서버 재시작 → 워밍업 → 잔여 작업 종료 확인 → 리뷰·통계 초기화 → 카운터 시작값 기록 |
| 데드락 판정 | `information_schema.INNODB_METRICS.lock_deadlocks` 증가분과 데드락 로그. 5xx를 전부 데드락으로 간주하지 않음 |
| 정합성 판정 | 작업 종료 후 리뷰 원본 집계와 count·sum 일치, 통계 행 누락 0, 평균 = ROUND(sum/count, 2). ①은 shops, ②·③은 stats와 비교 |
| ② 채택 검증 | 모든 회차에서 데드락·불일치·실패 0, 성공 응답 p95 ≤ 500ms. p95만 넘으면 `SHOP_POOL=1000` 분산 회차를 추가해 판단 |
| 응답 지연 | 전체 응답과 성공 응답의 p95·p99를 구분 |

closed model에서는 응답이 빨라지면 유입률도 바뀐다. ②→③ 결과는 같은 VU 수에서의 비교로 한정하고, 같은 유입률에서 ③의 대가를 보이려면 open model 회차를 추가한다.

| 부하 종료 후 잔여 작업 종료 관측 | 별도 통계 작업 없음 | 별도 통계 작업 없음 | `[측정값: queued=0·active=0 관측까지]`초, 폴링 간격 병기 |

- **①→②:** 모델 분리와 원자 갱신의 결합 효과. 원인별 기여는 제어된 재현 테스트로 보이고, 부하 결과로는 데드락·누락된 갱신·성공 응답 수 변화 `[측정값]`%를 서술한다. 성공 응답 수 변화 전체를 오류 감소만으로 설명하지 않는다
- **② 채택 검증:** 조건을 모두 만족하면 "가게당 동시 작성 `[VUS/SHOP_POOL]`건 수준의 경합에서도 성공 응답 p95 `[측정값]`ms"로 서술한다
- **②→③ (비교군):** "비동기로 바꾸면 p95는 `[②]`→`[③]`ms로 줄지만, 부하 종료 후 잔여 작업 `[측정값]`초, 거절·실패 `[측정값]`건, 최종 불일치 `[측정값]`이 생긴다"처럼 이득과 대가를 함께 적는다. ③의 p95가 낮아도 채택 근거로 쓰지 않는다

불일치 가게 수는 누락된 갱신 수와 다르다. 한 가게에서 100건이 누락되어도 불일치 가게는 1개이고, `SHOP_POOL=3`이면 최대 3개다. 그래서 헤드라인에는 누락된 갱신 수(개수 부족분 합계, 통계 행이 없는 가게의 리뷰 수 포함)를 쓰고, 초과분은 따로 합산해 상쇄를 피한다.

### 한계 및 후속 개선

- 제거한 것은 "리뷰 INSERT의 FK 공유 락에서 같은 행 배타 락으로 승격하는 충돌 경로"다. 다른 트랜잭션과의 락 순서까지 포함해 모든 데드락이 불가능하다고 주장하지 않는다
- 같은 가게의 stats 행 UPDATE는 커밋까지 직렬화되므로, 한 가게에 리뷰가 몰리면 응답 지연이 늘어난다. 허용 한도를 넘는 조건이 확인되면 ③과 복구 경로, 또는 집계 방식 변경을 검토한다
- 원자성의 대가로, 통계 갱신이 실패하면 리뷰 작성도 실패한다. 통계 행 누락은 가게 생성 시 통계 행을 같은 트랜잭션에서 만드는 것으로 예방한다
- 리뷰가 주문과 연결되지 않고 중복 방지 장치가 없어, 클라이언트 재시도 시 리뷰와 통계가 두 번 반영될 수 있다. 주문당 1회 작성 제약과 멱등 키가 후속 과제다
- 부하 조건은 결함 재현을 위해 소수 가게에 집중한 것으로 실제 트래픽 분포가 아니다

### 이전 접근과 이번 검증의 구분

초기 구현(2025.03)은 데드락을 피하려고 리뷰 커밋 후 별도 트랜잭션·비동기로 통계를 갱신했고, 동시 갱신의 덮어쓰기에 대비해 Shop에 낙관적 락과 재시도를 적용했다. 이번에는 데드락과 유실의 원인을 다시 분석해 통계 모델 분리와 원자 UPDATE로 원인을 제거했다. 분리·재시도 없이도 결함이 해결되었으므로, 통계 반영 방식은 요구사항 우선순위로 다시 판단했다(②).

과거 낙관적 락·재시도 단계와 nGrinder의 2.5만→3.8만 수치는 이번 비교에서 재현하지 않으며, 현재 설계의 성과로 합쳐 쓰지 않는다. ①은 "기존 설계를 재구성한 결함 재현 버전"으로 명시한다.

### 느낀 점

- 데드락은 락의 종류와 획득 순서 문제이고, 유실은 읽고-쓰기 사이의 경쟁 문제다. 원인이 다르면 해결과 검증도 따로 해야 한다
- 처음의 트랜잭션 분리는 원인을 피해 가는 우회책이었다. 원인을 제거하자 우회책이 필요 없어졌고, 남은 선택은 성능 수치가 아니라 무엇을 먼저 지켜야 하는지로 판단해야 한다는 것을 배웠다

> 상태: **측정 전 초안.** 결과는 모두 `[측정값: 출처]`로 남긴다. 성능은 3회 중앙값과 범위, 오류·불일치는 모든 회차의 건수를 기록한다. 목표값 0을 실측값으로 쓰지 않는다.

> 원문의 트랜잭션 분리·낙관적 락·Spring Retry는 이전 접근으로 남긴다. 과거 구현과 현재 재구성한 비교 단계를 동일한 개발 이력처럼 서술하지 않는다.

## 1-1. 리뷰 저장의 데드락과 통계 갱신 유실을 통계 모델 분리와 원자 UPDATE로 개선

### 결과 요약

- 리뷰 작성의 성공 기준을 원본 저장으로 정의하고, 파생 통계 갱신 실패가 리뷰 저장까지 롤백시키지 않도록 트랜잭션 경계를 분리
- `shop_review_stats` 분리로 기존 shops 행의 S→X 락 승격 경로를 없애고, 원자 증가 UPDATE로 이전 값을 덮어쓰는 경쟁을 방지
- 통계의 지연 반영은 허용하되 최종 누락은 복구해야 한다는 정책을 구분. 현재 자동 복구 미구현은 남은 한계로 명시
- 같은 동시 사용자 `[VUS]`명, 가게 `[SHOP_POOL]`개 집중 부하 15분에서 데드락 `[측정값: ①]` → `[측정값: ②]`건, 통계 불일치 가게 `[측정값: ①]` → `[측정값: ②]`개, 성공 응답 `[측정값: ① reviews_created]` → `[측정값: ② reviews_created]`건. **측정 후에만 결과로 확정**

### 문제 상황

- 리뷰를 저장한 뒤 가게의 리뷰 개수와 평균 평점을 갱신하는 구조. 통계 컬럼이 `shops` 테이블에 있어 리뷰 INSERT와 가게 UPDATE가 같은 트랜잭션에서 같은 행을 다룸
- 초기 동시 리뷰 작성 테스트에서 데드락으로 요청이 실패했다. 이후 검증에서 저장된 리뷰와 최종 통계가 달라지는 갱신 유실도 확인했다
- 외래 키를 유지한 채 기존 데드락 경로와 동시 갱신의 덮어쓰기를 없애는 것이 목표. 트랜잭션 분리에 따른 통계 미반영은 별도 복구 과제로 구분

### 설계 의도: 서로 다른 책임과 성공·실패 기준

리뷰 INSERT는 사용자가 작성한 원본 데이터를 저장하는 책임이고, Shop의 평점 UPDATE는 그 원본을 바탕으로 리뷰 개수·평점 합계·평균을 관리하는 책임이라고 보았다. 서로 다른 관심사의 결합을 줄이고, **리뷰 작성의 성공 기준을 원본 저장으로 정의**했다. 파생 통계는 지연 반영을 허용하는 방향으로 트랜잭션을 분리해, 통계 갱신 실패가 리뷰 저장까지 롤백시키지 않도록 했다.

| 대상 | 성공·실패 정책 |
|---|---|
| 리뷰 원본 저장 | 원본 저장이 커밋되면 리뷰 작성 성공. 원본 저장 실패는 요청 실패로 처리 |
| 파생 통계 갱신 | 리뷰 저장과 동시에 완료될 필요는 없으며 지연 반영 허용. 실패해도 커밋된 리뷰는 유지하고 통계는 별도로 복구해야 함 |

관심사 분리만 필요하다면 코드·모델을 나누면서 같은 트랜잭션을 사용할 수 있다. 여기서는 **두 작업이 함께 실패할 필요가 없다는 정책**이 트랜잭션 분리의 추가 근거다. 비동기 실행은 통계 갱신 완료를 리뷰 응답이 기다리지 않게 하는 별도의 선택이며, 성능 개선 폭만으로 트랜잭션 분리의 타당성을 판단하지 않는다.

지연 반영을 허용하는 정책이 최종 누락을 허용한다는 뜻은 아니다. **현재 구현은 거절·실패를 기록하지만 자동 재처리나 재집계를 구현하지 않아 불일치가 지속될 수 있다.** 허용 지연의 구체적인 범위와 복구 방식은 후속 보완 사항이며, 복구까지 구현된 최종 정합성 보장으로 표현하지 않는다.

### 원인 분석

**데드락**
- Review INSERT는 외래 키 `shop_id` 검사를 위해 부모 `shops` 행에 공유 락(S)을 획득
- 같은 트랜잭션에서 `shops` 통계를 UPDATE하려면 같은 행의 배타 락(X)이 필요
- 두 트랜잭션이 각자 S락을 든 상태에서 서로 X락을 기다리면 데드락. InnoDB가 한쪽을 롤백해 500 응답

(원문 시퀀스 그림 유지)

**갱신 유실**
- 통계를 "읽고 → 애플리케이션에서 계산 → 쓰기"로 갱신하면, 두 요청이 같은 이전 값을 읽은 뒤 나중 쓰기가 앞선 쓰기를 덮어씀
- 예: 리뷰 10개·합계 30점에 5점과 4점이 동시에 들어오면 12개·39점이어야 하지만, 둘 다 10개·30점을 기준으로 계산하면 11개·35점 또는 11개·34점으로 끝남
- 데드락이 없는 겹침에서도 발생하므로 데드락만 없애면 유실은 남음. "트랜잭션 분리가 새로 만든 문제"가 아니라 "분리 이후 추가 검증에서 확인한 읽고-계산-쓰기 구조의 결함"으로 구분

### 고려한 해결 방법

| 방법 | 장점 | 판단 |
|---|---|---|
| 외래 키 제거 | FK 공유 락 자체가 사라짐 | DB 제약이 없어져 정합성 관리 부담 증가 |
| 부모 shops 행을 먼저 비관적으로 잠금 | 리뷰 INSERT 전에 X락을 확보해 갱신 순서 직렬화 | 같은 가게의 요청이 부모 행에서 대기. 선택한 원자 UPDATE도 stats 행에서는 직렬화되므로 무조건 더 빠르다고 단정하지 않음 |
| 통계 갱신을 별도 트랜잭션으로 분리 | 리뷰 커밋 후 통계를 갱신해 통계 실패가 원본 저장을 롤백시키지 않음. 기존 FK 락 해제 후 UPDATE | 리뷰 원본과 파생 통계의 서로 다른 성공·실패 기준에 따른 선택. 읽고-계산-쓰기 경쟁과 통계 미반영 복구는 별도로 해결해야 함 |
| 통계 행 분리 + 원자 증가 UPDATE | S락(shops)과 X락(stats) 대상이 달라 기존 승격 경로 제거. 이전 값을 읽지 않아 덮어쓰기 방지 | 현재 구현. ②로 모델·갱신 방식 변경의 효과를 검증하고, ③에서 실패 처리 정책과 비동기의 성능·정합성 대가를 확인 |

### 선택한 해결 방법

**1. 데이터 모델 분리**

가게 기본 정보와 리뷰에서 계산되는 통계를 별도 모델로 관리한다. 리뷰 INSERT의 FK 검사는 `shops` 행에, 통계 UPDATE는 `shop_review_stats` 행에 락을 잡으므로 기존의 같은 shops 행에서 S→X 승격을 기다리는 경로가 사라진다. 같은 가게의 stats 행 UPDATE 간 락 대기는 남는다.

| 컬럼 | 역할 |
|---|---|
| shop_id | 가게 식별자 (PK, shops 1:1) |
| review_count | 누적 리뷰 개수 |
| rating_sum | 누적 평점 합계 |
| average_rating | 평균 평점. 매 갱신 시 `(rating_sum + r) / (review_count + 1)`로 계산해 저장 |

**2. 원자 증가 UPDATE**

```sql
UPDATE shop_review_stats
SET average_rating = (rating_sum + :r) / (review_count + 1),
    rating_sum     = rating_sum + :r,
    review_count   = review_count + 1
WHERE shop_id = :shopId
```

- 이전 값을 애플리케이션에서 읽지 않고 DB가 현재 값 기준으로 증가시키므로 실행 순서와 무관하게 결과가 같다. 동시 갱신의 덮어쓰기가 없다
- MySQL은 단일 테이블 UPDATE의 SET을 왼쪽부터 평가하고 뒤의 대입은 갱신된 값을 본다. 평균을 맨 앞에 두어야 원래 합계·개수로 계산된다 (뒤에 두면 증가분이 두 번 반영되어 5점 뒤 1점이 평균 3.00이 아니라 2.33이 됨. MySQL 8.0.36에서 확인)
- 이 방식은 stats 행의 행 락을 사용한다. "락 없이 처리"가 아니라 "락 승격 충돌 경로와 읽고-쓰기 경쟁을 없앤" 것이다

**3. 성공·실패 정책에 따른 트랜잭션 분리와 비동기 실행**

`omp.review.stats.mode` 설정으로 두 방식을 같은 코드에서 전환한다. ②도 리뷰 저장과 통계 갱신의 코드·모델 책임은 분리되어 있지만, 통계 갱신 실패 시 리뷰까지 롤백된다. ③은 리뷰 작성의 성공을 원본 저장으로 판단하고 통계 실패를 후속 처리로 남기는 정책을 구현한다. 동시에 워커 실행으로 통계 갱신 완료를 응답 경로에서 기다리지 않게 한다.

| 모드 | 동작 | 장점 | 대가 |
|---|---|---|---|
| sync (②) | 리뷰 INSERT와 같은 트랜잭션에서 UPDATE | 리뷰와 통계가 원자적으로 일치 | 통계 갱신 실패 시 리뷰도 롤백. 핫 가게 stats 행 락 대기가 응답 시간에 포함 |
| async (③) | 리뷰 커밋 후 `@TransactionalEventListener(AFTER_COMMIT)` → 전용 스레드 풀에서 UPDATE | 통계 실패가 커밋된 리뷰를 롤백시키지 않고, 응답이 통계 완료를 기다리지 않음 | 리뷰 저장과 통계 반영 사이의 정합성 창. 풀 포화 거절·실패 시 재처리가 없어 불일치가 지속 |

풀 포화 시 요청 스레드에서 몰래 실행하는 CallerRunsPolicy는 쓰지 않는다. 거절은 `omp.review.stats.rejected`, 실행 실패는 `omp.review.stats.failed` 카운터로 드러내고 리뷰 ID를 로그에 남긴다.

③도 요청과 통계 워커가 같은 HikariCP·DB를 사용하므로 자원 경쟁의 영향까지 격리되지는 않는다. 실패 시 원본이 유지되는지와 정상 부하에서 최종 집계가 일치하는지를 따로 확인하고, 응답 지연·반영 지연·복구 비용을 평가한다.

### 검증 방법

아래 절차로 세 설계를 비교할 예정이다. 재현 브랜치 ①은 현재 코드(main)에서 통계 필드 3개와 리뷰 저장 메서드를 옛 설계로 재구성한 것으로, 애플리케이션의 스레드 풀·검증·예외 처리는 동일하다.

**부하 전 원인 재현:** 두 트랜잭션의 실행 순서를 제어해 (a) 모두 FK 검사 S락을 보유한 뒤 X락을 요구하는 데드락, (b) 같은 이전 통계를 읽은 뒤 순차 커밋하며 덮어쓰는 갱신 유실을 각각 확인한다. ②에서는 같은 리뷰 입력에 대한 최종 정합성을 확인한다. 현재 순차 통계 테스트와 주석 처리된 동시성 테스트만으로 재현 완료를 주장하지 않는다. 재현 로그·테스트 결과는 측정 전에 확보할 항목이다.

**실패 처리 정책 검증:** 통계 행 누락을 강제해 ②는 리뷰까지 롤백하고, ③은 리뷰를 유지한 채 통계 실패를 기록하는지 확인한다. 관련 테스트는 `ReviewStatsMissingRowSyncModeTest`·`ReviewStatsMissingRowAsyncModeTest`이며, 실패 경계를 검증하는 사례다. 이 실패 주입 결과는 정상 부하 회차와 분리하고, 통계 자동 복구까지 검증한 것으로 쓰지 않는다.

| 항목 | 값 |
|---|---|
| 장비 배치 | 데스크탑 k6 → 유선 LAN → 노트북 Spring Boot + MySQL. 두 장비 CPU·RAM·OS·전원 설정 기록 |
| 도구 | k6 `[버전]`, closed model (`constant-vus`), `[VUS]` VU, 15분 × 3회. 성능은 중앙값·범위, 오류·불일치는 회차별 건수 |
| 파일럿 | `VUS=50`, `SHOP_POOL=3`, 1분에서 시작. 원인·부하기 여유 확인 후 본측정 조건을 세 설계에 동일하게 고정 |
| 경합 조건 | 리뷰 대상 가게 `[SHOP_POOL]`개에 집중, 평점 1~5. 결함 재현용 조건이며 실제 트래픽 분포나 서비스 전체 용량을 의미하지 않음 |
| 서버 | JDK 21 `-Xms2g -Xmx2g`, MySQL `[실제 버전]` 동거, HikariCP 20. 리뷰 격리 수준·DB 주요 설정 기록 |
| ③ 통계 풀 | core 10 / max 20 / queue 2000, AbortPolicy. 첫 비교에서는 튜닝하지 않고 고정 |
| 회차 준비 | 서버 재시작 → 워밍업 → 잔여 작업 종료 확인 → 리뷰·통계 초기화 → 카운터 시작값 기록 |
| 데드락 판정 | `information_schema.INNODB_METRICS.lock_deadlocks` 증가분과 데드락 로그. 5xx를 전부 데드락으로 간주하지 않음 |
| 정합성 판정 | 작업 종료 후 리뷰 원본 집계와 count·sum 일치, 통계 행 누락 0, 평균 = ROUND(sum/count, 2). ①은 shops, ②·③은 stats와 비교 |
| 응답 지연 | 전체 응답과 성공 응답의 p95·p99를 구분. 현재 k6 요약은 전체 응답이므로 성공 응답은 `--out csv=...` 결과의 2xx 표본으로 별도 집계 |

closed model에서는 응답이 빨라지면 유입률도 바뀐다. 결과는 **같은 VU 수에서의 비교**로 한정한다. ②·③을 "같은 유입률에서" 비교하려면 둘 다 감당 가능한 고정 RATE의 open model 측정을 추가하고 `dropped_iterations=0`을 확인한다.

### 결과

- **①→②:** 모델 분리와 원자 갱신의 결합 효과. 데드락·정합성의 회차별 결과와 성공 응답 수 변화 `[측정값]`%를 함께 서술한다. 성공 응답 수 변화 전체를 오류 감소만으로 설명하지 않는다
- **②→③:** 같은 VU 수에서 응답 지연·성공 응답 수·통계 거절·실패·최종 불일치가 어떻게 달라졌는지 서술한다. 불일치가 있으면 "최종 정합성 유지"라고 결론 내리지 않는다
- **설계 판단:** 트랜잭션 분리의 근거는 통계 갱신 실패 때문에 리뷰 원본 저장을 취소하지 않는 정책이다. ②는 기존 데드락·갱신 유실이 같은 트랜잭션에서도 해결되는지 확인하는 비교 기준이며, 응답 시간이 비슷하다는 이유만으로 ③과 같은 정책을 충족한다고 해석하지 않는다. 성능·정합성의 실측 결과는 `[측정 후 기입]`으로 남긴다
- **검증 범위와 남은 과제:** 정상 부하에서는 데드락·최종 불일치·③의 거절/실패를 확인하고, 실패 주입에서는 원본 유지와 실패 기록을 확인한다. 현재 자동 복구가 없으므로 정상 회차의 불일치 0이 장애 후 복구를 보장하지는 않는다. 허용 반영 지연의 수치화와 복구 구현·검증을 후속 과제로 남긴다

불일치 가게 수와 누락된 갱신 수는 다르다. 한 가게에서 100건이 누락되어도 불일치 가게는 1개다. 부족분은 가게별 `max(원본 리뷰 수 - 통계 review_count, 0)`을 합산하고, 통계 행이 없는 가게의 리뷰 수도 포함한다. 초과분은 반대 방향의 차이를 별도로 합산해 상쇄를 피한다. 거절·실패 카운터와는 원인을 대조하며, 불일치 행 수와 같다고 가정하지 않는다.

### 한계 및 후속 개선

- 제거한 것은 "리뷰 INSERT의 FK 공유 락에서 같은 행 배타 락으로 승격하는 충돌 경로"다. 다른 트랜잭션과의 락 순서까지 포함해 모든 데드락이 불가능하다고 주장하지 않는다
- 통계 모델을 분리한 ②에서도 기존 데드락 경로를 제거할 수 있다. 현재 트랜잭션 분리의 주된 근거는 데드락 회피의 필수 조건이 아니라 원본과 통계의 서로 다른 성공·실패 정책이다
- 원자 UPDATE는 동시 갱신의 덮어쓰기를 막지만 이벤트 누락·중복 적용을 막지는 않는다. ③에서 거절·실패한 갱신은 재처리가 없어 **불일치가 지속**된다. 운영 확장 시 Transactional Outbox 또는 리뷰 원본 기준 재집계가 필요
- 통계 행이 없는 가게에 리뷰가 들어오면 UPDATE 영향 행이 0이다. ②는 리뷰까지 롤백, ③은 실패 카운터로 기록한다
- ③의 2xx는 리뷰 저장 성공이며 통계 반영 완료까지 뜻하지 않는다. `queued=0·active=0`도 작업 실행 종료 조건일 뿐 정합성 성공 조건은 아니다. 최종 SQL 검증과 거절·실패 확인을 함께 수행한다
- 부하 종료 후 잔여 작업이 끝나는 시간은 리뷰별 통계 반영 지연이 아니다. 반영 지연의 p95·최댓값이나 허용 지연 충족을 주장하려면 리뷰 커밋부터 통계 갱신 커밋까지 별도 계측이 필요하다
- 부하 조건은 결함 재현을 위해 소수 가게에 집중한 것으로 실제 트래픽 분포가 아니다

### 이전 접근과 이번 검증의 구분

초기에는 데드락 회피와 리뷰 원본 저장·통계 갱신의 관심사 분리를 위해, 리뷰 커밋 후 별도 트랜잭션에서 통계를 갱신했다. 이후 갱신 유실을 확인하고 Shop에 낙관적 락과 재시도를 적용한 이력이 있다. 낙관적 락은 덮어쓰기를 감지하지만 경합 시 재시도 비용이 발생하고, 재시도가 소진되면 통계 미반영이 남을 수 있다. 현재 구현은 별도 통계 모델의 원자 UPDATE다. 이번 검증에서는 모델·갱신 방식 변경의 효과와, 리뷰 원본의 성공을 통계 갱신 실패와 분리하는 정책 및 그 성능·정합성 대가를 구분해 확인한다.

과거 낙관적 락·재시도 단계와 nGrinder의 2.5만→3.8만 수치는 이번 비교에서 재현하지 않는다. 현재 설계의 성과로 합쳐 쓰지 않으며, 재시도 소진을 이번에 재현한 것처럼 표현하지 않는다.

### 느낀 점

- 데드락은 락의 종류와 획득 순서 문제이고, 유실은 읽고-쓰기 사이의 경쟁 문제다. 서로 다른 원인에 맞춰 해결하고 검증해야 한다
- 관심사 분리는 코드·모델의 책임을 나누는 판단이고, 트랜잭션 분리는 함께 성공·실패해야 하는 범위를 정하는 판단이다. 리뷰 원본 저장을 성공 기준으로 삼고 파생 통계는 별도 복구 대상으로 두는 정책을 트랜잭션 경계에 반영했다
- 트랜잭션 분리의 정책적 근거와 비동기의 성능 효과는 구분해야 한다. 지연 반영을 허용하더라도 최종 누락은 복구해야 하며, 현재 실패 관측에서 자동 복구까지 확장하는 일이 남아 있다

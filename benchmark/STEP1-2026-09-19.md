## 2. 실측으로 확정된 사실 (포폴·면접 답변에 직접 쓸 것)

### 2-1. MySQL 단일 테이블 UPDATE는 SET을 왼쪽부터 평가하고 뒤의 대입은 갱신된 값을 본다

MySQL 8.0.36, 임시 테이블로 직접 실행:

| SET 순서 | 5점 뒤 1점 입력 후 count / sum / avg |
|---|---|
| 합계·개수 먼저, 평균 마지막 (옛 코드) | 2 / 6.00 / **2.33** |
| 평균 먼저 (수정) | 2 / 6.00 / **3.00** |

H2로는 재현되지 않는다. "예외 없음 = 성공"으로 판정하면 놓친다. 커밋된 값을 별도 커넥션으로 읽어 판정해야 한다.

### 2-2. Spring의 AFTER_COMMIT 리스너 예외는 호출자에게 전파되지 않는다

`@TransactionalEventListener`(AFTER_COMMIT)는 `afterCompletion` 단계에서 실행되고, 그 안의 예외는
`TransactionSynchronizationUtils`가 `"TransactionSynchronization.afterCompletion threw exception"`으로 **로그만 남긴다**.
`AsyncOrderRejectionTest` 1차 실행에서 리스너가 거절 예외를 던졌는데도 컨트롤러는 **202**를 반환했다.

따라서
- REVIEW 2-5의 서술("동기 AFTER_COMMIT 예외는 500"은 틀림)이 맞다. 실제는 "리뷰 저장 + 200, 통계는 조용히 누락".
- 비동기 통계 갱신의 근거는 "동기면 500이 난다"가 아니라 **"격리 + 실패 관측(거절·실패 카운터)"**이다.

### 2-3. 그래서 바뀐 설계: 주문 제출은 이벤트가 아닌 직접 호출 + 명시적 거절

포화 거절을 503으로 응답하려면 예외가 요청 스레드에 도달해야 한다. 현재 AFTER_COMMIT 리스너에서 예외를 던지는 방식으로는 불가능하므로
`OrderService.asyncOrder` → `AsyncOrderHandler.submit` 직접 호출로 변경. 제출은 `@Transactional` 서비스 메서드 안에서 일어난다
(REVIEW 2-2의 B안처럼 트랜잭션 종료 후가 아니다). 정확한 이름은 "직접 제출 + 명시적 거절".

이게 가능한 이유: 접수 트랜잭션은 **검증 SELECT만** 수행한다. "커밋 후"를 기다려 보호할 데이터가 없다.
AFTER_COMMIT 이벤트는 "커밋된 데이터에 대한 후속 작업"인 리뷰 통계에만 남는다.

포폴 1-2에서 "`@TransactionalEventListener`로 접수 커밋 후 INSERT 위임"이라고 쓰고 있었다면 이 문장은 지운다.

### 2-4. 통계 테이블 분리 후에는 같은 트랜잭션이어도 데드락이 없다

데드락 원인은 같은 `shops` 행에 S락(FK 검사) 뒤 X락(UPDATE)을 요구한 것. 통계를 `shop_review_stats`로 빼면
INSERT의 S락은 `shops`, UPDATE의 X락은 `stats` 행이라 승격 경로가 사라진다. `ReviewStatsSyncModeTest`는 **순차** 요청으로 통계값만 검증한다. 동시 실행 재현은 2단계의 결정적 테스트가 근거가 되며,
그때까지 표현은 "기존 FK 공유 락→배타 락 승격 충돌 경로 제거"로 한정한다. 다른 락 순서까지 포함한 "모든 데드락 불가"는 주장하지 않는다.

→ 비동기 분리의 근거는 "데드락 회피"가 아니라 **"핫 가게 stats 행 락 대기를 리뷰 응답에서 격리"**. 지연 트레이드오프이므로
2단계 이후 `omp.review.stats.mode` sync/async를 k6 02로 비교 측정해 결정한다. 차이가 미미하면 sync를 택하고 "복잡도를 걷어냈다"고 쓴다.

> **2026-09-24 확정 (위 결정 방식 대체):** 응답 지연 비교로 고르지 않고 요구사항 우선순위(원본 저장 > 통계의 최종 정합성 > 통계 신선도 > 작성 응답 지연)로 판단해 **sync(②)를 채택**했다. 기본 모드도 sync로 바꿨다. 측정은 ②가 허용 한도(성공 p95 ≤ 500ms)를 만족하는지 검증하고, async(③)는 비교군으로 이득과 대가를 기록한다. 근거와 검증 기준은 `benchmark/README.md` 2절.

| "같은 트랜잭션이어도 데드락 없음" (sync 테스트 근거) | 근거는 락 분석. sync 테스트는 순차 요청. 동시 재현은 2단계 |
| "격리 + 실패 관측이 비동기 근거" | 격리(요청 지연에서 락 대기 분리)가 고유 근거. 관측은 동기에서도 가능. (09-24: 격리는 4순위 요구라 채택 근거가 되지 못함 → sync 채택, 2-4 참고) |
| `orders_accepted == COUNT(orders)`로 유실·중복 판정 | "총건수 일치"로 한정. 요청별 대조는 3단계 |
| "로컬 값은 코드에 두지 않는다" | 환경변수로 덮어쓸 수 있게 했다. 기본값 1234는 설정에 남아 있다 |
| 통계 "반영 지연" | 거절·실패는 재처리가 없으므로 **"불일치 지속"**. 지연은 큐 대기 후 성공한 경우만 |
| 기간 "2025.02~03" | 초기 개발 2025.02~03 / 비동기 확장 2025.07~08 / 재검증·개선 2026.08~09 로 분리 (09-26 정정: 커밋 이력상 초기 개발은 2025.01~05 — 첫 커밋 2025-01-11, 기능 커밋 2025-05-26까지) |

### 8-4. 리뷰 비교 단계 (이미 마련된 구조, 계획에 명시)

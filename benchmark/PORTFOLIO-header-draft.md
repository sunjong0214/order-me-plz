## Project 1. [Order-Me-Plz](https://github.com/sunjong0214/order-me-plz)

음식 주문·배달 도메인의 백엔드 API를 설계·구현하고, 1년 뒤 동시성 결함과 비동기 설계를 원인부터 다시 검증해 재측정한 개인 프로젝트다.

### 핵심 성과

- 리뷰 저장의 데드락(외래 키 공유 락 → 배타 락 승격)과 통계 갱신 유실을 원인별로 나눠 실행 순서를 통제한 테스트로 각각 재현하고, 통계 모델 분리 + 원자 UPDATE로 두 원인을 제거해 비동기 우회 없이 같은 트랜잭션에서 통계 정합성 확보
  - 비동기로 우회하기 전의 동기 설계(옛 코드가 git에 없어 재현 브랜치로 재구성)와 비교해, 가상 사용자 50명이 가게 3곳에 몰리는 극단 경합(15분)에서 데드락 약 103만 건 → 0, 통계 누락 약 15만 건 → 0(개선 후 성공 응답 p95 35.5–37.1ms, 허용 500ms)
  - 가게 1,000곳에 고르게 나눈 분산 부하(초당 20건)에서는 개선 전 설계도 데드락·통계 누락 0건. 평소 지표로는 보이지 않고 특정 가게에 작성이 몰릴 때 터지는 결함
- 선착순 한정 수량 이벤트(재고 10만 개, 시도 약 23만 건, 최고 초당 3,000건은 실험용 가정)에서 재고 판정 3방식을 비교해 메모리 번호표 + DB 안전망(유니크·외래 키)을 채택. 10만 건 확정이 DB 행 하나 약 90초 → 38–41초(10만 번째 시도가 도착하는 35.8초에 근접), 매진은 DB를 거치지 않고 접수에서 즉시 응답(p95 3.8ms 이하), 31회 측정(무효 7회 포함) 모두 초과 판매 0
  - 접수 방식은 동기(상한 없음)와 비동기의 일반 주문 포화 처리량이 같아 성능이 아닌 우선순위로 판단. 동시 처리 상한을 넘으면 즉시 429를 주는 빠른 거절 동기는 재고가 남은 동안 시도를 상한 130에서 약 0.9–1.5만 건, 190으로 올려도 약 0.6–1.3만 건 거절했고, 상한 없는 동기는 Tomcat 스레드 200개를 모두 점유. 번호표와 함께 쓸 때 매진 전 거절 0이고 요청 스레드를 묶지 않는 비동기를 선택
  - 대가와 한계: 주문 하나의 확정은 상한 190 동기가 더 빠름(요청 → 확정 평균 0.08초 vs 0.72초), 비동기 접수 p95 요구(200ms)는 유효 3회 중 1회만 충족, 메모리 큐라 재시작 시 저장 전의 접수 주문 유실(영속 큐가 전제). "매진 전 거절 0"을 확정 속도·접수 p95 요구보다 앞에 둔 우선순위는 첫 측정 결과를 본 뒤 정함. 상한 190 추가 측정은 해석 기준을 먼저 정한 뒤 실시
- 가게가 문을 닫아도 목록에 최대 24시간 "영업 중"으로 보이던 가게 목록 캐시(Caffeine)를 재설계. 영업 상태·가게 정보·새 가게는 변경 시 커밋 후 무효화하고, 평점·리뷰 수는 허용 지연(수 초~수 분) 안에서 서비스 규모 재조회 부하(키 수 ÷ 만료 시간)와 견줘 만료 시간을 24시간 → 5분으로 재산정. 여러 키의 동시 만료(Jitter)와 인기 키 하나의 동시 로딩(sync)을 나눠 대응(같은 키 동시 미스 10건의 목록 쿼리 10회 → 1회, 기능 테스트)

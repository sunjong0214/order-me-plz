## Project 1. [Order-Me-Plz](https://github.com/sunjong0214/order-me-plz)

음식 주문·배달 도메인의 백엔드 API를 설계·구현하고, 1년 뒤 동시성 결함과 비동기 설계를 원인부터 다시 검증해 재측정한 개인 프로젝트입니다.

| 구분 | 내용 |
|---|---|
| 기간 | 2025.01 ~ 2025.08 |
| 재검증·개선 | 2026.08 ~ 2026.09 (결함 수정, 리뷰 통계 재설계, 주문 접수 재설계, k6 재측정) |
| 참여 인력 | 1인 |
| 기술 | Java 21, Spring Boot 3.4, Spring Data JPA, QueryDSL, MySQL 8.0, SSE, Caffeine |
| 측정 | k6 (open·closed model), Micrometer·Prometheus 히스토그램, InnoDB 락 지표 |
| 테스트 환경 | 서버 노트북(물리 4코어·RAM 16GB, Spring Boot + MySQL) ↔ 유선 LAN ↔ 부하기 데스크탑(k6). 같은 조건 3회, 중앙값·범위 |

### 핵심 성과

- 리뷰 저장의 데드락과 통계 갱신 유실을 원인별로 분석하고 통계 모델 분리 + 원자 UPDATE로 제거. 가게 `[SHOP_POOL]`개 집중 부하 15분에서 데드락 `[①]` → `[②]`건, 누락된 통계 갱신 `[①]` → `[②]`건
- 주문 접수와 저장을 분리하고 큐를 "허용 저장 지연 × 측정한 처리량"으로 산정해, 처리량 2배 스파이크에서 접수 p95 `[S]`ms·저장 완료 p99 `[S]`초를 지키며 초과분 `[S]`%만 즉시 거절 (같은 조건의 동기 방식: 타임아웃 `[S]`건)
- 가게 목록 캐시의 근거 없던 만료 시간(24시간)을 평점 허용 지연과 서비스 규모 재조회 부하로 계산해 5분으로 재산정하고, 즉시 반영이 필요한 값은 변경 시 무효화, 여러 키의 동시 만료(Jitter)와 인기 키 하나의 동시 로딩(sync)을 나눠 대응 (동시 미스 10건의 쿼리 10회 → 1회, 기능 테스트)

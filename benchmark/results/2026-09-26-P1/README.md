# 파일럿 P1 — 커넥션 총량 P (2026-09-26)

동기 주문(`MODE=sync`, `POST /api/v1/order`)을 포화시켜 HikariCP 커넥션 수 P별 최대 처리량을 쟀다. 선정 규칙은 [README 2절 "풀 크기 산정"](../../README.md): **최대 처리량의 95%에 도달하는 가장 작은 P**.

**결과: P = 10.**

## 유효 회차 (이 폴더 최상위)

모든 유효 회차는 같은 조건에서 돌았다.
- 직전 부하 종료 후 15분 휴식.
- 충전기 연결 확인(기동 전·측정 전·측정 후, `BatteryStatus` = 2).
- 서버 재시작 → 워밍업 1분(버림) → 잔여 작업 0 확인 → `reset-round.sql`(결과 0 0 0 0 확인) → 3분 측정 → 서버 종료.
- 측정 전 문턱: 노트북 CPU 10초 평균 15% 미만, 데스크톱 5초 평균 30% 미만.
- 부하 발생기 판정: 측정 중 데스크톱 CPU 평균 80% 미만, 80% 이상 2표본 연속 없음.
- 노트북 클럭·프로세스별 CPU를 5초마다 기록(`laptop-cpu-*.csv`).

- 순서는 5 → 15 → 10 → 20 (크기순을 피해 발열 누적과 P 효과가 섞이지 않게). 이후 경계였던 10·15를 한 번씩 더 쟀다.
- 처리량 = `orders_accepted` ÷ 180초. 노트북 CPU·클럭·프로세스 몫은 `laptop-cpu-*.csv`의 측정 구간 평균. 측정 중 그 밖의 프로세스는 약 6%(대부분 System)로 회차 간 같았다.
- 클럭은 `% Processor Performance`(기본 2.8GHz 대비). 부하 시작 직후 120%대 중반 → 30~40초 뒤 113% 안팎 → 3분 동안 109%까지 서서히 내려간다(p15-cool: 122 → 112.6 → 109.3). 측정 구간 평균은 네 회차 모두 112%, P=5는 CPU가 덜 차서 116%. 15분 본측정에서는 더 내려갈 수 있어 같은 방식으로 기록한다.

### 판정

| P | 평균 처리량/s | 최대 평균(2,363.6) 대비 |
|---|---|---|
| 5 | 1,999.2 | 84.6% |
| **10** | **2,314.4** | **97.9%** ← 95% 이상인 가장 작은 P |
| 15 | 2,363.6 | 100% |
| 20 | 2,360.8 | 99.9% |

- P=10부터 노트북 CPU가 96~100%로 포화돼 처리량이 평탄하다. 10·15·20의 평균 차이(2% 이내)는 같은 P 반복 편차(P=10 4.2%, P=15 2.9%)보다 작다.
- P=5는 CPU가 76%로 여유가 있는데 요청 55개가 커넥션을 기다렸다. 이 구간은 커넥션 수가 병목이다.
- CPU의 약 60%를 MySQL이 쓴다. 동기 주문의 한계는 커넥션 수가 아니라 앱과 MySQL이 나눠 쓰는 노트북 CPU다.
- 첫 측정만으로는 P=10이 94.5%로 경계여서 10·15를 반복했고, 평균으로 규칙을 적용했다(반복 전에 정한 방법).

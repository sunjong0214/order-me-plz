> **정정 (2026-09-30):** 이 측정의 동기 회차(closed 가상 사용자 200명)는 서버를 다 채우지 못했다. 측정 중 Tomcat 바쁜 스레드가 200개 중 평균 74–86개였다. 가상 사용자 400명으로 다시 재니 동기 3,283–3,320건/s로 비동기(3,157–3,388건/s)와 같았고, 주문당 redo fsync도 0.37–0.42회로 묶였다(`2026-09-30-CAP2`). 그래서 아래 1절의 "비동기가 동기보다 약 19% 많이 저장한다"와 2절의 "동기는 커밋이 덜 묶인다"는 동기를 포화시키지 못해 생긴 결과로 정정한다. 비동기 회차의 값과 3절(워밍업 붕괴)·4절(부하기 간섭)은 그대로 유효하다.

## 2. 차이는 MySQL 쪽에서 난다

- 앱(java)의 주문당 CPU는 모든 회차에서 12.9~13.6으로 같다. 차이는 MySQL의 주문당 CPU다: 비동기 정상 15.3~15.6, 동기 21.5~22.4 (+40~46%)
- 같은 방향으로 주문당 redo fsync가 비동기 정상 0.38~0.41회, 동기 1.07~1.16회다. 비동기는 저장 스레드 20개가 쉬지 않고 커밋해 여러 커밋이 한 번의 디스크 기록에 묶이고(그룹 커밋), 동기는 덜 묶인다. 참고로 용량의 약 60%인 초당 2,000건에서는 2.1회였다 (`2026-09-29-ISO`)
- 동기에서 덜 묶이는 이유는 확인하지 못했다. 동기 폴링 표본은 커넥션 사용 0~20개, 대기 스레드 0~149개로 크게 흔들렸고(평균 16.7·13.3), 비동기는 표본 거의 전부가 20개였다. 요청 스레드 200개가 CPU 8스레드를 나눠 쓰는 동안 반납된 커넥션을 다음 스레드가 이어받기까지 틈이 생기는 것으로 추정한다. 표본 평균은 회차 사이 정량 비교에 쓸 만큼 안정적이지 않다 (2회차 16.7 → 3회차 13.3인데 처리량 차이는 2%)

## 3. 4회차: 워밍업에서 시작된 붕괴

- 막 띄운 서버가 워밍업에서 초당 4,000건을 바로 받으며 응답이 늦어졌고(워밍업 p95 4.8초, 연결 실패 3,499건), k6가 VU를 4,000명까지 늘리며 새 연결을 계속 열었다. 측정에서도 회복하지 못했다: 서버 연결 최대 6,824개(1회차 1,385), TCP 재전송 초당 1,881건, 연결 실패 13,162건, 성공 응답 p95 2.5초
- **무너진 비동기는 동기와 같아졌다.** W 2,684 (동기 평균 2,680), 주문당 redo fsync 1.05 (동기 1.07~1.16), MySQL 주문당 CPU 21.7 (동기 21.5~22.4). 비동기의 이득은 커밋 묶음에서 나오고, 서버가 연결 폭주에 휘말리면 그 이득이 사라진다
- 같은 부하로 워밍업한 1회차도 워밍업 중 VU가 2,618명까지 늘었다가 회복했다. 워밍업을 초당 2,000건으로 낮춘 5·6회차는 워밍업 VU가 723·363명에 그쳤고 둘 다 무너지지 않았다 (2회라 원인으로 확정하지는 않는다). P2 8절의 "나쁜 회차는 모두 워밍업 연결 실패가 있었다"와 같은 모양이다
- 그래서 선착순 측정의 워밍업도 용량보다 낮은 부하로 한다

## 4. 5·6회차: 부하기 간섭

- 5회차는 측정 중 데스크톱에서 다른 프로그램(브라우저·영상 재생)이 CPU를 약 30% 써서 데스크톱 CPU 평균 67%·최대 89%, k6 연결 실패 97건으로 무효다. 서버 쪽 값(W 3,272, redo fsync 0.41, MySQL 주문당 CPU 15.5)은 1회차와 같다
- 6회차도 데스크톱 CPU 평균이 49%로 1~4회차(21~27%)보다 높았지만 판정 기준 안이다. 지연 중앙값·p90이 1회차보다 높은 것(28·81 vs 17·51ms)은 이 영향일 수 있다

## 5. 지연 값에 대해

- 모든 회차에서 p90에서 p95로 넘어가며 약 3배 뛴다 (예: 동기 101 → 311ms). 과부하에서 생기는 TCP 재전송 대기(약 0.3초)로 추정한다. 노트북 재전송이 초당 88~163건으로 요청의 약 3~5%다. Windows 클라이언트에서는 최소 재전송 시간 설정이 조회되지 않아 확인하지 못했다
- 포화 부하라 지연은 참고용이다. 포트폴리오의 지연 수치는 선착순 측정에서 가져온다

## 6. 선착순 측정과의 관계

- 선착순 최고 시도 유입 초당 3,000건(설계 1절)은 동기 용량(2,680)보다 높고 비동기 용량(3,202)보다 낮다
- 할인 주문은 참여 INSERT(메모리 방식), 재고 조회·차감(DB 방식)이 더해져 두 방식 모두 용량이 이보다 낮아진다

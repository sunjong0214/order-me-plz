# 파일럿 P2 — 비동기 방식과 워커 k (2026-09-26~27)

비동기 주문(`POST /api/v1/order/async`)의 저장 처리량 W를 정하는 파일럿. 조건은 P1과 같다.
- 회차마다 직전 부하 종료 후 15분 휴식, 충전기 확인, 노트북 클럭·프로세스별 CPU 기록.
- 서버 재시작 → 워밍업 1분 → 큐 소진 → reset → 3분 측정 → 큐 소진 → DB 주문 수·MySQL 명령 수 확인.
- 판정: k6 연결 실패 0건, 측정 중 데스크톱 CPU 평균 80% 미만(80% 이상 2표본 연속 금지), 정합성 대조(503 수 = 서버 거절 카운터, DB 주문 수 = 접수 − 저장 실패).

**결론: `single` 채택, P = 20, k = 20, W = 약 2,940건/s(노트북 유입 한계에 닿은 값), 큐 Q = 70,000.**

- **결함:** 접수가 트랜잭션(커넥션 → 검증 SELECT)을 마친 뒤에야 큐 포화를 알았고, 거절마다 WARN 로그(회차당 32만~38만 줄)를 남겼다. 과부하에서 거절 비용이 받은 주문까지 느리게 했다.
- **수정 (6cb1e25):** 트랜잭션 전 대기 자리 예약(`AsyncOrderAdmission`, 자리 수 = 큐 용량, 워커가 작업을 시작할 때 반납), 건별 로그 제거. 트랜잭션 구성 전환(`omp.order.async.transaction=split|single`) 추가.
- **부하 발생기 설정:** Tomcat은 503마다 연결을 닫는다. 거절이 많으면 k6가 새 연결을 계속 열어 데스크톱 포트가 고갈된다. 동적 포트 10000~65534(55,535개), TcpTimedWaitDelay 30초로 늘린 뒤 이후 회차는 k6 연결 실패 0건을 판정에 넣었다.

## 5. 선정

규칙은 P1과 같다: 최대 평균 W의 95% 이상인 가장 작은 설정, 202 p95 ≤ 200ms.

| 설정 | 유효 회차 W/s | 평균 | 최대 평균 대비 |
|---|---|---|---|
| **P=20, k=20** | 2,939 · 2,947 | **2,943** | **100%** |
| P=15, k=15 | 2,760 · 2,728 (1회 붕괴) | 2,744 | 93.2% |
| P=10, k=10 | 2,187 · 2,210 | 2,199 | 74.7% |

- 95% 기준선 2,796건을 넘는 가장 작은 설정은 **P=20·k=20**이다. 두 회차 모두 안정적이었고 거절이 적어 유입 한계 근처에서도 연결 재수립이 적다.
- **사전 규칙과 다른 선택이다.** P2 전에 적은 대비 규칙("P=10에서 어떤 k도 W 정체 + 202 p95 ≤ 200ms를 만족하지 못하면 P=15")을 글자대로 적용하면 P=10에서 k=8 → 10이 정체(2,173 → 2,187)하므로 P=10·k=8이 된다. 그 규칙은 "P를 10 넘게 늘려도 처리량이 늘지 않는다"는 동기(P1) 결과를 전제로 했는데, 비동기 single에서는 k를 20까지 늘리면 +35%로 전제가 틀렸다. 그래서 P1과 같은 95% 규칙을 격자 전체에 적용했다.
- W = 2,943건/s는 유입 한계(약 3,000건/s)에 닿은 값이라 실제 저장 용량은 이보다 높을 수 있다.
- 큐 Q = W × 30초 × 0.8 = 70,632 → **70,000**(최대 대기 ≈ 70,000 ÷ 2,943 ≈ 24초). 리뷰 통계 워커 = P/2 = 10.
- 동기 비교군도 같은 P=20으로 돈다(고정 설정). P1에서 동기 P=20은 2,361건/s.

## 6. 유입 한계 재확인 (채택 설정 single P=20·k=20, 2026-09-27 22~23시)

3,600/s 붕괴(11회차, P=15·k=15)가 우연이었는지 보려고 채택 설정으로 부하만 바꿔 쟀다. 순서는 3,300 → 4,000 → 3,000 → 3,600(부하 증가와 발열 누적이 겹치지 않게).

- **안정 구간은 3,000/s까지.** 그 위로는 부하가 늘수록 저장량이 줄고(2,940 → 2,804 → 2,751) 응답이 느려지다가 4,000/s에서 무너졌다. 같은 3,600/s에서 P=15·k=15는 무너지고 P=20·k=20은 저하에 그쳤다.
- **원인 추정(미확인): 503마다 끊기는 연결.** 4,000/s 붕괴 때 노트북 CPU 90%, GC 멈춤 최대 328ms로 CPU·GC만으로는 설명되지 않는다. Tomcat은 503 뒤 연결을 닫으므로 거절된 요청마다 새 TCP 연결이 필요하고, 거절이 늘면 새 연결을 받는 대기열(Tomcat 기본 accept-count 100)이 넘쳐 연결 요청이 버려지고 클라이언트가 재시도하는 것으로 보인다(응답이 1초·수 초 단위로 튐, 거절이 많은 설정이 먼저 무너짐).
- **확인 방법(보류):** 같은 4,000/s에서 거절 응답만 503 → 429(Tomcat이 연결을 유지)로 바꾼 회차, 503 그대로 accept-count만 늘린 회차를 비교한다.
- GC 기록: 이 시리즈는 같은 파일 이름에 덮여 21회차(3,600/s) 것만 남았다(`p20-k20-intake4-3600-single/gc.log`). 나머지 회차의 GC 수치는 각 회차 직후 확인한 값이다.

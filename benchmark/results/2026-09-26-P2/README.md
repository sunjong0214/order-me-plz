# 파일럿 P2 — 비동기 방식과 워커 k (2026-09-26~27)

비동기 주문(`POST /api/v1/order/async`)의 저장 처리량 W를 정하는 파일럿. 조건은 P1과 같다.
- 회차마다 직전 부하 종료 후 15분 휴식, 충전기 확인, 노트북 클럭·프로세스별 CPU 기록.
- 서버 재시작 → 워밍업 1분 → 큐 소진 → reset → 3분 측정 → 큐 소진 → DB 주문 수·MySQL 명령 수 확인.
- 판정: k6 연결 실패 0건, 측정 중 데스크톱 CPU 평균 80% 미만(80% 이상 2표본 연속 금지), 정합성 대조(503 수 = 서버 거절 카운터, DB 주문 수 = 접수 − 저장 실패).

**결론: `single` 채택, P = 20, k = 20, W = 약 2,940건/s(좋은 상태 기준, 회차에 따라 약 2,620~2,950건/s로 갈림 — 8절), 큐 Q = 70,000. 거절 응답은 429(7절).**

## 5. 선정

규칙은 P1과 같다: 최대 평균 W의 95% 이상인 가장 작은 설정, 202 p95 ≤ 200ms.

| 설정 | 유효 회차 W/s | 평균 | 최대 평균 대비 |
|---|---|---|---|
| **P=20, k=20** | 2,939 · 2,947 | **2,943** | **100%** |
| P=15, k=15 | 2,760 · 2,728 (1회 붕괴) | 2,744 | 93.2% |
| P=10, k=10 | 2,187 · 2,210 | 2,199 | 74.7% |

- 95% 기준선 2,796건을 넘는 가장 작은 설정은 **P=20·k=20**이다. 두 회차 모두 안정적이었고 거절이 적어 유입 한계 근처에서도 연결 재수립이 적다.
- **사전 규칙과 다른 선택이다.** P2 전에 적은 대비 규칙("P=10에서 어떤 k도 W 정체 + 202 p95 ≤ 200ms를 만족하지 못하면 P=15")을 글자대로 적용하면 P=10에서 k=8 → 10이 정체(2,173 → 2,187)하므로 P=10·k=8이 된다. 그 규칙은 "P를 10 넘게 늘려도 처리량이 늘지 않는다"는 동기(P1) 결과를 전제로 했는데, 비동기 single에서는 k를 20까지 늘리면 +35%로 전제가 틀렸다. 그래서 P1과 같은 95% 규칙을 격자 전체에 적용했다.
- W = 2,943건/s는 유입 한계(약 3,000건/s)에 닿은 값이라 실제 저장 용량은 이보다 높을 수 있다.
- 큐 Q = W × 30초 × 0.8 = 70,632 → **70,000**(최대 대기 ≈ 70,000 ÷ 2,943 ≈ 24초). 리뷰 통계 워커 = P/2 = 10.
- 동기 비교군도 같은 P=20으로 돈다(고정 설정). P1에서 동기 P=20은 2,361건/s.

- 503 회차의 양상은 6절 19회차(4,000/s, 503: p95 1,241ms, 연결 실패 7,502건)와 같다. **503은 3회 중 3회 붕괴, 429는 2회 중 0회.**
- **원인 확인: 503 뒤 끊기는 연결.** 거절 수는 비슷한데(초당 약 800~1,070건) 새 TCP 연결이 429에서 초당 44~45개(k6가 VU를 늘릴 때 여는 연결과 지표 폴링), 503에서 824~1,051개로 거절 수만큼 늘었다. 재전송도 429 첫 회 79/s에 비해 503은 1,163~1,264/s였다. 거절마다 연결을 새로 받는 일에 연결 요청 재시도가 겹쳐 응답이 초 단위로 튀고(p95 약 1.2초, p99 약 4.8초), 느려진 요청이 쌓여 회복하지 못한 것으로 본다. 재시도 간격은 패킷 캡처로 확인하지 않았다.
- **연결 대기열(accept-count)을 100 → 1,000으로 늘려도 붕괴했다.** 대기열 길이만의 문제가 아니거나 OS가 대기열 길이를 제한했을 수 있다(Windows Home의 상한은 확인하지 못함). 어느 쪽이든 대기열을 늘리는 것으로는 해결되지 않았다.
- **CPU·GC는 원인이 아니다.** GC 멈춤 최대는 네 회차 모두 52~82ms로 비슷했다. 노트북 CPU는 오히려 429 회차가 높았는데(95~99%), 무너지지 않고 계속 일했기 때문이다.
- **429도 4,000/s는 용량 밖이다.** 두 회차 모두 접수 p95가 요구값 200ms를 넘었고(246·372ms), 25회차는 짧은 멈춤으로 연결 실패 48건·p99 1.2초가 나왔다. 429가 바꾸는 것은 "넘는 순간 무너지느냐, 느려지며 버티느냐"이고 처리 용량(약 2,900건/s)은 그대로다.
- 데스크톱 CPU는 평균 25~38%(최대 56%)로 부하 발생기 기준 안이다. 503 회차의 연결 실패는 서버가 연결을 받지 못한 것이다(오류 종류는 연결 시도 시간 초과 `connectex`·`wsarecv`, 포트 고갈 오류 없음).
- **채택: 거절 응답 429**(`omp.order.async.reject-status` 기본값, 근거와 프록시 구성은 [benchmark/README.md](../../README.md) 2절 "거절 응답 코드"). 1~6절은 503으로 쟀다. 거절이 섞인 회차의 선정·유입 한계·구성 비교는 429로 다시 잰다.

## 8. 429 재측정과 안정 한계 (single P=20·k=20, 2026-09-28 19:57~22:27)

429 채택 뒤 선정 확인(3,000/s)과 유입 한계(3,300·3,600/s)를 다시 재려 했으나, 첫 두 회차가 이전과 크게 달라 계획을 바꿨다: 503/429 대조(28·29회차) → 안정 한계 찾기(2,850·2,700/s, 30~33회차). 절차·판정은 앞 절과 같다. TCP 재전송은 노트북 TCPv4 카운터의 측정 3분 평균이다.

- **503과 429는 차이가 없다.** 같은 저녁의 3,000/s에서 503은 2,695건(나쁨), 429는 2,708건(나쁨)·2,923건(좋음)이었다. 7절의 차이(503만 붕괴)는 거절이 초당 800건 이상인 4,000/s에서의 이야기이고, 거절이 적은 부하에서는 응답 코드가 결과를 가르지 않는다.
- **3,000/s는 안정 구간이 아니다(6절 정정).** P=20·k=20의 3,000/s 누적 6회(13·16·20·26·28·29회차) 중 4회 좋음(2,923~2,947건), 2회 나쁨(2,695·2,708건). P=15·k=15는 4회 중 2회 붕괴(15·27회차). 6절의 "안정 구간은 3,000/s까지"는 3회만 보고 내린 판단이었다.
- **부하를 낮춰도 나쁜 상태가 사라지지 않았다.** 2,850/s는 2회 모두 좋음, 2,700/s는 2회 중 1회 나쁨. 회차가 2회씩이라 부하별 확률은 말할 수 없고, 2,700~3,000/s 구간에 깔끔한 문턱이 없다는 것까지만 말할 수 있다.
- **좋고 나쁨은 커밋 묶음과 함께 움직인다.** 같은 부하에서 나쁜 회차는 주문당 redo fsync가 많고(3,000/s: 좋음 0.35 / 나쁨 0.57~0.65, 2,700/s: 좋음 0.54 / 나쁨 0.69), MySQL이 주문당 CPU를 약 15~20% 더 쓴다. 한 번의 fsync에 묶이는 커밋이 적을수록 주문당 비용이 오른다.
- **노트북 CPU 사용률로는 여유를 알 수 없다.** 2,700~3,000/s의 모든 회차에서 96~99%였다. 부하가 낮으면 커밋이 덜 묶여 주문당 CPU가 오른다(좋은 회차 기준 3,000/s 약 0.033%p, 2,700/s 약 0.037%p).
- **나쁜 상태의 고리(추정):** 접수가 조금 밀림 → 큐가 비었다 찼다 반복 → 동시에 커밋하는 워커 감소(평균 15.5~16.9개, 좋은 회차 17.8~19.6개) → 커밋 묶음 감소 → MySQL 주문당 CPU 증가 → 접수에 쓸 CPU 감소. 과부하가 깊으면(3,000/s) TCP 재전송(363~1,248/s)과 연결 지연(최대 15초)이 겹쳐 붕괴로 간다. 어떤 회차가 이 고리에 빠지는지는 확인하지 못했다(3,000/s의 나쁜 회차는 모두 워밍업 연결 실패가 365~628건, 좋은 회차는 0건).
- **원인이 아닌 것:** 거절 응답 코드, GC(멈춤 최대 65~97ms), Microsoft Defender(17:36 정의 업데이트 뒤 40초 검사 기록에서 mysqld 파일 검사 322ms), 노트북 백그라운드(부하 없을 때 CPU 1.5~2%), SSD(52°C, 마모 0), binlog 파일 교체(나쁜 회차 3회 중 1회만 겹침), 네트워크 오류 카운터(0), 데스크톱(측정 중 평균 19~39%).
- **판단:** 이 노트북에서 single P=20·k=20의 저장 용량은 한 점이 아니라 **약 2,620~2,950건/s 구간**이고, 회차마다 어느 쪽으로 갈지 정해지지 않는다. 좋은 상태만 골라 쓰면 과장이 되고, 나쁜 상태만 쓰면 과소평가가 된다.

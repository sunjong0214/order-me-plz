P1에서 확정한 P = 10으로 비동기 주문(`MODE=async`, `POST /api/v1/order/async`)의 저장 처리량 W를 재는 파일럿. 조건은 P1과 같다(회차마다 15분 휴식, 충전기 확인, 노트북 클럭 기록, 서버 재시작 → 워밍업 1분 → 큐 소진 → reset → 3분 측정 → 큐 소진 → DB 주문 수·MySQL 명령 수 확인).

## 첫 시도(3,470/s)에서 찾은 결함

- 접수 트랜잭션(커넥션 획득 → 검증 SELECT)을 마친 뒤 submit에서야 큐가 찼는지 알았다. 어차피 거절될 요청도 커넥션과 쿼리를 썼다.
- 거절마다 WARN 로그 한 줄. 회차당 32만~38만 줄(63~74MB), 초당 약 1,700줄을 커넥션을 쥔 채 썼다.
- 결과: 과부하가 클수록 거절 비용이 받은 주문까지 느리게 했다(503조차 p95 0.3~0.8초, 저장 처리량 약 1,000/s). "초과분 즉시 503" 요구를 구현이 지키지 못했다.
- 정합성은 유지됐다: k6 503 수 = 서버 거절 카운터, DB 주문 수 = 접수 수(k=4·8).
- 수정: 트랜잭션 전 대기 자리 예약(`AsyncOrderAdmission`, 자리 수 = 큐 용량, 워커가 작업을 시작할 때 반납) + 건별 로그 제거. 테스트: 자리가 없으면 검증 쿼리 0회로 즉시 503.

## 비동기 용량이 동기보다 낮은 이유 (확인 중)

같은 SQL(검증 SELECT 1 + INSERT)인데 비동기 용량(약 1,500/s)은 동기(2,314/s)의 약 65%이고 주문당 MySQL CPU는 약 1.6배다. 비동기(SPLIT)는 주문을 트랜잭션 두 개(접수 검증 + 워커 INSERT)로 나눈다. before2250 회차의 주문 1건당 MySQL 명령 수: Questions 17.5, SELECT 3.71, INSERT 2.00, COMMIT 2.00, SET(격리 수준·autocommit 등) **9.42**, redo fsync 2.30. 트랜잭션 구성을 설정으로 전환(`omp.order.async.transaction=split|single`)해 같은 조건에서 비교한다. SELECT에는 거절·실패한 요청의 검증 쿼리도 포함된다(접수 1건 기준으로 나눈 값).

## 부하 발생기 한계: 503마다 연결이 끊긴다

Tomcat은 503(400·500 등도) 응답 뒤 연결을 닫는다. 거절이 많으면 k6가 새 연결을 계속 열고, 데스크톱의 임시 포트(1024~15000, 13,977개)가 TIME_WAIT(기본 120초)에 묶여 초당 약 116개 이상은 새 연결을 열 수 없다. 실서비스의 클라이언트는 각자 포트를 쓰므로 이 제약은 부하 발생기 한 대로 흉내 낼 때만 생긴다. 과부하 회차 전에 데스크톱의 포트 범위를 넓히고 TIME_WAIT를 줄여야 한다(README 7절).

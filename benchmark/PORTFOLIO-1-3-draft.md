# 포트폴리오 1-3 재작성 초안 (2026-09-26)

> 상태: **설계 초안.** 만료 시간 5분은 2026-09-26 확정(근거는 아래 "만료 시간 5분의 근거"). `[제안]` 표시는 아직 코드에 반영하지 않은 변경이며, 구현·테스트 후 표시를 지운다. 수치는 계산값이거나 선택 측정 자리표시다.
> 구성: 문제(목록 캐시의 만료 시간에 근거가 없고, 바뀌는 값이 그대로 캐시됨) → 캐시 대상과 신선도 요구 → 만료 시간 5분의 근거 → 만료 집중과 동시 로딩 → 검증 → 한계.
> 1-1과의 연결: 1-1은 리뷰 통계의 신선도를 3순위(즉시 반영 불필요, 수 분 지연 허용)로 두었다. 목록 캐시의 만료 시간은 그 "얼마나 늦어도 되는가"를 수치로 정하는 자리다.

## 1-3. 가게 목록 캐시의 만료 시간을 신선도 요구로 정하고, 만료 집중과 동시 로딩을 나눠 대응

기간: 캐시 적용 2025.03 → 만료·무효화 정책 재설계 2026.09

### 결과 요약

- 카테고리별 가게 목록(커서 페이지)에 Caffeine 로컬 캐시 적용
- 만료 시간을 성능이 아니라 "목록에 보이는 값이 얼마나 늦어도 되는가"로 다시 정했다. 평점·리뷰 수는 최대 **5분** 지연을 허용하고, 영업 상태·가게 정보·새 가게는 변경 시 즉시 무효화한다 `[제안: 무효화]`
- 5분은 1-1에서 정한 통계의 허용 지연("수 분") 안에 있으면서, 서비스 규모로 계산한 목록 재조회 부하를 60초 대비 1/5로 줄이는 값이다
- 여러 키가 한꺼번에 만료되는 문제는 Jitter로, 인기 키 하나가 만료되는 순간 요청이 몰리는 문제는 동시 로딩 합치기(`sync`)로 원인을 나눠 대응했다 `[제안]`

### 문제 상황

- 가게 목록은 카테고리·커서·페이지 크기 조합으로 반복 조회되고, 매번 shops와 shop_review_stats를 조인한다
- 기존 구현은 만료 24시간 + 0~3초 Jitter였고 무효화가 없었다
  - 목록에 영업 상태와 평점이 들어 있어, 가게가 문을 닫아도 최대 24시간 "영업 중"으로 보였다. 주문은 DB 기준으로 검증하므로 400으로 거절되어, 목록과 주문 결과가 어긋났다
  - 1-1에서 통계 정합성을 보장해도, 목록 화면은 최대 24시간 전의 평점을 보여 주었다
  - 24시간에 3초 Jitter는 만료 분산 폭이 만료 시간의 0.003%로, 24시간이라는 값 자체의 근거도 없었다
  - 인기 키 하나가 만료되는 순간 동시에 들어온 요청은 모두 DB를 조회한다. Jitter는 서로 다른 키의 만료 시각을 흩을 뿐 이 경우를 막지 못한다
- 목록 쿼리에 정렬이 없어(`shop_id < cursor`인데 `ORDER BY` 없음) 페이지 경계가 고정되지 않았다. 커서 페이징과 캐시 키가 모두 흔들리는 버그다 `[제안: ORDER BY shop_id DESC]`

### 캐시 대상과 신선도 요구

캐시 키는 (카테고리, 커서, 페이지 크기)이고 값은 가게 최대 20개짜리 목록 페이지 하나다.

| 목록의 값 | 바뀌는 계기 | 허용 지연 | 대응 |
|---|---|---|---|
| 영업 상태 | 영업 시작·종료 | 즉시 (주문 가능 여부와 직결) | 변경 시 캐시 전체 무효화 `[제안]` |
| 이름·카테고리 | 가게 정보 수정 | 즉시 | 수정 시 무효화 `[제안]` |
| 새 가게 | 가게 생성 (페이지 경계가 밀림) | 즉시 | 생성 시 무효화 `[제안]` |
| 평점·리뷰 수 | 리뷰 작성 (빈번) | **최대 5분** | 만료 시간으로 상한. 리뷰마다 무효화하면 리뷰가 많은 가게일수록 캐시가 비어 의미가 없다 |

만료 시간은 이벤트로 무효화할 수 없는 값(평점·리뷰 수)의 허용 지연으로 정한다. 가게 변경은 드물어서 캐시 전체(`allEntries`)를 비워도 부담이 작다.

### 만료 시간 5분의 근거

처음에는 1-1 요구("수 초~수 분")의 짧은 쪽에서 60초를 골랐지만 계산 근거가 없었다. 무효화가 영업 상태 등을 맡으면 만료 시간이 책임지는 값은 평점·리뷰 수뿐이므로, 짧을 때와 길 때의 비용을 각각 따져 다시 정했다.

**① 길 때의 비용 (평점 지연): 체감이 작다.** 평점 범위가 1~5점이라 리뷰 n개인 가게에 리뷰 한 건이 추가되면 평균은 최대 4/(n+1) 움직인다. 리뷰 100개면 최대 0.04, 1000개면 0.004다. 리뷰가 자주 달리는 가게일수록 평균이 거의 움직이지 않고, 한 건에 크게 움직이는 리뷰 적은 가게는 몇 분 안에 새 리뷰가 달릴 확률이 낮다. 가게 상세는 캐시하지 않아 방금 쓴 리뷰는 상세에서 바로 보인다.

**② 짧을 때의 비용 (재조회 부하): 테스트 규모에서는 없고, 서비스 규모에서 드러난다.** 목록 재조회는 인스턴스당 많아야 "키 수 ÷ 만료 시간"이다.

| 만료 시간 | 테스트 규모 (키 52개) | 서비스 규모 (인기 키 약 1.4만 개, 인스턴스당) |
|---|---|---|
| 60초 | 초당 0.87회 | 초당 약 226회 |
| **5분** | **초당 0.17회** | **초당 약 45회** |
| 10분 | 초당 0.09회 | 초당 약 23회 |
| 24시간 | ≈ 0 | 초당 0.2회 |

- 테스트 규모: 가게 1000개 ÷ 카테고리 4개 ÷ 페이지 20개 = 카테고리당 13페이지 × 4 = 52키. 어느 값이든 재조회 부하는 무시할 수준이라 테스트만으로는 만료 시간을 정할 수 없다
- 서비스 규모: 배달의민족 입점 가게 전국 약 30만 개(2025) 기준. 실제 목록은 배달 권역 단위이므로 권역 226곳(기초자치단체 수) × 카테고리 약 20개 × 주로 보는 앞쪽 3페이지 ≈ 1.4만 키로 가정했다. 60초와 5분 사이에 재조회 부하가 5배 차이 난다

**③ 결정.** 1-1에서 허용한 "수 분" 안에서, 서비스 규모의 재조회 부하를 60초 대비 1/5로 줄이는 **5분**. 10분도 같은 논리로 가능하지만 "수 분"이라는 요구와 가장 자연스럽게 맞는 값을 택했다. 가게·필터 조합이 늘어 키가 커지면 같은 식(키 수 ÷ 만료 시간)으로 다시 계산한다.

적중률도 확인했다. 요청이 무작위로 온다고 보면 적중률 = λT / (1 + λT)이다(λ: 키당 초당 요청 수, T: 만료 시간).

| 키 | λ | T = 60초 | **T = 5분** | T = 24시간 |
|---|---|---|---|---|
| 인기 키 (카테고리 첫 페이지) | 초당 10건 | 99.83% | **99.97%** | 99.9999% |
| 뒤쪽 페이지 | 100초에 1건 | 37.5% | **75%** | 99.88% |

인기 키는 어느 값이든 99.8% 이상이다. 24시간은 신선도를 크게 잃는 대신 얻는 것이 거의 없는 값이었다.

### 만료 집중과 동시 로딩

| 상황 | 원인 | 대응 |
|---|---|---|
| 여러 키가 같은 시각에 만료 | 재시작·배포 직후처럼 인기 키들이 같은 순간에 채워지면 5분 뒤 함께 만료되어 재조회가 한꺼번에 몰린다 | Jitter: 만료 시간에 0~10%(0~30초)를 무작위로 더해 재조회를 흩는다 `[제안: 고정 3초 → 비율]` |
| 인기 키 하나의 만료 순간 요청 집중 | 만료 직후 도착한 요청이 모두 캐시 미스 → 같은 쿼리를 N번 실행 | `@Cacheable(sync = true)`: 같은 키의 동시 미스는 한 요청만 DB를 조회하고 나머지는 그 결과를 기다린다 (JVM 단위) `[제안]` |

### 검증 방법

- 기능 테스트 `[제안]`
  - 영업 상태를 바꾼 직후 목록을 다시 조회하면 바뀐 값이 보인다 (무효화)
  - 만료된 같은 키에 동시 요청 N개 → 목록 쿼리 실행 1회 (sync)
  - 커서로 이어서 조회하면 가게가 중복·누락 없이 id 내림차순으로 나온다 (정렬)
  - 만료 시간이 지나면 다시 조회한다 (Caffeine 가짜 시계로 시간 제어)
- 선택 측정: k6로 목록 API에 고정 유입. 캐시 켬/끔에 따른 p95, MySQL 조회 수(`Com_select` 증가분), 적중률(`cache.gets` hit/miss, `recordStats` 활성). 만료 순간의 DB 조회 수를 sync 켬/끔으로 비교

### 한계 및 후속 개선

- 목록 API에 위치(배달 권역) 필터가 없다. 테스트 DB의 가게 1000개는 "배달 권역 하나"(전국 30만 개 ÷ 226곳 ≈ 평균 약 1,300개, 추정)에 해당하며, 서비스 규모의 판단은 위 계산으로 대신했다
- 로컬 캐시라 다중 인스턴스에서는 인스턴스마다 값이 다르고, 무효화도 요청을 받은 인스턴스에만 적용된다. 공유 캐시(Redis)나 무효화 메시지 전파가 필요하다
- `sync`는 한 JVM 안에서만 동시 로딩을 합친다
- 평점·리뷰 수는 최대 5분(+ Jitter) 늦게 보인다(의도한 허용 지연). 허용 지연과 서비스 규모의 키 수는 서비스 데이터가 아닌 가정이다
- 가게 상세 조회는 캐시하지 않아 항상 최신 값이다. 목록과 상세의 평점이 잠시 다를 수 있다

### 느낀 점

- 캐시 만료 시간은 성능 숫자가 아니라 "얼마나 늦어도 되는가"라는 요구로 정하고, 그 요구 안에서 부하를 계산해 고른다. 테스트 규모에서는 어떤 값도 차이가 없어서, 서비스 규모를 따로 계산해야 값이 정해졌다
- 만료 문제는 "여러 키가 동시에"와 "한 키에 요청이 동시에"로 원인이 달라 해법도 다르다

## 1. 배경

포트폴리오의 OMP 수치는 nGrinder 기반이며 재현 조건이 기록되어 있지 않음. k6로 전·후를 동일 조건에서 재측정해 정확한 수치로 교체하는 것이 목표.

**현재 포폴 수치 (교체 대상)**

| 항목 | 변경 전 | 변경 후 | 조건 |
|---|---|---|---|
| 리뷰 15분 처리량 | 약 25,000건 | 약 38,000건 | 데드락 발생 → 제거 |
| 주문 15분 접수량 | 1,230,487건 | 최대 2,680,000건 | vUser 500 |
| 주문 평균 응답 | 359ms (Pool 10) / 323ms (Pool 15) | 172ms | 목표 200ms |
| 환경 | CPU 4코어, 단일 JVM, nGrinder vUser 200~500 | | |

포폴이 스스로 인정한 미측정 항목: p95·p99, 비동기 INSERT의 DB 저장 완료 건수, Executor Queue 잔여량·소진 시간.

**서사 전환 (플랜 PDF 기준, 유지)**: 처리량 주장 → 결함·정합성 주장. 데드락은 동시 2건이면 발생하는 결함이므로 빈도가 아닌 결함 관점으로 재현·검증.

## 2. 측정 전에 반드시 고쳐야 하는 코드 결함

> ⚠️ 이 결함들을 두고 측정하면 수치가 무효가 된다. 수정 전 재현 테스트 → 수정 → 동일 테스트 통과 순서로 진행.

### 2-1. 평균 평점 UPDATE 대입 순서 버그

- 위치: `ShopReviewStatsRepository.applyReviewRating`
- 현재 JPQL은 `rating_sum`, `review_count`를 먼저 증가시킨 뒤 평균을 `(rating_sum + :rating) / (review_count + 1)`로 계산.
- MySQL은 단일 테이블 UPDATE의 대입을 왼쪽부터 평가하고 뒤의 대입은 갱신된 값을 봄 → 증가분이 두 번 반영됨. 예: 5점 뒤 1점 → 평균 3이 아니라 7/3.
- 수정: 평균 대입을 맨 앞으로 옮기거나, 뒤에 두고 갱신된 컬럼으로 `rating_sum / review_count` 사용.
- 검증: 실제 MySQL에서 1점·5점 두 건 → `count=2, sum=6, average=3` 확인. 생성 SQL 로그와 별도 커넥션으로 읽은 최종 커밋 값으로 판정 (예외 없음 = 성공으로 처리 금지). H2로는 재현 안 됨.
- 근거: 코드 + MySQL 공식 문서 (미실행).

### 2-2. CallerRunsPolicy + REQUIRED 트랜잭션 → 커밋 유실 (가장 중요)

- 위치: `ShopReviewStatsUpdater.updateReviewStats`, `AsyncOrderProcessor.processOrderTask` (둘 다 기본 전파 `@Transactional`)
- 메커니즘: `@TransactionalEventListener(AFTER_COMMIT)` 리스너가 executor에 제출 → 풀 포화 시 CallerRunsPolicy가 **요청 스레드에서 인라인 실행** → 그 시점은 원 트랜잭션의 afterCompletion 단계로 커넥션·트랜잭션 자원이 아직 바인딩되어 있음 → REQUIRED가 이미 커밋된 트랜잭션에 참여 → 변경이 커밋되지 않음 (또는 TransactionRequiredException).
- 영향: 주문은 202를 반환했는데 INSERT가 사라짐. 리뷰 통계는 조용히 누락. README가 "이중 분포 = 백프레셔 정상 동작"이라 적은 구간이 실제로는 유실 구간일 수 있음.
- 삭제된 옛 `ReviewUpdateService`는 `REQUIRES_NEW`였음 → 리팩터링 회귀.

**REQUIRES_NEW만으로는 부족한 이유 (2차 리뷰 지적)**
- 요청 스레드가 원 트랜잭션 커넥션을 보유한 채 새 커넥션을 요구 → 스레드 하나가 커넥션 2개 필요.
- 이런 스레드가 Hikari 풀(20) 이상 겹치면 서로 대기 → connection-timeout(기본 30s) 후 예외. 주문은 예외가 afterCompletion에서 로그로만 남고 202는 그대로 나감 → **30초 지연 + 유실**.

**수정 방향 후보 (결정 필요)**

| 방향 | 내용 | 장점 | 비고 |
|---|---|---|---|
| A. 명시적 거절 (추천) | CallerRunsPolicy 제거. 거절 시 주문은 맵 엔트리 제거 + 503/Retry-After, 리뷰 통계는 reviewId 로그 + 거절 카운터 | 지연 격리 주장이 실제로 성립, 백프레셔 발동 횟수가 지표로 생김, 포폴에 정직하게 서술 가능 | REQUIRES_NEW는 방어선으로 병행 |
| B. 제출 시점 이동 | 컨트롤러가 서비스 반환 후(트랜잭션 완전 종료·커넥션 반납 후) 제출 | 어떤 스레드든 커넥션 1개만 사용 | "커밋 이후 이벤트" 서사·구조 변경 |

**테스트 2종**
1. Executor 포화 시 커밋 여부: 첫 작업을 latch로 대기시켜 큐를 채운 뒤 추가 제출로 거절 경로 강제 → 호출 스레드 실행 횟수 vs DB 커밋 건수 대조. 수정 전 실패·수정 후 통과 확인.
2. 커넥션 부족 상황: Hikari 풀 2~3개, connection-timeout 3초로 낮춰 제한 시간 안에 어떤 결과로 끝나는지 확인. 풀을 늘려 통과시키지 말 것. 측정 회차에서 `hikaricp.connections.timeout` 카운터 기록.

### 2-3. 동기 주문 검증이 사실상 꺼져 있음

- `OrderValidateDto.isValid()`가 `||` → 셋 중 하나만 유효해도 통과. `&&`로 수정.

### 2-4. 동기·비동기 주문의 비교 조건 불일치

| 항목 | 동기 `POST /api/v1/order` | 비동기 `POST /api/v1/order/async` |
|---|---|---|
| 검증 | validateOrder SELECT 1회 | 접수: existsById SELECT 3회 (트랜잭션·커넥션 점유) + 워커: findById 2회 |
| 저장 | INSERT 2회 | INSERT 2회 |
| validateCart | 주석 처리 | 주석 처리 |
| 격리 수준 | READ_COMMITTED 명시 | 기본 |

- 검증 규칙·입력 데이터·저장 데이터·격리 수준을 맞추고 실행 방식만 바꿔야 "비동기 전환 효과"라 말할 수 있음. 접수 경로가 DB 쿼리 3회를 포함한다는 점을 결과 표에 명시.
- 시딩된 장바구니의 가게와 요청 shopId 일치 여부도 결정.

### 2-5. 기타 확인 사항

- `src/test`의 동시성 테스트 3개(ReviewServiceDeadlockTest, ReviewConcurrencyTest, ShopReviewsTest)는 전부 주석 처리 상태 → 결정적 재현 테스트는 새로 작성.
- Spring의 AFTER_COMMIT 리스너는 afterCompletion 경로에서 실행되며 그곳의 예외는 로그로만 남음 → 면접 답변 "동기 AFTER_COMMIT은 500"은 틀림. 실제는 "리뷰 저장 + 200, 통계는 조용히 누락". 비동기 근거는 "격리 + 실패 관측(거절 카운터·실패 상태 기록)"으로 수정.
- `AsyncOrderManager` 맵은 완료 시 remove되어 누수 아님 (확인).

## 4. 측정 설계 보완

### 4-1. 절차

- 워밍업 순서 변경: `재시작 → 워밍업 → reset-round.sql → 데드락 카운터 기록 → 본측정`. (현재 README는 reset 뒤 워밍업이라 워밍업 데이터가 본측정에 섞임)
- 리뷰 결함 재현 회차: `RATE=20, SHOP_POOL=10`은 요청이 거의 겹치지 않아 개선 전에서도 데드락이 안 날 수 있음. closed model `constant-vus` 50~100 + SHOP_POOL 1~3으로 잡고, **1분 파일럿으로 개선 전 데드락 발생 조건을 먼저 확정** 후 전·후 동일 조건 적용. 결정적 재현 테스트(두 트랜잭션이 FK 락 획득 후 UPDATE하도록 순서 통제)와 부하 테스트를 병행.
- 용량: 램프로 후보 구간 탐색 → 후보 rate에서 15분 고정 × 3회 확정. 현재 램프 주석은 각 목표까지 계속 증가만 하고 유지 구간이 없음 → 같은 값의 hold 스테이지 추가 또는 계단식 고정 run. k6 최종 summary p95는 전체 집계라 한계 지점을 못 읽음.
- 판정 기준: 실패율 0은 **개선 후 정상 동작 검증**에만 적용. 개선 전 데드락 재현 회차는 "예상한 원인의 실패가 발생했는가"로 별도 판정.

### 4-2. 지표 정의

| 현재 명세 | 보완 |
|---|---|
| `iterations` = 접수량 | 실패 포함됨. 시도량 / 성공 응답량 / 202 접수량 / DB 커밋량 구분. `orders_accepted`, `reviews_created` 카운터 활용 |
| "15분 내 DB 저장 완료량" | 사용 금지. **"15분 부하 인가 후 k6 종료 시점의 저장 완료량"** + **"전체 작업 완료 시점의 저장 완료량"** 두 줄로 분리. gracefulStop 명시. (정확한 900초 시점 측정은 "15분 내 완료량"을 주장할 때만 필요) |
| `queued=0` = 완료 | `executor.active`, 호출 스레드(또는 거절) 실행 횟수, 커밋 완료량까지 확인 |
| 종료 후 1~2분 대기 후 검증 | 완료 조건 충족까지 대기, 제한 시간 초과 시 미완료로 기록 |
| 큐 소진 시간 | insertTaskExecutor 큐 100이라 항상 1초 미만 → 의미 있는 지표는 **거절/백프레셔 발동 횟수** (2-2 수정 A로 자연스럽게 확보) |

- 요청별 식별자와 저장 결과 대조 → 유실·중복 검증 (2-2 검증 시 함께).
- 요청~DB 커밋 p95/p99를 쓰려면 그 구간을 별도 계측.

### 4-3. k6 설정

- thresholds: `http_req_failed: rate==0`, `checks: rate==1` 추가 (check 실패만으로는 k6가 실패 처리하지 않음). 현재 `<1%`는 "실패 0건" 문구보다 느슨.
- `--no-usage-report`, k6 버전 기록, 요청 timeout·gracefulStop·VU 설정·실제 전송률 기록, `dropped_iterations=0` 확인.
- 결과 저장: `benchmark/results/` 생성, 스크립트에 OUT_DIR env 추가, 회차별 요약 JSON + 시계열(`--out csv`) 커밋.
- 성능은 회차별 중앙값·범위, 오류·불일치는 모든 회차의 건수 기록.

### 4-4. 검증 SQL (verify.sql) 보완

- 현재: count·sum만 비교. 추가: **리뷰는 있는데 통계 행이 없는 가게**, **average 불일치** (DB 소수 자릿수·반올림 규칙 명시).
- 개선 전 회차용: shops 구 컬럼 기준 유실 확인 쿼리.

## 6. 포폴 문구 수정 방향

| 현재/계획 문구 | 수정 |
|---|---|
| "데드락이 구조적으로 불가능" | "기존 FK S→X 잠금 승격으로 발생하던 데드락 경로 제거" |
| "원자 연산으로 유실 불가능" | "동시 UPDATE의 갱신 유실 방지" (이벤트 누락·중복은 별개) |

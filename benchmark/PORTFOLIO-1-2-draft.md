## 1-2. 선착순 한정 수량 주문: 재고 판정은 3방식 중 재고 행 병목이 없는 메모리 번호표로, 접수 방식은 매진 전 거절과 확정 속도를 비교해 선택

기간: 비동기 접수 구현 2025.07–08 → 거절 정책·트랜잭션·풀과 큐 재설계, 선착순 재고 설계·검증 2026.08–10

### 결과 요약

- 중소 배달앱(MAU 약 345만) 규모의 선착순 할인을 가정해 실험했다. 정각에 앱 전체 재고 10만 개를 두고 시도 약 23만 건(최고 초당 3,000건, 가정)이 몰리고, 그동안 평상시 주문이 초당 40건 들어온다
- 재고 판정 3방식(DB 행 하나 · DB 여러 행 · 메모리 번호표) × 접수 2방식(빠른 거절 동기 · 비동기)에, 상한 없는 동기 · 메모리와 상한을 190으로 올린 빠른 거절 동기 · 메모리를 더한 8개 구성을 유효 3회씩 쟀다(무효 7회 포함 모두 31회). 메모리 번호표는 재고 수만큼의 번호를 메모리에서 먼저 발급하고 DB 유니크 제약이 최종 보증하는 방식이고, 빠른 거절 동기는 동시 처리 수가 상한(처음 130, 다시 잰 190)을 넘으면 기다리지 않고 바로 429를 준다. 31회 모두 초과 판매 0, 재고 보존(할인 주문 수 + 남은 재고 = 10만)
- **결정 1. 재고 판정은 메모리 번호표로 정했다.** 10만 건이 모두 확정(DB 커밋)된 시각(비교군별 유효 3회 중앙값. 범위는 같은 재고 방식 안에서 접수 방식에 따른 차이)은 DB 행 하나 89.7–90.0초 → DB 여러 행 52.5–56.7초 → 메모리 번호표 37.9–41.0초였다. 같은 재고 방식이면 동기·비동기 차이는 작았다. 메모리 방식은 10만 번째 시도가 도착하는 시각(정각 + 약 35.8초)보다 2–5초 늦었다
- **결정 2. 접수는 비동기를 택했다. 성능 우위가 아니라 무엇을 먼저 지킬지의 판단이다.** 측정한 동기 구성에서는 넘친 요청이 요청 스레드(Tomcat 200개)를 쥐거나 그 앞의 Tomcat 대기열에서 기다린다. 빠른 거절 동기는 재고가 남은 동안(서버 1초 기록 기준) 상한 130에서 시도 9,279–15,418건·평상시 주문 120–208건을, 상한을 190으로 올려도 시도 6,215–13,393건·평상시 주문 85–190건을 429로 돌려보냈고, 상한 없는 동기는 서버가 거절하지 않았지만 스레드 200개가 모두 차 저장 완료 p95 1.48초, 평상시 주문 p95 0.74초로 늦어졌다. 비동기는 메모리 번호표와 함께 쓸 때 대기를 스레드 밖의 큐(7만 칸)로 옮겨 매진 전 거절이 0이었다(DB 행 하나와 쓰면 큐가 차 시도 약 5.1만 건을 429로 돌려보냈다)
- **결정 2의 대가.** 주문 하나가 확정되기까지는 상한 190 동기가 빨랐다(요청 → 확정 평균 0.08초, 비동기 0.72초). 비동기의 접수(202) p95 ≤ 200ms 요구는 유효 3회 중 1회만 지켰고, 202를 받고 아직 저장되지 않은 주문은 메모리 큐에 있어 재시작하면 사라진다(운영하려면 영속 큐가 전제다). 응답 p95는 200(저장 완료)과 202(접수)의 뜻이 달라 비교하지 않는다. "매진 전 거절 0"을 확정 속도와 접수 p95 요구보다 앞에 둔 이 우선순위는 첫 측정 결과를 본 뒤 정했고, 상한 190 추가 측정은 "매진 전 429가 남으면 결정 2를 유지하고 0이면 범위를 줄인다"고 해석을 먼저 정한 뒤 쟀다
- **처음 잰 "비동기 처리량 +19%"는 스스로 정정했다.** 부하가 동기를 포화시키지 못한 측정(Tomcat 바쁜 스레드 200개 중 평균 68–86개)이었고, 가상 사용자를 400명으로 늘려 다시 재니 할인 없는 일반 주문의 포화 처리량은 상한 없는 동기 3,283–3,320 · 비동기 3,157–3,388건/s로 범위가 겹쳤다. 이벤트 없는 평상시 부하(초당 40건, 방식별 1회)의 요청 → 확정 평균도 동기 4.1ms, 비동기 약 4.3ms로 같았다. 비동기는 처리량을 늘리지도, 평상시 확정을 앞당기지도 않는다
- 측정 중 찾아 고친 것: Tomcat이 503 뒤 연결을 끊어 재연결이 몰리며 초당 4,000건에서 무너지던 문제(→ 429, 붕괴 3/3 → 0/2), 거절이 DB 조회 뒤에 일어나던 결함(→ 트랜잭션 전에 큐 자리부터 예약), 트랜잭션 2개(→ 1개, 커넥션 10개에서 저장 처리량 +16–26%), 트랜잭션마다 붙던 격리 수준 전환 명령(→ 제거, 주문당 명령 9 → 6)
- 범위: 최고 초당 3,000건은 처음 잰 노트북 용량(동기 2,680 · 비동기 3,202건/s) 사이로 정한 실험용 가정이고, 결정 2는 이 가정에서 나온 결과다(서비스에 비동기가 필요하다는 근거는 아니다). 노트북 한 대에서 쟀고, 비동기 회차의 부하기는 202 뒤 결과(SSE·폴링)를 받으러 가지 않았다

### 문제 상황

- 처음에는 이벤트 푸시 직후 60초 동안 일반 주문 10만·20만 건이 몰린다고 가정했다. 하지만 수량 제한이 없으면 서두를 이유가 없어 주문이 수십 분에 퍼진다고 보았고, 그 정도는 이 서버에서 동기로도 충분했다. 순간 몰림은 수량 제한이 있을 때 생기므로 시나리오를 선착순 한정 수량 할인으로 바꿨고, 그래서 재고 정합성을 함께 다룬다
- 선착순 할인은 정각 직후 1–2분에 시도가 몰린다고 가정했다. 최고 초당 3,000건(가정)이면 평상시의 약 75배다
- 지켜야 할 것: 초과 판매 0, 재고 보존, 1인 1회, 몰리는 동안에도 평상시 주문은 영향을 받지 않을 것
- 문제 1: 재고 10만 개는 앱 전체 이벤트 하나의 재고다. 이를 이벤트 재고 행 하나(`promotions.remaining_stock`)에서 차감하면, 어느 가게로 가는 주문이든 모든 할인 주문이 그 행의 잠금을 커밋까지 차례로 기다려 커밋이 하나씩만 된다. 주문은 가게 1,000곳에 흩어지고, 주문 경로는 가게 행을 잠그지 않는다
- 문제 2: 동기 처리에서는 처리량을 넘친 요청이 Tomcat 대기열에 쌓여, 할인 주문뿐 아니라 평상시 주문까지 늦어진다. 넘친 요청을 바로 429로 돌려보내면 늦어지지는 않지만, 재고가 남은 동안 먼저 온 시도를 돌려보내게 된다(측정 전 예측 2만–3만 건). 거절된 사람이 다시 시도하는 동안 나중에 온 사람이 산다

### 고려한 방법

비동기 접수는 2025.07–08에 몰리는 주문을 받으려고 만들었다. 이번에는 그 선택이 필요한지 다시 보려고, 재고 판정과 접수를 나눠 같은 시나리오에서 비교했다.

| 결정 | 방법 | 기대한 점 | 예상한 대가 |
|---|---|---|---|
| 재고 판정 | DB 행 하나 (조건부 차감) | DB가 원자성을 보장해 보상 로직 없음 | 모든 할인 주문이 한 행에서 커밋까지 줄을 섬 |
| | DB 여러 행 (20행) | 경합 약 1/20 | 매진 직전 빈 행을 도는 재시도가 늘 수 있음 |
| | 메모리 번호표 + DB 안전망 | 할인 주문끼리 기다리는 행 없음 | 보상 규칙 필요, 서버 한 대 전제 |
| 접수 | 상한 없는 동기 | 응답 = 확정, 구조가 단순 | 넘친 요청이 Tomcat 대기열에 쌓임 |
| | 빠른 거절 동기 (동시 처리 상한을 넘으면 즉시 429) | 응답 = 확정, 넘친 요청을 바로 돌려보냄 | 재고가 남은 동안에도 거절 (예측 2만–3만 건) |
| | 비동기 (큐 7만 칸) | 넘친 요청을 받아 둠 | 확정이 202 뒤로 미뤄짐, 재시작 시 유실 |

### 선택한 구조 (아래 측정으로 확정)

**1. 재고 판정: 메모리 번호표 + DB 안전망**
- 접수 단계에서 메모리 발급기가 번호표(1–10만)를 준다. 다 나가면 DB에 가지 않고 즉시 409 SOLD_OUT, 같은 사용자의 예약이 있으면 즉시 409 ALREADY_JOINED
- 최종 보증은 DB가 한다. 참여 행의 번호표는 유니크 + 번호표 테이블 외래 키라 메모리에 버그가 있어도 10만 건을 넘을 수 없고, 1인 1회는 참여 기본 키(이벤트, 사용자)가 막는다. 외래 키 검사는 부모인 번호표 행에 공유 락을 잡지만, 주문마다 번호표가 다르고 주문 트랜잭션은 그 행을 고치지 않아 1-1의 데드락처럼 같은 행에서 락이 승격되는 경로가 없다
- 실패한 주문의 번호표는 그 주문이 DB에 확실히 없을 때만 발급기에 돌려준다. 롤백이면 바로 돌려주고, 커밋 결과를 모르면(STATUS_UNKNOWN) 대조기가 참여 행을 확인한 뒤 확정하거나 돌려준다. 커밋된 주문의 번호를 돌려주면 같은 번호가 다시 나가 그 번호를 받은 주문이 실패하기 때문이다(초과 판매는 DB 유니크가 막는다. 같은 이유로 rollbackOnCommitFailure는 켜지 않았다). 그래도 번호가 잘못 돌아가면 그 번호를 받은 다음 주문만 DB 유니크에 걸려 실패하고, 발급기는 그 번호를 다시 내보내지 않는다. 재시작하면 참여 행에서 쓰인 번호와 참여자를 읽어 발급기를 다시 채운다. 결과 모름의 두 경우(실제로 커밋됨·안 됨)는 트랜잭션 매니저가 커밋 예외를 던지게 한 테스트로, 재시작은 메모리 상태를 버리고 다시 읽는 테스트로 확인했다(실제 연결 끊김은 한계 참고)
- 비교한 DB 방식은 행 하나(조건부 차감 UPDATE)와 여러 행(재고를 20행으로 분산, 행 수는 20 한 가지로만 쟀다)이다. 여러 행 경로만 READ COMMITTED를 쓴다. 기본 격리 수준에서는 조건이 안 맞는 빈 행의 잠금이 남아 교착이 실제로 났다

**2. 접수와 저장 분리 (비동기)**
- 접수(요청 스레드, DB 없음): 대기 자리 예약(큐 칸 수 세마포어) → 번호표 예약(메모리 방식만) → 상태 등록(Caffeine, TTL 5분) → 워커 제출 → 202 + Location. DB 방식의 비동기는 재고를 워커가 판정한다
- 저장(워커, 트랜잭션 하나): 검증 SELECT + 주문·메뉴 INSERT + 참여 INSERT. 결과는 불변 상태 객체로 교체해 COMPLETED + 주문 id 또는 FAILED가 함께 보인다
- 큐가 차면 요청 스레드에서 대신 실행하지 않고(CallerRunsPolicy 미사용) 429 + Retry-After 1로 거절한다
- 상태 전달: SSE + 폴링(처리 중 202, 완료 303, 실패 200 + FAILED)

**3. 풀과 큐 크기: 공식에서 출발해 측정으로 확정**

| 값 | 출발점 | 측정 | 확정 |
|---|---|---|---|
| 커넥션 P | 코어 × 2 + 1 ≈ 10 | 워커와 함께 20까지 늘리면 비동기 처리량 +35% (비동기 파일럿) | **20** |
| 저장 워커 k | 커넥션 예산 안 | 규칙: 최대 처리량의 95% 이상인 가장 작은 설정(동기 파일럿과 같은 규칙). P=20·k=20 2,943건/s(최대), P=15·k=15는 93.2%로 미달 | **20** |
| 대기 큐 Q | 저장 처리량 × 허용 지연 30초 × 0.8 | 파일럿 저장 처리량 2,943건/s × 24초 | **70,000칸** |

- 비동기 파일럿 전에 적어 둔 규칙(커넥션 10에서 워커를 늘려 처리량이 멈추는 곳)을 그대로 쓰면, k를 8에서 10으로 늘려도 처리량이 멈춰(2,173 → 2,187건/s) P=10·k=8이었다. 그 규칙은 커넥션을 10 넘게 늘려도 처리량이 늘지 않는다는 동기 파일럿 결과를 전제로 했는데, 비동기에서는 20까지 늘리면 +35%로 틀렸다. 그래서 동기 파일럿과 같은 95% 규칙을 비동기의 P·k 조합 전체에 다시 적용했다

### 측정하며 바꾼 것

**1. 거절이 DB 조회 뒤에 일어나던 결함**
- 발견: 과부하 회차에서 거절 응답도 p95 0.3–0.8초였고, 회차당 거절 로그가 32만–38만 줄 남았다
- 원인: 접수 트랜잭션(커넥션 획득 → 검증 SELECT)을 마친 뒤에야 큐가 찼는지 알았다. 어차피 거절될 요청이 커넥션과 쿼리를 써서 받은 주문까지 느려졌다
- 수정: 트랜잭션 전에 대기 자리를 예약하고 건별 로그를 없앴다. 거절 요청의 쿼리 0회를 테스트로 고정했다(Hibernate 통계)

**2. 트랜잭션 2개 → 1개 (접수의 검증을 워커의 저장 트랜잭션으로 합침)**
- 같은 조건(P=10·k=6, 초당 2,250건)에서 저장 처리량 1,559 → 1,959건/s(+26%), 접수 p95 70.1 → 6.0ms, 주문당 MySQL 명령 15 → 9개. 초당 2,700건에서 P=10의 같은 k끼리 비교하면 +16–18%였다
- 나눈 구성은 접수도 커넥션을 써서, 워커를 늘릴수록 접수가 커넥션을 기다렸다
- 대가: 잘못된 주문도 202를 받은 뒤 FAILED가 된다. 대신 나눈 구성에 있던 틈이 없어졌다. 그 구성은 검증 뒤 큐에서 기다리는 동안(큐가 차면 최대 약 21–24초) 바뀐 상태를 다시 보지 않았다. 검증·접수·저장의 책임은 클래스로 나눠 두고 트랜잭션 경계만 하나로 합쳤다

**3. 거절 응답 503 → 429**
- 발견: 초당 4,000건에서 서버가 응답을 1–5초씩 멈추며 무너졌다. CPU·GC로는 설명되지 않았다
- 원인: Tomcat은 503 응답 뒤 연결을 끊는다. 거절이 초당 800건을 넘자 거절된 클라이언트가 모두 새 연결을 맺어(초당 824–1,051개) 서버가 연결 수립에 매달렸다
- 확인: 초당 4,000건에서 응답 코드만 바꿔 503은 3회 모두 붕괴, 429는 2회 모두 버팀(새 연결 초당 44–45개). 거절이 적은 초당 3,000건에서는 응답 코드에 따른 차이가 없었다
- 이 거절은 서버 쪽 자리 부족이라 HTTP 의미로는 503이 맞고, 429는 "이 클라이언트가 너무 많이 보냈다"는 뜻이다. 그래도 앱이 클라이언트 연결을 직접 받는 구성에서는 503 뒤 끊긴 연결의 재연결이 서버를 무너뜨려 앱은 429로 둔다. 앞에 프록시를 두면 프록시가 클라이언트에 503 + Retry-After로 바꿔 보내는 구성으로 정했다(측정하지 않은 설계)

**4. 격리 수준 지정 제거**
- 일반 주문 경로의 READ COMMITTED 지정이 트랜잭션마다 SET 2개 + SELECT 1개를 붙였다(선착순의 DB 여러 행 경로만은 교착 때문에 READ COMMITTED를 쓴다, 선택한 구조 1). 동기·비동기 경로 모두에서 지정을 빼 주문당 명령 9 → 6개, 접수 p95 6.3–8.3 → 3.2–3.6ms(비동기 일반 주문, 초당 2,000건). 읽기가 검증 SELECT 하나뿐이라 격리 수준 자체의 결과 차이는 없었다

**5. 측정 방법 정정: 동기 용량을 낮게 쟀던 것**
- 처음에는 동기를 closed 가상 사용자 200명으로 재 2,680건/s로 보고, 비동기(3,202건/s)가 19% 많이 저장한다고 봤다. 선착순에서 상한 없는 동기가 비동기와 같은 속도로 매진된 것을 보고 다시 확인하니, Tomcat 바쁜 스레드가 200개 중 평균 68–86개로 서버를 다 채우지 못했다
- 가상 사용자 400명으로 다시 재니 동기 3,283–3,320건/s로 비동기와 범위가 겹쳤다. 결론을 내기 전에 부하가 서버를 포화시켰는지(바쁜 스레드·커넥션)부터 확인하도록 절차를 바꿨다

### 해석과 선택

선착순 측정 전에 저장소에 커밋해 둔 설계 문서([DESIGN-promotion-stock.md, 2026-09-29 커밋 `13159bf`](https://github.com/sunjong0214/order-me-plz/blob/13159bf/benchmark/DESIGN-promotion-stock.md))에는 빠른 거절 동기 · 메모리와 비동기 · 메모리의 차이를 10만 건 확정 5–10초, 429 2만–3만 건으로 예상하고, "동기 용량이 비동기와 비슷하게 나오면 이 시나리오의 핵심 효과는 저장 흡수가 아니라 재고 처리 방식이 된다. 그 경우 결과를 그대로 적는다"고 적어 두었다. 결과는 약 3초와 9,279–15,418건이었고, 포화 용량을 다시 재니 동기 용량이 비동기와 같아 그 경우가 됐다.

**결정 1. 재고 판정: 메모리 번호표 (근거가 가장 강하다)**
- 10만 건 확정 시각의 차이는 동기·비동기가 아니라 재고 방식에서 났다. 비교군·회차마다 순서가 같았다
- DB 방식은 서버가 정했다. DB 행 하나는 커밋이 하나씩만 돼(주문당 fsync 약 4회) 초당 확정 약 1,200건에 묶였다
- 메모리 방식은 10만 번째 시도가 도착하는 정각 + 약 35.8초보다 2–5초 늦었다. 사실상 시도가 들어오는 속도가 정했고, 몰리는 동안 노트북 CPU가 97% 이상(5초 기록)이어서 남은 서버 여유는 크지 않았던 것으로 본다(따로 재지 않음)
- 비동기 + DB 방식은 사용자를 기다리게 한다. 202는 빨라도 확정까지 평균 7.6초(여러 행)·26.1초(행 하나)이고, 매진을 202 뒤 중앙값 10.7초·30.4초에 FAILED로 안다. 비동기 + DB 행 하나는 큐 70,000칸이 차서 시도 4.9–5.2만 건을 429로 돌려보냈고, 확정 p99가 약 59초로 요구(30초)를 넘었다. 비동기를 쓸 거면 재고 판정은 접수 단계에서 끝내야 한다

**결정 2. 접수: 비동기 (우선순위 판단)**
- 판단 순서는 초과 판매 0·재고 보존 → 재고가 남은 동안 거절하지 않음 → 넘친 요청이 요청 스레드를 쥐고 기다리지 않음(문제 2) → 확정 p99 ≤ 30초 → 성공 응답 p95 ≤ 200ms다. 선착순에서는 재고가 남았는데 돌려보내진 사람이 다시 시도하는 동안 나중에 온 사람이 산다. 그래서 이 거절을 응답 지연보다 앞에 두었다
- 이 우선순위는 측정 전에 정한 것이 아니다. 측정 전 요구에는 정합성·응답·확정·평상시 주문 지연만 있었고, 거절은 "넘친 요청을 거절하는가, 큐로 받아 두는가"를 비교하는 항목으로만 두었다. 첫 28회의 1초 기록에서 빠른 거절 동기의 429가 모두 재고가 남은 동안 났다는 것을 확인하고 이 순서를 정했다. 상한 190 추가 측정은 해석을 먼저 정해 두고 쟀다. 매진 전 429가 남으면 이 근거를 유지하고, 0이면 결정 2를 "이 부하에서는 동기로도 충분했고, 비동기는 동기의 동시 처리 한도를 넘는 몰림에 대비한 선택"으로 줄여 쓰기로 했다. 결과는 429가 남는 쪽이었다
- 세 접수 방식의 차이는 넘친 요청을 어디서 기다리게 하느냐였다. 빠른 거절 동기는 기다리게 하지 않고 429로 돌려보냈고, 상한 없는 동기는 요청 스레드(Tomcat 200개)와 Tomcat 대기열에서, 비동기는 스레드 밖의 큐(7만 칸)에서 기다리게 했다
- 빠른 거절 동기는 동시 처리가 상한을 넘는 순간 재고가 남아 있어도 거절한다. 1초 기록상 상한 130의 429는 7회(무효 4회 포함) 모두 재고가 0으로 기록되기 전에 났다(유효 3회: 시도 9,279–15,418건, 평상시 주문 120–208건). 상한을 정정한 용량 기준(약 165)보다도 높은 190으로 올려, 동기에 더 유리한 조건에서 다시 잰 3회도 시도 6,215–13,393건(중앙값 13,312건)과 평상시 주문 85–190건을 매진 전에 거절했다
- 상한 없는 동기는 서버가 거절하지는 않았다. 그러나 넘친 요청이 Tomcat 스레드 200개를 모두 쥐고 기다려(커넥션 대기 최대 179), 할인 주문과 평상시 주문의 응답이 함께 늦어졌다(저장 완료 p95 1.48초, 평상시 주문 0.74초). 확정까지 걸린 시간(평균 0.90초)은 비동기(0.72초)와 비슷했다. 차이는 기다리는 동안 요청이 스레드와 커넥션을 쥐고 있었다는 점이다. 부하기가 가상 사용자 상한에 닿아 4,683–7,758건은 보내지도 못해, 실제 지연은 이보다 길 수 있다
- 비동기는 메모리 판정과 함께 쓸 때 큐(7만 칸)에 받아 두어 매진 전 거절이 0이었고, 바쁜 스레드는 최대 5–37개였다. 서버가 매진 전에 거절하지 않은 구성은 비동기와 상한 없는 동기 둘이었고, 그중 요청 스레드를 묶지 않는 비동기를 골랐다
- 대신 확정은 상한 190 동기가 빨랐다. 요청 → 확정 평균은 0.08초(회차 66–102ms, 상한 130은 0.07초)였고, 비동기는 재전송이 가장 적은 회차에서도 0.31초였다. 이 차이는 처리 속도보다 서버 안에서 기다린 줄의 길이에서 온 것으로 본다. 상한 190 동기는 넘친 요청을 429로 덜어 내 커넥션 대기가 최대 170건이었고, 비동기는 거절하지 않은 만큼 큐에 최대 1,776–3,436건이 쌓였다(거절된 시도는 동기의 확정 평균에 들어 있지 않다). 성공 응답 p95는 200(저장 완료)과 202(접수)로 뜻이 다르고 회차별 네트워크 조건(TCP 재전송)도 달라, 응답 p95로는 우열을 정하지 않는다
- 접수한 주문의 보존은 이 판단 순서에 넣지 못했다. 1-1에서 리뷰 원본의 유실 0을 1순위로 둔 것처럼, 주문도 받은 것을 잃지 않는 것이 맨 앞이어야 한다. 측정한 비동기는 큐가 차면 202 대신 429로 거절하는 구조라 1-1의 ③처럼 받은 뒤 큐 초과로 버리지는 않지만, 메모리 큐라 재시작하면 202를 받고 아직 저장되지 않은 주문이 사라지고 그 번호표는 매진 전이면 뒤에 온 사람이 받는다(동기의 200은 커밋 뒤 응답이다). 그래서 결정 2는 영속 큐(메시지 큐·Outbox)로 바꾼다는 전제의 선택이고, 영속 큐가 접수 지연과 처리량에 주는 비용은 재지 않았다
- 그래서 결정 2는 "측정한 구성(자리가 없으면 바로 거절하는 동기, 상한 없이 기다리는 동기, 비동기) 중 매진 전 거절이 없고 요청 스레드를 묶지 않는 방식을, 확정 속도와 접수 p95 요구보다 우선해 택했다"는 판단이고, 운영에 쓰려면 영속 큐가 전제다. 비동기는 접수 응답을 먼저 돌려줄 뿐 확정이 빠른 것은 아니고, 접수 p95 요구는 유효 3회 중 1회만 충족해 검증을 마치지 못했다. 상한에 닿으면 짧게 기다리게 하는 동기(예: 가상 스레드 + 대기 한도)는 재지 않았다(한계 참고)

**요구 충족 (결정 2에서 확정 속도와 견준 두 구성)**

| 요구 | 비동기 · 메모리 (유효 3회) | 빠른 거절 동기(상한 190) · 메모리 (유효 3회) |
|---|---|---|
| 초과 판매 0 · 재고 보존 | 3/3 | 3/3 |
| 매진 전 거절 (측정 중 더한 기준) | 0 | 시도 6,215–13,393건 · 평상시 주문 85–190건 |
| 성공 응답 p95 ≤ 200ms | 1/3 (565 · 24 · 307ms, 202 접수) | 2/3 (190 · 324 · 178ms, 200 저장 완료) |
| 매진 응답 p95 ≤ 200ms | 0.9–3.8ms | 0.7–1.1ms |
| 확정 | 저장 완료 p99 0.96–2.42초 (≤ 30초) | 응답 = 확정, p99 311–492ms |
| 평상시 주문 p95 ≤ 200ms | 4.9–15.6ms (202 접수, 측정 전체 구간), 거절 0 | 31.6–60.2ms (200 저장 완료), 거절 85–190건 |

- 초과 판매 0과 재고 보존은 31회 모두 지켰다. 1인 1회는 부하 측정에서 시도마다 다른 사용자를 보내 시험하지 않았다. 테스트와 참여 기본 키(이벤트, 사용자)로 보장한다
- 성공 응답 p95는 뜻(200 저장 완료 vs 202 접수)과 회차의 네트워크 조건(재전송 초당 상한 190 1–14건, 비동기 3–78건)이 달라 견주지 않는다. 비동기 + 메모리는 재전송이 가장 적은 회차(초당 3건)에서만 요구를 지켰고, 재전송이 많아진 원인은 확인하지 않았다. 상한 130은 재전송이 적은 한 회차(초당 5건)에서만 154ms로 지켰다
- 비동기의 평상시 주문 값은 접수 응답이라, 같은 큐에서 기다린 확정 지연은 들어 있지 않다(평상시 주문이 섞인 할인 구간의 제출 → 커밋은 평균 0.30–0.71초였고, 평상시 주문만 따로 재지는 않았다). 그래서 "평상시 주문은 영향을 받지 않을 것"은 거절 0까지만 확인했다

**이벤트 없는 평상시 부하**
- 이벤트 없는 평상시 부하(초당 40건)에서는 비동기가 확정을 앞당기지 않는다. 접수 응답은 1.35ms로 동기(4.1ms)보다 빠르지만 확정까지는 약 4.3ms로 같고, 결과를 SSE·폴링으로 받는 시간이 더 붙는다. 비동기는 속도가 아니라 몰리는 순간을 위한 선택이다

### 이전 접근과의 구분

- 초기 구현(2025.07–08)은 접수에서 검증한 뒤 커밋 후 이벤트로 저장을 워커에 넘겼고, 풀이 차면 요청 스레드가 저장을 떠안았다(CallerRunsPolicy). 재측정 전 점검에서 이를 명시적 거절로 바꾸려다, 커밋 후 리스너가 던진 예외는 호출자에게 전달되지 않아 거절해도 202가 나간다는 것을 테스트로 확인했다. 그래서 이벤트 대신 직접 제출 + 명시적 거절로 바꿨다

### 한계 및 후속 개선

**운영 전제**
- 번호표·큐·상태가 프로세스 메모리에 있다. 재시작하면 202를 받은 주문이 유실될 수 있고(초과 판매는 DB 제약이 막는다) 서버 한 대가 전제다. 운영 전에 영속 큐(메시지 큐·Outbox)와 공유 재고 카운터(예: Redis)가 필요하다
- 평상시 주문과 할인 주문이 같은 대기 자리(동시 처리 상한·큐 칸)·워커·커넥션을 쓴다. 그래서 빠른 거절 동기 · 메모리에서는 평상시 주문도 85–208건이 429를 받았고, 비동기에서는 평상시 주문도 같은 큐에서 기다렸다(할인 구간 제출 → 커밋 평균 0.30–0.71초, 평상시 주문만 따로 재지 않음). 둘을 나누는 격벽(대기 자리·워커 분리)은 만들지 않았다
- 검증이 저장 단계에 있어 잘못된 주문도 202 뒤 FAILED가 되므로 클라이언트가 SSE·폴링 결과로 실패를 안내해야 하고, 재시도 때 중복 주문을 막는 멱등 키가 없다

**측정 범위**
- 비동기의 결과 전달(SSE 연결·상태 폴링) 부하는 선착순 측정에 넣지 않았다. 접수한 주문마다 연결이나 요청이 더해지므로, 노트북 CPU가 97% 이상이던 몰림 구간에서는 접수·확정 지연이 늘 수 있다(재지 않음)
- 비동기의 거절 0은 최고 유입 초당 3,000건에서 관찰한 결과다. 이때 큐는 최대 1,776–3,436칸(7만 칸의 5% 이하)만 찼다. 큐가 차면 비동기도 재고와 상관없이 429를 준다. 유입이 저장 처리량을 크게 넘는 몰림은 재지 않았다
- 빠른 거절 동기의 매진 전 429는 최고 유입이 할인 주문 처리량과 거의 같은 이 가정에서, 자리가 없으면 기다리지 않고 바로 거절하는 형태를 상한 130·190으로만 재서 나온 결과다(상한 190에서 바쁜 스레드가 190 이상인 1초 표본은 회차마다 4–16개). Tomcat 스레드가 200이라 상한은 190 위로 거의 올릴 수 없고, 상한을 없앤 끝이 상한 없는 동기다(거절 0, 스레드 200개 모두 사용). 몰림이 더 작으면 빠른 거절 동기도 거절 없이 받을 수 있고, 그러면 결정 2는 "동기의 동시 처리 한도를 넘는 몰림에 대비한 선택"으로 범위가 줄어든다(재지 않음)
- Java 21의 가상 스레드로 동기의 대기 자리를 Tomcat 스레드 200개 밖으로 늘리고 대기 한도를 두는 구성은 재지 않았다. 그 구성에서는 결정 2의 "요청 스레드를 묶지 않음"이라는 비동기의 이점이 줄고, 남는 차이는 응답 시점(저장 완료 vs 접수)과 재시작 유실일 것으로 본다
- k6는 429를 다시 시도하지 않는다. 거절된 사람이 1초 뒤 다시 시도해 샀을지, 그 재시도가 부하를 얼마나 늘렸을지는 재지 않았다
- 번호표의 "결과 모름" 처리는 트랜잭션 매니저가 커밋 예외를 던지게 한 테스트로만 확인했다. 실제로 커밋 도중 연결이 끊길 때 Spring이 어떤 결과를 알리는지는 실행해 보지 않았고, JPA 경로에서는 "롤백됨"으로 알려 번호가 대조 없이 돌아갈 수 있다(라이브러리 코드를 읽은 판단). 그래도 초과 판매는 DB 유니크가 막는다
- 재고 판정 비교의 범위: DB 여러 행은 20행 한 가지만 쟀고, 메모리 방식은 시도가 도착하는 속도에 묶여 서버에 남은 여유를 재지 못했다

**측정 코드·환경**
- 측정 도중 코드 점검에서, 주문 검증의 장바구니 소유·가게 일치 조건이 첫 구현(2025.07)부터 주석 처리돼 남의·다른 가게 장바구니로도 주문되던 결함을 찾아 고치고 회귀 테스트를 더했다([`7732962`](https://github.com/sunjong0214/order-me-plz/commit/7732962)). 모든 회차의 서버는 고치기 전 코드로 쟀다(선착순 회차는 빌드 [`b328abf`](https://github.com/sunjong0214/order-me-plz/commit/b328abf)). 검증 SELECT의 대상 행과 횟수는 같지만, 고친 코드로 다시 재지는 않았다
- 노트북 한 대에 앱과 MySQL이 함께 있고, 부하기는 가상 사용자 4,000개가 상한이다

### 느낀 점

- "비동기는 빠르다"는 가정을 측정이 깼다. 처리량은 같았고, 차이는 넘친 요청이 어디서 기다리느냐였다
- 병목은 처리 방식이 아니라 재고 행 하나였다. 구조를 바꾸기 전에 어디서 줄을 서는지부터 재야 한다

- 비교 상대가 불리하게 잡혀 있으면 선택의 근거가 되지 않는다. 동기의 상한을 낮게 잡힌 130에서 190으로 올려 다시 재도 매진 전 거절은 남았고, 주문 하나의 확정은 두 상한 모두 동기가 더 빨랐다. 그래서 접수 방식은 성능 우위가 아니라 무엇을 먼저 지킬지로 판단했다

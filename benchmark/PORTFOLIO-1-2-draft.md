## 1-2. 주문 접수와 저장을 분리해 순간 유입을 흡수하고, 넘치는 분량은 명시적으로 거절

### 결과 요약

- 동기 주문 API는 저장 커밋까지 기다린 뒤 응답해, 순간 유입이 DB 처리량을 넘으면 대기가 HTTP 연결과 요청 스레드에 그대로 쌓인다
- 검증은 동기로 두고 저장은 전용 워커로 분리했다. 큐 크기를 "허용 저장 지연(30초) × 측정한 저장 처리량"으로 산정해 순간 초과분을 흡수하고, 그 이상은 503 + Retry-After로 즉시 거절한다
- 커넥션·워커·큐 크기는 코어 수 기반 공식에서 출발해 파일럿 측정으로 확정했다 (커넥션 `[P]`, 워커 `[k]`, 큐 `[Q]`)
- 저장 처리량의 2배가 60초간 몰리는 스파이크에서 비동기 접수 p95 `[측정값: S]`ms, 저장 완료 p99 `[측정값: S]`초(한도 30초), 거절 `[측정값: S]`%(예측 약 30%). 같은 조건에서 동기 p95 `[측정값: S]`, 타임아웃 `[측정값: S]`건. **측정 후에만 결과로 확정**
- 평상시에는 비동기의 확정 시간(접수 + 저장)이 동기 응답보다 짧지 않다(`[측정값: B]`). 비동기는 속도가 아니라 피크 대응을 위한 선택이다

### 문제 상황

- 동기 주문은 검증 SELECT와 주문·메뉴 INSERT를 요청 스레드에서 한 트랜잭션으로 끝낸 뒤 응답한다
- 쿠폰 오픈·푸시 발송 직후처럼 수십 초~1분 동안 유입이 저장 처리량을 넘으면, 넘친 요청은 커넥션을 기다리며 HTTP 연결과 Tomcat 스레드를 붙잡는다. 지연이 급증하고, 30초 커넥션 대기 한도를 넘긴 요청은 실패하며, 클라이언트 재시도가 부하를 더한다
- 한 시간씩 이어지는 저녁 피크는 이와 다르다. 지속 유입이 처리량을 넘으면 어떤 구조로도 모두 받을 수 없으므로 용량(A)과 지속 초과(C) 회차로 따로 확인한다
- 목표: 순간 초과분은 허용 지연 안에서 받아 저장하고, 받을 수 없는 분량은 빨리 거절한다

### 요구 수준과 근거

| 요구 | 값 | 근거 (서비스 데이터가 아닌 가정) |
|---|---|---|
| 접수 응답 | 성공 응답 p95 ≤ 200ms | 원 목표(평균 200ms)를 p95로 강화. 응답 시간 기준(0.1초 즉각, 1초 흐름 유지)에 비춰 네트워크 지연을 더해도 1초보다 한참 아래 |
| 저장 완료 | 제출 → 커밋 p99 ≤ 30초 | SSE로 "처리 중"을 보여주는 전제의 대기 한도. 동기 경로의 커넥션 대기 한도(30초)와 같아 "동기라면 실패했을 시점 안에 저장한다"가 비교 기준이 된다. 상태 보관 시간(5분)의 1/10 |
| 초과분 | 즉시 503 + Retry-After | 허용 지연 안에 저장할 수 없는 분량은 받지 않는다 |

### 왜 비동기인가

주문 생성에서 지켜야 할 순서를 주문 원본(접수한 주문의 유실·중복 없음) > 결과 확정 > 피크 대응 > 확정까지의 지연으로 두고 비교했다.

| 기준 | 동기 | 비동기 (현재 구현) |
|---|---|---|
| 주문 원본 | 응답 = 커밋 완료 | 접수 후 메모리 큐에 있어 재시작 시 유실 가능 |
| 결과 확정 | 응답이 곧 결과 | SSE·폴링으로 한 번 더 확인 |
| 피크 대응 | 넘친 요청이 연결·스레드를 붙잡다 타임아웃 | 허용 지연분까지 큐가 흡수하고, 넘치면 즉시 503 |
| 확정까지의 지연 | 응답 시간 | 접수 + 큐 대기 + 저장. 평상시에는 동기보다 짧지 않음 |

비동기가 앞서는 것은 피크 대응 하나이고, 원본 보장에서는 뒤진다. 그래서 선택 근거를 "빠른 응답"이 아니라 "순간 유입 흡수"로 한정하고, 운영 적용 전 영속 큐 전환을 전제 조건으로 둔다. 리뷰(1-1)는 같은 기준으로 동기를 택했다. 리뷰는 작성 응답 지연의 우선순위가 낮아 흡수의 이득이 정합성 대가보다 작았고, 주문은 이벤트 순간의 주문 실패가 곧 매출 손실이라 흡수 자체가 요구가 된다.

| 고려한 방식 | 장점 | 판단 |
|---|---|---|
| 동기 + 커넥션 풀 확장 | 구조 변경 없음 | DB가 동시에 유효하게 처리하는 수(코어 수 기반)를 넘는 커넥션은 처리량을 늘리지 못한다. 파일럿 P1에서 `[측정값: P1]` (원 포폴의 10 → 15 → 20 개선 폭 감소와 같은 현상) |
| 동기 + 동시 처리 제한(벌크헤드) | 과부하 시 빠른 거절 | 순간 초과분을 받아 두지 못하고 전부 거절한다 |
| **비동기 접수 + 메모리 큐** | 초과분을 허용 지연 안에서 흡수하고, 넘치면 503 | **채택.** 재시작 시 큐에 있던 주문 유실 |
| 비동기 접수 + 영속 큐 (메시지 큐·Outbox) | 재시작 후에도 복구 | 이번 구현·측정 범위 밖. 운영 전환 방향 |

### 설계

**접수 경로**
1. 검증: 주문자 상태·가게 영업 여부·장바구니 존재를 단일 조인 쿼리 1회로 확인. 실패는 400. 동기 API와 같은 쿼리·격리 수준(READ_COMMITTED)
2. 상태 등록: UUID로 `PROCESSING` 상태를 TTL 저장소(Caffeine, 5분)에 기록
3. 제출: INSERT 작업을 insert 워커 풀에 제출. 접수 트랜잭션은 SELECT만 하므로 커밋 후 이벤트가 아닌 직접 호출이다. 그래야 거절 예외가 요청 스레드로 전파되어 503이 된다
4. 응답: `202 Accepted` + `Location: /api/v1/order/sse/{uuid}`

**저장 경로 (워커)**
- 새 트랜잭션(REQUIRES_NEW)에서 주문·메뉴 INSERT만 수행한다
- 완료·실패 시 상태 객체를 통째로 교체(불변 record)해 `COMPLETED + orderId` 또는 `FAILED`가 항상 함께 관측된다
- 검증은 접수 시점 1회다. 접수 뒤 가게 영업·사용자 상태가 바뀌어도 저장 단계에서 다시 확인하지 않는다

**풀과 큐 크기: 공식으로 출발해 측정으로 확정**

설정은 시나리오와 무관하게 고정하고, 병목인 DB에서 거꾸로 정했다. 서버는 물리 4코어(논리 8)·RAM 16GB이고 앱과 MySQL이 CPU를 나눠 쓴다.

| 값 | 출발점 | 확정 |
|---|---|---|
| 커넥션 P | HikariCP 공식 `물리 코어 × 2 + 디스크 1` = 9 → 10. 코어보다 조금 많아야 I/O 대기 중에도 CPU가 놀지 않고, 그보다 많으면 경합만 는다 | 동기 포화에서 P = 5 / 10 / 15 / 20을 비교해 최대 처리량의 95%에 도달하는 최소값 `[P]` |
| insert 워커 k | P − 접수 경로 몫(Little의 법칙: 유입률 × 커넥션 점유 시간 ≈ 4~5). 워커의 상한은 코어가 아니라 배정된 커넥션 수다 | 비동기 포화에서 k = 4 / 6 / 8을 비교해 처리량이 더 오르지 않고 접수 p95 ≤ 200ms인 최소값 `[k]`. 이때의 처리량이 저장 처리량 W `[W]` |
| insert 큐 Q | W × 30초 × 0.8. 최대 대기 ≈ Q ÷ W이므로 30초 한도의 상한은 30W이고, 0.8은 스파이크 중 W 변동 여유 | 계산값 `[Q]` |

워커는 core = max로 고정했다. 스레드 풀은 큐가 가득 차야 max까지 늘어나므로 큐가 크면 max 설정이 의미가 없다. 접수 경로 몫의 커넥션을 남겨 두어, 저장이 몰려도 검증 SELECT가 커넥션을 얻을 수 있게 했다.

**동기 API와 같은 것 / 다른 것**

| 항목 | 동기 `POST /api/v1/order` | 비동기 `POST /api/v1/order/async` |
|---|---|---|
| 검증 | validateOrder 1회 | 같음 |
| 저장 | orders 1행 + order_menu N행 | 같음 |
| 격리 수준 | READ_COMMITTED | 같음 |
| DB 커넥션 풀 | HikariCP `[P]` | **같은 풀 공유** |
| INSERT 실행 스레드 | 요청 스레드 | insert 워커 `[k]` |
| 응답이 뜻하는 것 | 저장 완료 | 접수 |
| 유입이 넘칠 때 | 커넥션 대기(최대 30초) 후 실패 | 큐 `[Q]`까지 흡수, 넘치면 503 |

### 포화와 상태 전달

**거절 (백프레셔)**
- 큐가 가득 차면 요청 스레드에서 몰래 실행하지 않고(CallerRunsPolicy 미사용) 상태 엔트리를 지운 뒤 `503 Service Unavailable` + `Retry-After: 1`로 응답한다. 거절 수는 `omp.order.async.rejected` 카운터로 드러낸다
- CallerRunsPolicy를 쓰면 포화 구간에서 Tomcat 스레드가 INSERT를 하게 되어, 202를 돌려준 요청이 실제로는 동기로 처리되고 요청 스레드 격리가 깨진다
- 거절은 검증 SELECT 뒤에 일어나므로 503 요청도 커넥션을 잠시 쓴다. 그래서 거절 응답의 지연도 따로 기록한다

**상태 전달**
- 상태는 SSE 연결 유무와 무관하게 TTL 동안 보관한다. 202를 받은 클라이언트가 SSE에 붙기 전에 작업이 끝나도, 연결 시 현재 상태를 먼저 확인해 `COMPLETED`·`FAILED`를 즉시 전달하고 종료한다
- 폴링 `GET /api/v1/order/async/{uuid}`: 처리 중 202, 완료 303 + `Location: /api/v1/order/{orderId}`, 모르는 uuid 404. 실패는 현재 406인데, 406은 표현 형식 협상 실패라는 뜻이라 맞지 않아 200 + `FAILED` 상태로 바꿀 예정이다
- 상태 전달 방식 비교(Polling / WebSocket / SSE)는 원문 표 유지

(원문 시퀀스 그림 수정: 실제 경로와 Location 헤더, 저장 완료가 SSE 연결보다 먼저 오는 분기, 503 거절 분기 추가)

### 검증 방법

| 항목 | 값 |
|---|---|
| 장비 | 데스크탑 k6(부하기) → 유선 LAN → 노트북 Spring Boot + MySQL (물리 4코어·RAM 16GB) |
| 도구 | k6 `[버전]`, open model. 성능은 3회 중앙값·범위, 오류·거절은 회차별 건수 |
| 서버 | JDK 21 `-Xms2g -Xmx2g`, MySQL `[실제 버전]` 동거, HikariCP `[P]`, insert 워커 `[k]`·큐 `[Q]` |
| 데이터 | users 10만, shops 1천(전부 영업), carts 10만. 회차마다 주문 테이블 초기화 |
| 계측 | k6: 접수·거절 응답별 지연(`order_accepted_duration`·`order_rejected_duration`), 스파이크 구간 태그. 서버: 제출→커밋·큐 대기 Timer(누적 히스토그램), 거절·실패 카운터, 큐 길이·커넥션 대기·Tomcat 스레드 5초 폴링 |
| 저장 완료 판정 | 두 시점의 히스토그램 스냅샷 차이로 구간 분포를 계산한다. 30초 이하 비율 ≥ 99%면 p99 ≤ 30초 충족(30초가 버킷 경계라 정확한 값) |
| 건수 대조 | 접수(202) = 저장 완료 + 저장 실패, 503 = 서버 거절 카운터 증가분. 총건수 대조이며 요청별 대조는 아니다 |
| 측정 범위 | POST 응답과 서버 저장까지. SSE·폴링을 포함한 사용자 흐름은 기능 테스트(`AsyncOrderStatusHttpTest`, SSE 늦은 연결 테스트)로 검증하고 성능은 재지 않는다 |

**파일럿 (본측정 전 1회):** P1에서 커넥션 P를, P2에서 워커 k와 저장 처리량 W를 정한다. W는 이후 모든 부하의 기준이다.

| 회차 | 부하 | 질문 |
|---|---|---|
| B. 평상시 | 0.5W, 15분 × 3 | 평소에는 두 방식 모두 여유가 있는가. 비동기가 치르는 확정 지연은 얼마인가 |
| A. 용량 | 0.6 ~ 1.4W 계단, 4분씩 | 지속 유입의 한계 (저녁 피크) |
| **S. 스파이크** | 0.5W → 5초 만에 2W → 60초 유지 → 0.5W, × 3 | 순간 초과분을 허용 지연 안에서 흡수하고, 넘치는 분량을 거절하고, 회복하는가 |
| C. 지속 초과 | 1.5W, 5분 | 흡수 한도를 넘는 지속 부하에서 어떻게 동작하는가 |

**S 예측 (측정 전 기록):** 큐가 24W이므로 스파이크 시작 약 24초 뒤부터 초과분을 거절하고, 스파이크 요청의 약 30%가 503이 된다. 저장 완료는 최대 약 24초이고, 스파이크 뒤 약 48초에 큐가 빈다. 동기는 지연이 수 초 이상으로 늘고, 30초를 넘긴 요청은 커넥션 대기 타임아웃으로 실패한다.

### 한계 및 후속 개선

- 작업과 상태가 프로세스 메모리에 있어 재시작 시 접수한 주문이 유실될 수 있다. 주문 원본 보장(1순위 요구)을 위해 운영 적용 전 영속 큐(메시지 큐 또는 Outbox)로 전환하는 것이 전제 조건이다
- 흡수량은 "허용 지연 × 처리량"으로 정해진다. 30초분을 넘게 이어지는 초과 유입이나 연속되는 스파이크는 흡수하지 못하고 거절한다
- 검증은 접수 시점 1회다. 접수 후 가게가 닫혀도 저장은 진행된다. 장바구니가 주문자·가게에 속하는지 확인하는 조건도 아직 없다
- 재시도 시 중복 주문을 막는 멱등 키·유니크 제약이 없다
- 유실 판정은 총건수 대조까지다. 누락과 중복이 상쇄될 수 있어 요청별 대조가 후속 과제다
- 거절이 검증 SELECT 뒤에 일어나 503 요청도 커넥션을 쓴다. 과부하가 더 커지면 검증 전에 큐 여유를 먼저 확인하는 방식을 검토한다
- 단일 인스턴스 전제다. 다중 인스턴스에서는 상태 저장소와 SSE 연결이 인스턴스에 묶인다. Graceful Shutdown 시 큐에 남은 작업의 처리 정책도 없다

### 느낀 점

- 빠른 접수는 빠른 확정이 아니다. 비동기는 속도를 높이는 도구가 아니라 순간 유입을 받아 두는 도구이고, 받아 둘 수 있는 양은 허용 지연과 처리량으로 계산해야 한다
- 요구값을 가정으로 명시하고, 측정한 처리량으로 풀과 큐 크기를 계산해 결과를 미리 예측한 뒤 측정으로 확인하는 순서로 설계를 검증했다

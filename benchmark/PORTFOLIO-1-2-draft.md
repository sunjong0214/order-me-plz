# 포트폴리오 1-2 재작성 초안 (2026-09-22)

> 상태: **수치 미기입 초안.** `[측정값: 출처]` 자리는 아래 "검증 방법"의 회차 A~D(open model, 3회 중앙값) 결과로 채운다.

## 1-2. 주문 생성을 접수와 저장으로 분리하고 포화·상태 전달까지 설계

### 결과 요약

- 동기 주문 API는 요청 스레드가 DB INSERT 완료까지 점유되어 유입량이 늘면 응답 시간이 목표 200ms를 넘김
- 검증은 동기로 유지하고 INSERT만 전용 워커 풀로 옮겨 202 Accepted로 접수. 상태는 TTL 저장소에 두고 SSE 또는 폴링으로 전달. 풀 포화는 503 + Retry-After로 명시 거절
- p95 200ms·실패 0을 유지하는 최대 유입률 `[측정값: A sync]` → `[측정값: A async]` req/s. 같은 유입량 `[B rate]` req/s에서 p95 `[측정값: B sync]` → `[측정값: B async]` ms
- 접수(202) `[측정값: C async orders_accepted]`건 = 저장 완료 `[측정값: C completed_orders]`건. 거절 503 `[측정값: C orders_rejected]`건 = 서버 거절 카운터 증가분

### 문제 상황

- 동기 구조에서는 검증 SELECT와 주문·메뉴 INSERT가 요청 스레드에서 한 트랜잭션으로 끝나야 응답. DB 쓰기 지연이 그대로 응답 시간
- 유입량이 늘면 요청 스레드가 커밋 대기에 묶여 p95가 200ms를 넘고, 그 이상에서는 톰캣 스레드·커넥션 대기가 겹쳐 응답이 급격히 늘어남
- 목표: 접수 응답을 200ms 안에 유지하면서 저장 완료·유실·거절을 측정 가능하게 만들기

### 설계

**접수 경로**
1. 검증: 주문자 상태·가게 영업 여부·장바구니 존재를 **단일 조인 쿼리 1회**로 확인. 실패는 400. 동기 API와 같은 쿼리·같은 격리 수준(READ_COMMITTED)
2. 상태 등록: UUID로 `PROCESSING` 상태를 TTL 저장소(Caffeine, 5분)에 기록
3. 제출: INSERT 작업을 `insertTaskExecutor`(core 10 / max 30 / queue 100)에 제출. 접수 트랜잭션은 SELECT만 수행하므로 커밋을 기다릴 데이터가 없어 이벤트가 아닌 직접 호출
4. 응답: `202 Accepted` + `Location: /api/v1/order/sse/{uuid}`

**저장 경로 (워커)**
- 새 트랜잭션(REQUIRES_NEW)에서 주문·메뉴 INSERT만 수행. 검증은 접수 시점에 끝났으므로 재조회 없음
- 완료·실패 시 상태 객체를 통째로 교체(불변 record). `COMPLETED + orderId` 또는 `FAILED`가 항상 함께 관측됨

**동기 API와 같은 것 / 다른 것**

| 항목 | 동기 `POST /api/v1/order` | 비동기 `POST /api/v1/order/async` |
|---|---|---|
| 검증 | validateOrder 1회 | 같음 |
| 저장 | orders 1행 + order_menu N행 | 같음 |
| 격리 수준 | READ_COMMITTED | 같음 |
| DB 커넥션 풀 | HikariCP 20 | **같은 풀 공유** |
| INSERT 실행 스레드 | 요청 스레드 | 워커 스레드 |
| 응답이 뜻하는 것 | 저장 완료 | 접수 |

같은 빌드에 두 엔드포인트가 공존하므로 서버·스키마·JVM을 바꾸지 않고 URL만 바꿔 비교한다. 분리한 것은 **스레드 풀**이고 DB 커넥션 풀은 공유한다.

### 포화와 상태 전달

**포화 시 거절 (백프레셔)**
- 워커 풀이 가득 차면 요청 스레드에서 몰래 실행하지 않고(CallerRunsPolicy 미사용) 접수를 거절한다. 상태 엔트리를 지우고 `503 Service Unavailable` + `Retry-After: 1`
- CallerRunsPolicy를 쓰면 포화 구간에서 톰캣 스레드가 INSERT를 하게 되어 "지연 격리"가 깨지고, 202를 돌려준 요청이 실제로는 동기 처리된다. 거절 건수는 `omp.order.async.rejected` 카운터로 드러낸다
- 503이 나기 시작하는 유입률이 이 구조의 접수 용량이다. 그 아래에서는 202 건수와 저장 행 수가 일치해야 한다

**상태 전달**
- 상태는 SSE 연결 유무와 무관하게 TTL 동안 보관한다. 202를 받은 클라이언트가 SSE에 붙기 전에 작업이 끝나도, 연결 시 현재 상태를 먼저 확인해 `COMPLETED`·`FAILED`를 즉시 전달하고 종료한다
- 폴링 `GET /api/v1/order/async/{uuid}`: 처리 중 202, 완료 303 + `Location: /api/v1/order/{orderId}`, 실패 406, 모르는 uuid 404
- 상태 전달 방식 비교(Polling / WebSocket / SSE)는 원문 표 유지

(원문 시퀀스 그림은 "저장 완료가 SSE 연결보다 먼저 오는 분기"를 추가해 수정)

**해석**
- 동기와 비동기의 **저장 완료 처리량은 같은 DB·같은 커넥션 풀에 묶여 있어 근본적으로 같다.** 비동기가 바꾸는 것은 요청 스레드가 DB 커밋을 기다리지 않는다는 점이고, 그 결과가 A의 접수 용량 차이와 B의 p95 차이다
- 응답 시간의 계약이 다르다. 동기 p95는 저장 완료까지, 비동기 p95는 접수까지다. "저장 속도 개선"이 아니라 "접수 지연 격리"다
- C에서 동기는 `[양상: p95 급증·타임아웃·dropped]`으로 무너지고, 비동기는 `[측정값]`건을 503으로 거절하되 202를 준 요청은 전부 저장됐다. 거절이 카운터와 일치하므로 포화가 관측 가능한 실패로 바뀌었다

### 한계 및 후속 개선

- 작업과 상태가 프로세스 메모리에 있어 서버 종료 시 접수된 주문이 유실될 수 있다. 영속 큐(메시지 큐 또는 Outbox)가 필요하다
- 처리 중 TTL(5분)이 먼저 만료되면 완료 갱신이 무시되고 복구되지 않는다. 큐 대기 시간이 TTL에 근접하는지 D 회차로 확인한다
- 검증은 접수 시점 1회다. 접수 후 가게가 닫히거나 사용자가 차단되어도 저장은 진행된다. 저장 시 재검증 여부는 정책 결정이 필요하다
- 재시도 시 중복 주문을 막는 Idempotency Key·Unique 제약이 없다
- 유실 판정은 총건수 일치까지다. 한 건 누락과 한 건 중복은 상쇄될 수 있어 요청별 대조가 후속 과제다
- 단일 인스턴스 전제. 다중 인스턴스에서는 상태 저장소와 SSE 연결이 인스턴스에 묶인다
- Graceful Shutdown 시 큐에 남은 작업 처리 정책이 없다

### 느낀 점

- 빠른 접수 응답과 실제 저장 완료는 다른 지표라는 것을 이번에는 수치로 분리해 확인했다. 접수량·저장량·거절량·완료 시점을 따로 재야 비동기 구조를 설명할 수 있다
- 포화를 숨기는 정책(CallerRuns)보다 드러내는 정책(503 + 카운터)이 측정과 운영 모두에서 낫다는 것을 배웠다

## 1-2. 선착순 한정 수량 주문: 재고 판정은 메모리 번호표로, 저장은 비동기 큐로 분리해 몰린 요청을 흡수

기간: 비동기 접수 구현 2025.07–08 → 거절 정책·트랜잭션·풀과 큐 재설계, 선착순 재고 설계·검증 2026.08–10

### 결과 요약

- 중소 배달앱(MAU 약 345만) 규모로 선착순 할인을 가정했다: 정각에 재고 10만 개, 시도 약 23만 건(최고 초당 3,000건), 그동안 평상시 주문 초당 40건
- 재고 처리 3방식(DB 행 하나 · DB 여러 행 · 메모리 번호표)과 동기·비동기를 교차한 7개 비교군을 회차당 약 23만 건으로 측정했다. 모든 회차 초과 판매 0
- **결정 1. 재고 판정은 메모리 번호표로 정했다.** 매진 속도는 재고 방식이 정했다: 10만 건 확정까지 DB 행 하나 약 90초 → DB 여러 행 52.5–56.7초 → 메모리 번호표 37.9–41.0초. 같은 재고 방식이면 동기·비동기 차이는 작았다
- **결정 2. 접수는 비동기를 택했다.** 근거는 속도가 아니라 넘친 요청을 다루는 구조다. 동시 처리 상한으로 거절하는 동기는 몰리는 순간 재고가 남아 있어도 시도 9,279–15,418건과 평상시 주문 일부를 429로 돌려보냈고(5회 모두 매진 전), 상한이 없는 동기는 Tomcat 대기열에서 모두 늦어졌다(성공 p95 1.48초, 평상시 주문 p95 0.74초). 비동기는 30초분까지 큐에 받아 두어 거절 0, 평상시 주문 p95 15ms였다
- 메모리 번호표 + 비동기 조합: 10만 건 확정 정각 + 37.9초, 매진 응답 p95 1.4ms, 요청→확정 평균 0.72초(저장 완료 p99 2.4초). 접수 p95 200ms 요구는 네트워크 재전송이 적은 회차에서만 지켰다(24ms, 나머지 두 회차 307·565ms)
- **비동기는 처리량을 늘리지 않는다:** 포화 처리량은 동기 3,283–3,320 · 비동기 3,157–3,388건/s로 같았다. 비동기의 이득은 넘친 요청을 큐에 받아 두어 응답과 평상시 주문을 지키는 데 있다
- 평상시(초당 40건)에는 비동기가 확정을 앞당기지 않는다: 동기 4.1ms, 비동기 약 4.3ms(접수 응답만 1.35ms로 빠름)
- 측정 중 찾아 고친 것: 거절이 DB 조회 뒤에 일어나던 결함(→ 대기 자리 선예약), 트랜잭션 2개(→ 1개, 처리량 +26%), 503이 연결을 끊어 과부하에서 붕괴(→ 429, 붕괴 3/3 → 0/2), 트랜잭션마다 붙던 격리 수준 전환 명령(→ 제거, 주문당 명령 9 → 6)

### 문제 상황

- 선착순 할인은 정각 직후 1–2분에 시도가 몰린다. 최고 초당 3,000건으로 평상시의 약 75배다
- 지켜야 할 것: 초과 판매 0, 1인 1회, 몰리는 동안에도 평상시 주문은 영향을 받지 않을 것
- 문제 1: 재고를 DB 행 하나에서 차감하면 모든 할인 주문이 그 행 잠금에 줄을 서 커밋이 하나씩만 된다
- 문제 2: 동기 처리에서는 처리량을 넘친 요청이 Tomcat 대기열에 쌓여, 할인 주문뿐 아니라 평상시 주문까지 늦어진다

### 설계

**1. 재고 판정: 메모리 번호표 + DB 안전망**
- 접수 단계에서 메모리 발급기가 번호표(1–10만)를 준다. 다 나가면 DB에 가지 않고 즉시 409 SOLD_OUT, 같은 사용자의 예약이 있으면 즉시 409 ALREADY_JOINED
- 최종 보증은 DB가 한다. 참여 행의 번호표는 유니크 + 번호표 테이블 외래 키라 메모리에 버그가 있어도 10만 건을 넘을 수 없고, 1인 1회는 참여 기본 키(이벤트, 사용자)가 막는다
- 번호표를 돌려주는 조건은 "그 주문이 DB에 확실히 없다"뿐이다
- 비교한 DB 방식: 행 하나(조건부 차감 UPDATE), 여러 행(재고를 20행으로 나눠 분산. 이 경로만 READ COMMITTED — 기본 격리 수준에서는 조건이 안 맞는 빈 행의 잠금이 남아 교착이 실제로 났다)

**2. 접수와 저장 분리 (비동기)**
- 접수(요청 스레드, DB 없음): 대기 자리 예약(큐 칸 수 세마포어) → 번호표 예약 → 상태 등록(Caffeine, TTL 5분) → 워커 제출 → 202 + Location
- 저장(워커, 트랜잭션 하나): 검증 SELECT + 주문·메뉴 INSERT + 참여 INSERT. 결과는 불변 상태 객체로 교체해 COMPLETED + 주문 id 또는 FAILED가 함께 보인다
- 큐가 차면 요청 스레드에서 몰래 실행하지 않고(CallerRunsPolicy 미사용) 429 + Retry-After 1로 거절한다
- 상태 전달: SSE + 폴링(처리 중 202, 완료 303, 실패 200 + FAILED)

### 측정하며 바꾼 것

**1. 거절이 DB 조회 뒤에 일어나던 결함**
- 발견: 과부하 회차에서 거절 응답도 p95 0.3–0.8초였고, 회차당 거절 로그가 32만–38만 줄 남았다
- 원인: 접수 트랜잭션(커넥션 획득 → 검증 SELECT)을 마친 뒤에야 큐가 찼는지 알았다. 어차피 거절될 요청이 커넥션과 쿼리를 써서 받은 주문까지 느려졌다
- 수정: 트랜잭션 전에 대기 자리를 예약하고 건별 로그를 없앴다. 거절 요청의 쿼리 0회를 테스트로 고정했다(Hibernate 통계)

**2. 트랜잭션 2개 → 1개**
- 같은 조건(P=10·k=6, 초당 2,250건)에서 저장 처리량 1,559 → 1,959건/s(+26%), 접수 p95 70.1 → 6.0ms, 주문당 MySQL 명령 15 → 9개
- 실제 일(검증 SELECT 1 + INSERT 2)은 같고, 트랜잭션마다 부가 명령이 약 6개 붙었다. 나눈 구성은 접수도 커넥션을 써서 워커를 늘릴수록 접수가 커넥션을 기다렸다
- 대가: 잘못된 주문도 202를 받은 뒤 FAILED가 된다

**3. 거절 응답 503 → 429**
- 발견: 초당 4,000건에서 서버가 응답을 1–5초씩 멈추며 무너졌다. CPU·GC로는 설명되지 않았다
- 원인: Tomcat은 503 응답 뒤 연결을 끊는다. 거절된 클라이언트가 모두 새 연결을 맺어(초당 824–1,051개) 서버가 연결 수립에 매달렸다
- 확인: 응답 코드만 바꿔 503은 3회 모두 붕괴, 429는 2회 모두 버팀(새 연결 초당 44–45개). 앞에 프록시를 두면 클라이언트에 보일 코드는 거기서 바꾼다

**4. 격리 수준 지정 제거**
- 코드의 READ COMMITTED 지정이 트랜잭션마다 SET 2개 + SELECT 1개를 붙였다. 지정을 빼 주문당 명령 9 → 6개, 접수 p95 6.3–8.3 → 3.2–3.6ms. 읽기가 검증 SELECT 하나뿐이라 격리 수준 자체의 결과 차이는 없었다

**5. 측정 방법 정정: 동기 용량을 낮게 쟀던 것**
- 처음에는 동기를 closed 가상 사용자 200명으로 재 2,680건/s(비동기보다 19% 낮음)로 봤다. 선착순에서 빠른 거절 없는 동기가 비동기와 같은 속도로 매진된 것을 보고 다시 확인하니, Tomcat 바쁜 스레드가 200개 중 평균 74–86개로 서버를 다 채우지 못했다
- 가상 사용자 400명으로 다시 재니 동기 3,283–3,320건/s로 비동기와 같았다. 결론을 내기 전에 부하가 서버를 포화시켰는지(바쁜 스레드·커넥션)부터 확인하도록 절차를 바꿨다

### 해석과 선택

**결정 1. 재고 판정: 메모리 번호표 (근거가 가장 강하다)**
- 매진 속도의 차이는 동기·비동기가 아니라 재고 방식에서 났다. DB 행 하나는 커밋이 하나씩만 돼(주문당 fsync 약 4회) 초당 약 1,200건에 묶였고, 메모리 번호표는 할인 주문끼리 기다리는 행이 없다. 비교군·회차마다 순서가 같았다
- 비동기 + DB 방식은 사용자를 기다리게 한다. 202는 빨라도 확정까지 평균 7.6초·26.1초이고, 매진을 202 뒤 10.7초·30.4초에 FAILED로 안다. 비동기를 쓸 거면 재고 판정은 접수 단계에서 끝내야 한다

**결정 2. 접수: 비동기 (근거를 구조적인 차이로 한정한다)**
- 같은 메모리 방식에서 세 접수 방식의 매진 속도는 비슷했다(비동기 37.9초, 상한 없는 동기 39.1초, 빠른 거절 동기 41.0초). 차이는 넘친 요청을 다루는 방식이다
- 상한 없는 동기는 넘친 요청이 Tomcat 대기열에 쌓여 모두가 늦어졌다(성공 p95 1.48초, 평상시 주문 0.74초)
- 빠른 거절 동기는 응답은 비슷했지만(가장 깨끗한 회차 성공 p95 154ms), 동시 처리가 상한을 넘는 순간 재고가 남아 있어도 거절한다. 429는 5회 모두 매진 전에 났다(시도 9,279–15,418건, 평상시 주문 120–208건). 먼저 온 사람을 돌려보내고 나중 온 사람이 사는 선착순 순서의 역전이고, 거절된 사람은 다시 시도해야 한다. 이 거절은 상한 값과 상관없는 구조이고, 상한 값은 거절 수만 바꾼다(선착순은 상한 130으로만 쟀다)
- 비동기는 30초분까지 큐에 받아 두어 거절 0, 평상시 주문 p95 15ms였고 매진도 약 3초 빨랐다

**응답 요구 충족**
- 비동기 + 메모리는 네트워크 재전송이 적었던 회차(초당 3건)에서 모든 요구를 지켰고(접수 p95 24ms, 저장 완료 p99 0.96초), 재전송이 초당 75–78건이던 두 회차는 접수 p95 307·565ms로 200ms를 넘었다. 선택의 근거는 응답 속도가 아니라 거절 0과 평상시 주문 보호다

**평상시**
- 평상시(초당 40건)에는 비동기가 확정을 앞당기지 않는다. 접수 응답은 1.35ms로 동기(4.1ms)보다 빠르지만 확정까지는 약 4.3ms로 같고, 결과를 SSE·폴링으로 받는 시간이 더 붙는다. 비동기는 속도가 아니라 몰리는 순간을 위한 선택이다

### 한계 및 후속 개선

- 번호표·큐·상태가 프로세스 메모리에 있다. 재시작하면 접수한 주문이 유실될 수 있고 서버 한 대가 전제다. 운영 전에 영속 큐(메시지 큐·Outbox)와 공유 재고 카운터(예: Redis)가 필요하다
- 검증이 저장 단계에 있어 잘못된 주문도 202 뒤 FAILED가 된다. 클라이언트는 SSE·폴링 결과로 실패를 안내해야 한다
- 빠른 거절 동기는 선착순에서 상한 130(낮게 잡힌 값)으로만 쟀다. 상한을 올리면 거절 수는 줄 수 있지만, 상한을 넘는 순간 재고가 남아도 거절하는 구조는 같다. 용량 측정에서 상한 190은 3,086–3,191건/s로 비동기와 비슷한 처리량을 냈다
- 접수 p95 ≤ 200ms 요구는 유효 3회 중 1회만 지켰다. 재전송이 많은 시간대의 회차는 307–565ms였고, 원인(공유기·USB 랜 어댑터 등 네트워크 쪽)은 확인하지 않았다
- 재시도 때 중복 주문을 막는 멱등 키가 없다
- 노트북 한 대에 앱과 MySQL이 함께 있고, 부하기는 가상 사용자 4,000개가 상한이다

### 느낀 점

- "비동기는 빠르다"는 가정을 측정이 깼다. 처리량은 같았고, 차이는 넘친 요청이 어디서 기다리느냐였다
- 병목은 처리 방식이 아니라 재고 행 하나였다. 구조를 바꾸기 전에 어디서 줄을 서는지부터 재야 한다
- 처음 잰 동기 용량이 틀린 것은 부하가 서버를 다 채우지 못해서였다. 숫자를 믿기 전에 그 숫자가 무엇을 쟀는지부터 확인해야 한다

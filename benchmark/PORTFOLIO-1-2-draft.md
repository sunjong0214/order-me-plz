## 1-2. 주문 생성을 접수와 저장으로 분리하고 포화·상태 전달까지 설계

### 결과 요약

- 동기 주문 API는 검증과 저장 트랜잭션 커밋이 끝난 뒤 응답한다. 비동기 API는 검증 후 저장 작업 제출이 성공하면 접수 응답을 반환한다
- 검증은 동기로 유지하고 INSERT만 전용 워커 풀로 옮겨 202 Accepted로 접수. 202는 주문 저장 완료가 아니라 작업 접수를 뜻한다. 상태는 TTL 저장소에 두고 SSE 또는 폴링으로 전달. 풀 포화는 503 + Retry-After로 명시 거절
- p95 200ms·실패 0을 유지하는 최대 유입률 `[측정값: A sync]` → `[측정값: A async]` req/s. 같은 유입량 `[B rate]` req/s에서 p95 `[측정값: B sync]` → `[측정값: B async]` ms
- 접수(202) `[측정값: C async orders_accepted]`건, 저장 완료 `[측정값: C completed_orders]`건. 거절 503 `[측정값: C orders_rejected]`건 = 서버 거절 카운터 증가분. 접수·저장 총건수 일치는 요청별 유실·중복이 없다는 증명은 아니다

### 문제 상황

- 동기 구조에서는 검증 SELECT와 주문·메뉴 INSERT가 요청 스레드에서 한 트랜잭션으로 끝나야 응답. DB 쓰기 지연이 그대로 응답 시간
- 유입량이 늘면 요청 스레드가 저장과 커밋 완료까지 기다리므로 p95가 200ms를 넘을 수 있다. Tomcat 스레드나 DB 커넥션 대기가 주된 원인인지는 서버 지표와 함께 확인한다
- 목표: 접수 응답을 200ms 안에 유지하면서 저장 완료·유실·거절을 측정 가능하게 만들기

### 응답 계약과 선택 이유

- 동기 API의 200 응답은 주문 저장 트랜잭션이 커밋된 뒤 반환된다. 비동기 API의 202 응답은 입력 검증을 통과하고 저장 작업이 실행기에 제출됐다는 뜻이며, 주문 저장 성공을 뜻하지 않는다. 작업은 이후 `COMPLETED + orderId` 또는 `FAILED`로 종료 상태를 갖는다. 실행기 포화로 제출하지 못한 요청은 작업 접수로 취급하지 않고 503으로 거절한다.
- 동기 처리는 완료 결과가 즉시 필요할 때 단순하지만 요청 응답이 저장 지연을 그대로 기다린다. 메모리 실행기 방식은 접수 지연과 작업 큐를 분리하고 과부하를 503으로 드러내기 쉽지만, 프로세스 재시작 때 작업을 잃을 수 있다. 영속 메시지 큐나 Outbox는 재시작 뒤 복구 가능한 방향이지만 이번 구현·측정 범위에는 들어가지 않았다.
- 따라서 이번 비교의 주장은 저장 속도 향상이 아니라 **비동기 API가 작업 접수 응답을 얼마나 낮은 지연으로 유지하는지, 그 동안 저장 완료와 거절이 어떻게 되는지**로 한정한다.
### 설계

**접수 경로**
1. 검증: 주문자 상태·가게 영업 여부·장바구니 존재를 **단일 조인 쿼리 1회**로 확인. 실패는 400. 동기 API와 같은 쿼리·같은 격리 수준(READ_COMMITTED)
2. 상태 등록: UUID로 `PROCESSING` 상태를 TTL 저장소(Caffeine, 5분)에 기록
3. 제출: INSERT 작업을 `insertTaskExecutor`(core 10 / max 30 / queue 100)에 제출. 접수 트랜잭션은 SELECT만 수행하므로 커밋을 기다릴 데이터가 없어 이벤트가 아닌 직접 호출
4. 응답: `202 Accepted` + `Location: /api/v1/order/sse/{uuid}`

**저장 경로 (워커)**
- 새 트랜잭션(REQUIRES_NEW)에서 주문·메뉴 INSERT만 수행. 검증은 접수 시점에 끝났으므로 재조회 없음
- 완료·실패 시 상태 객체를 통째로 교체(불변 record). `COMPLETED + orderId` 또는 `FAILED`가 항상 함께 관측됨
- 검증과 INSERT 사이에는 시간 간격이 있으므로 가게 영업·사용자 상태가 접수 뒤 바뀌어도 저장 단계에서 다시 확인하지 않는다. 이는 현재 구현의 의미이며 정책상 허용 여부를 별도로 판단해야 한다

**동기 API와 같은 것 / 다른 것**

| 항목 | 동기 `POST /api/v1/order` | 비동기 `POST /api/v1/order/async` |
|---|---|---|
| 검증 | validateOrder 1회 | 같음 |
| 저장 | orders 1행 + order_menu N행 | 같음 |
| 격리 수준 | READ_COMMITTED | 같음 |
| DB 커넥션 풀 | HikariCP 20 | **같은 풀 공유** |
| INSERT 실행 스레드 | 요청 스레드 | 워커 스레드 |
| 응답이 뜻하는 것 | 저장 완료 | 접수 |

같은 빌드에 두 엔드포인트가 공존하므로 서버·스키마·JVM을 바꾸지 않고 URL만 바꿔 비교한다. 분리한 것은 **스레드 풀**이고 DB 커넥션 풀은 공유한다.

### 포화와 상태 전달

**포화 시 거절 (백프레셔)**
- 워커 풀이 가득 차면 요청 스레드에서 몰래 실행하지 않고(CallerRunsPolicy 미사용) 접수를 거절한다. 상태 엔트리를 지우고 `503 Service Unavailable` + `Retry-After: 1`
- CallerRunsPolicy를 쓰면 포화 구간에서 톰캣 스레드가 INSERT를 하게 되어 "지연 격리"가 깨지고, 202를 돌려준 요청이 실제로는 동기 처리된다. 거절 건수는 `omp.order.async.rejected` 카운터로 드러낸다
- 503이 나타나는 구간은 실행기 포화가 관측된 구간이다. 접수 용량은 특정 순간의 첫 503만으로 단정하지 않고, 측정 조건과 지속 유입률, p95, 다른 오류, dropped iterations, 저장 완료 결과를 함께 보고 표현한다

**상태 전달**
- 상태는 SSE 연결 유무와 무관하게 TTL 동안 보관한다. 202를 받은 클라이언트가 SSE에 붙기 전에 작업이 끝나도, 연결 시 현재 상태를 먼저 확인해 `COMPLETED`·`FAILED`를 즉시 전달하고 종료한다
- 폴링 `GET /api/v1/order/async/{uuid}`: 처리 중 202, 완료 303 + `Location: /api/v1/order/{orderId}`, 실패는 현재 구현에서 406, 모르는 uuid 404. 406은 보통 응답 표현 형식 협상 실패를 뜻하므로 작업 실패 표현으로는 의미가 맞지 않는다. 문서화한 현재 동작과 별개로 API 계약은 200 응답의 `FAILED` 상태 표현 등으로 바로잡는 것이 적절하다
- 상태 전달 방식 비교(Polling / WebSocket / SSE)는 원문 표 유지

(원문 시퀀스 그림은 "저장 완료가 SSE 연결보다 먼저 오는 분기"를 추가해 수정)

**해석**
- 동기와 비동기는 같은 DB와 Hikari 풀을 공유하지만, 요청·워커의 동시성, 커넥션 점유 시간, 트랜잭션 경계가 달라 저장 완료 처리량이 같다고 미리 단정할 수 없다. 저장 완료량과 완료 관측 시각을 결과로 비교한다. 비동기의 설계 목적은 요청 스레드가 DB 커밋을 기다리지 않게 해 접수 응답 지연을 분리하는 것이다
- 응답 시간의 계약이 다르다. 동기 p95는 저장 완료까지, 비동기 p95는 접수까지다. "저장 속도 개선"이 아니라 "접수 지연 격리"다
- C에서 동기는 `[양상: p95 급증·타임아웃·dropped]`을 보이고, 비동기는 `[측정값]`건을 503으로 거절했다. 202 수와 완료 건수가 일치하면 총건수 기준으로 일치한 것이며, 요청별 저장 검증은 별도 과제다. 거절 수와 카운터 증가분이 일치하면 실행기 포화가 계측됐다고 해석한다

### 한계 및 후속 개선

- 작업과 상태가 프로세스 메모리에 있어 서버 종료 시 접수된 주문과 상태가 유실될 수 있다. 주문 원본 데이터가 사라질 수 있으므로 운영 환경에서는 영속 큐(메시지 큐 또는 Outbox)와 재처리 기준을 마련해야 한다
- 처리 중 TTL(5분)이 먼저 만료되면 완료 갱신이 무시되고 복구되지 않는다. 현재 5초 폴링은 전체 큐가 비었는지 관측할 뿐 개별 작업의 접수 후 대기 시간을 재지 않는다. TTL 여유를 검증하려면 작업별 접수·시작·완료 시각을 계측해야 한다
- 검증은 접수 시점 1회다. 접수 후 가게가 닫히거나 사용자가 차단되어도 저장은 진행된다. 저장 시 재검증 여부는 정책 결정이 필요하다
- 재시도 시 중복 주문을 막는 Idempotency Key·Unique 제약이 없다
- 유실 판정은 총건수 일치까지다. 한 건 누락과 한 건 중복은 상쇄될 수 있어 요청별 대조가 후속 과제다
- 단일 인스턴스 전제. 다중 인스턴스에서는 상태 저장소와 SSE 연결이 인스턴스에 묶인다
- Graceful Shutdown 시 큐에 남은 작업 처리 정책이 없다

### 느낀 점

- 빠른 접수 응답과 실제 저장 완료는 다른 지표라는 것을 이번에는 수치로 분리해 확인했다. 접수량·저장량·거절량·완료 시점을 따로 재야 비동기 구조를 설명할 수 있다
- 포화를 숨기는 정책(CallerRuns)보다 드러내는 정책(503 + 카운터)이 측정과 운영 모두에서 낫다는 것을 배웠다

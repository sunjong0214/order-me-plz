## 1-2. 이벤트 순간 유입을 흡수하도록 주문 접수와 저장을 분리하고, 넘치는 분량은 연결을 끊지 않고 즉시 거절

기간: 비동기 접수 구현 2025.07~08 → 거절 정책·트랜잭션 구성·풀과 큐 크기 재설계와 검증 2026.08~09

### 결과 요약

- 중소 배달앱 규모(MAU 약 345만)를 가정해 목표를 정했다: 평상시 저녁 피크 초당 약 40건, 쿠폰 이벤트 직후 60초에 10만·20만 명(초당 약 1,707·3,373건)
- 동기 주문은 커넥션을 10개 넘게 늘려도 초당 약 2,360건에서 멈췄다(노트북 CPU 포화). 20만 명 이벤트는 동기 용량의 약 1.4배다
- 저장을 전용 워커로 분리하고 대기 큐를 "허용 저장 지연 30초 × 측정한 저장 처리량"(70,000칸)으로 산정했다. 20만 명 이벤트에서 비동기 접수 p95 `[측정값: S]`ms, 저장 완료 p99 `[측정값: S]`초, 거절 `[측정값: S]`건. 같은 조건에서 동기 `[측정값: S]`, 동기 + 빠른 거절 `[측정값: S]`
- 측정 중 세 가지를 찾아 고쳤다
  - 거절이 DB 조회 뒤에 일어나던 결함 → 대기 자리 선예약
  - 트랜잭션 2개 구성(주문당 MySQL 명령 15개) → 1개(9개)로 바꿔 처리량 +26%
  - 503 응답이 연결을 끊어 과부하에서 서버가 무너짐 → 429로 바꿔 붕괴 3회 중 3회 → 2회 중 0회
- 평상시에는 비동기가 빠르지 않다(`[측정값: B]`). 비동기는 속도가 아니라 이벤트 순간 대응을 위한 선택이다

### 문제 상황

- 동기 주문은 요청 스레드에서 검증 SELECT와 주문·메뉴 INSERT를 한 트랜잭션으로 끝낸 뒤 응답한다
- 중소 앱은 평소 초당 수십 건이라 서버 한 대로 충분하지만, 선착순 쿠폰·푸시 직후에는 40~85배가 몰린다. 드문 순간을 위해 평소 서버를 늘려 둘 수 없다
- 동기에서 처리량을 넘친 요청은 Tomcat 대기열에 쌓인다. 지연이 늘고, 기다리다 떠난 요청은 받지 못한 주문이 된다
- 목표: 이벤트 순간의 초과분은 허용 지연 안에서 받아 저장하고, 받을 수 없는 분량은 빨리 거절한다

### 목표치와 요구 수준

서비스 데이터가 아니라 공개 자료로 계산한 가정이다.

| 항목 | 값 | 근거 |
|---|---|---|
| 규모 | MAU 약 345만 명 | 땡겨요 수준(와이즈앱·리테일 2025년 10월) |
| 평상시 (저녁 피크 1시간) | 초당 약 40건 | 월 주문 = MAU × 5건(배민 월 1억 건 ÷ MAU 약 2천만 비율 가정), 17~21시에 70%, 피크는 평균의 1.5배 |
| 이벤트 (60초) | 10만 명 초당 약 1,707건 / 20만 명 초당 약 3,373건 | 평상시 + 참여자 ÷ 60초. 참여자 = MAU의 약 3% / 6%(근거 데이터가 없어 두 단계 모두 잰다) |
| 접수 응답 | 성공 응답 p95 ≤ 200ms | 원 목표(평균 200ms)를 p95로 강화. LAN에서 잰 서버 측 값 |
| 저장 완료 | 제출 → 커밋 p99 ≤ 30초 | SSE로 "처리 중"을 보여 주는 전제의 대기 한도. 동기 경로의 커넥션 대기 한도(30초)와 같다 |
| 초과분 | 즉시 429 + `Retry-After: 1` | 허용 지연 안에 저장할 수 없는 분량은 받지 않는다 |

### 왜 비동기인가

주문에서 지킬 순서를 주문 원본(유실·중복 없음) > 결과 확정 > 이벤트 순간 대응 > 확정까지의 지연으로 두고 비교했다.

| 방식 | 이벤트 순간 | 판단 |
|---|---|---|
| 동기 + 커넥션 확장 | 처리량이 초당 약 2,360건에서 멈춤(P1) | 커넥션이 병목이 아니다 |
| 동기 + 빠른 거절(동시 처리 상한) | 처리량을 넘는 분량은 전부 거절 | 비교군으로 측정. 받아 둘 수 없다 |
| **비동기 접수 + 메모리 큐** | 30초분까지 받아 두고, 넘치면 즉시 거절 | **채택.** 재시작 시 큐의 주문이 유실될 수 있다 |
| 비동기 + 영속 큐(메시지 큐·Outbox) | 위와 같고 재시작 후 복구 | 이번 범위 밖. 운영 전환 방향 |

비동기가 앞서는 것은 이벤트 순간 대응 하나이고 원본 보장에서는 뒤진다. 그래서 선택 근거를 "빠른 응답"이 아니라 "순간 유입 흡수"로 한정하고, 운영 전 영속 큐 전환을 전제 조건으로 둔다.

### 설계

**접수 (요청 스레드, DB를 쓰지 않음)**
1. 대기 자리 예약: 큐 칸 수만큼의 세마포어에서 자리를 먼저 잡는다. 없으면 DB에 가지 않고 즉시 429
2. 상태 등록: UUID로 `PROCESSING` 상태를 TTL 저장소(Caffeine, 5분)에 기록
3. 제출: 저장 작업을 워커 풀에 넘긴다. 자리는 워커가 작업을 꺼낼 때 반납한다
4. 응답: `202 Accepted` + `Location: /api/v1/order/sse/{uuid}`

**저장 (워커, 트랜잭션 하나)**
- 새 트랜잭션(REQUIRES_NEW, DB 기본 격리 수준)에서 검증 SELECT와 주문·메뉴 INSERT를 함께 한다. 동기 API와 같은 쿼리·격리 수준이다. 처음에는 READ COMMITTED를 지정했지만, 읽기가 검증 한 번뿐이라 결과가 같고 트랜잭션마다 전환 명령만 붙어 기본값으로 되돌렸다(비교 `[측정값: ISO]`)
- 결과는 상태 객체를 통째로 교체해(불변 record) `COMPLETED + orderId` 또는 `FAILED`가 항상 함께 보인다
- 관심사 분리는 코드 구조로 유지한다: 검증(`OrderValidator`), 자리 관리(`AsyncOrderAdmission`), 제출(`AsyncOrderHandler`), 저장(`AsyncOrderProcessor`). 트랜잭션 경계만 저장 단계 하나로 둔다

**거절**
- 큐가 차면 요청 스레드에서 몰래 실행하지 않는다(CallerRunsPolicy 미사용). 202를 돌려준 요청을 Tomcat 스레드가 INSERT하면 요청 스레드 격리가 깨지기 때문이다
- 429 + `Retry-After: 1`로 응답하고 거절 수는 카운터로 드러낸다. 503을 쓰지 않는 이유는 아래 "측정하며 바꾼 것" 3번

**상태 전달**
- 상태는 SSE 연결과 무관하게 TTL 동안 보관한다. SSE 연결 전에 작업이 끝나도 연결 시 현재 상태를 먼저 전달한다
- 폴링 `GET /api/v1/order/async/{uuid}`: 처리 중 202, 완료 303 + 주문 Location, 실패 200 + `FAILED`, 모르는 uuid 404

| 값 | 출발점 | 측정 | 확정 |
|---|---|---|---|
| 커넥션 P | HikariCP 공식 코어 × 2 + 1 ≈ 10 | 동기 포화: P=10부터 CPU 포화로 처리량 평탄(P1). 비동기: 워커와 함께 늘리면 +35%(P2) | **20** |
| 저장 워커 k | 커넥션 예산 안에서 | 워커를 늘릴수록 처리량이 늘었다(P=10에서는 k=8~10에서 정체, P와 함께 20까지 늘리면 증가). 동시 커밋이 많을수록 주문당 디스크 기록이 줄어드는 경향(초당 3,000건에서 k=10 1.21회 → k=20 0.32~0.35회) | **20** (= P) |
| 대기 큐 Q | 저장 처리량 W × 30초 × 0.8 | W ≈ 2,943건/s | **70,000칸** (최대 대기 약 24초) |

규칙은 "최대 평균 처리량의 95% 이상인 가장 작은 설정"이다. P=15·k=15는 93.2%로 미달해 P=20·k=20을 골랐다.

### 측정하며 바꾼 것

**1. 거절이 DB 조회 뒤에 일어나던 결함**
- 발견: 과부하 회차에서 거절 응답(503)도 p95 0.3~0.8초였다. 회차당 거절 WARN 로그가 32만~38만 줄 남았다
- 원인: 접수 트랜잭션(커넥션 획득 → 검증 SELECT)을 마친 뒤에야 큐가 찼는지 알았다. 어차피 거절될 요청이 커넥션과 쿼리를 써서 받은 주문까지 느려졌다
- 수정: 트랜잭션 전에 대기 자리를 예약하고 건별 로그를 없앴다. 거절 요청의 쿼리 0회를 테스트로 고정했다(Hibernate 통계)

**2. 트랜잭션 구성: 2개 → 1개**
- 처음에는 "접수 트랜잭션에서 검증 → 워커 트랜잭션에서 저장"으로 나눴다(관심사 분리 목적)
- 같은 조건(P=10·k=6, 초당 2,250건)에서 비교했다

| 구성 | 저장 처리량 | 접수 p95 | 주문당 MySQL 명령 (COMMIT / SET) |
|---|---|---|---|
| 나눔 (`split`) | 1,559건/s | 70.1ms | 15개 (2 / 8) |
| **하나 (`single`)** | **1,959건/s (+26%)** | **6.0ms** | **9개 (1 / 4)** |

- 실제 일(검증 SELECT 1 + INSERT 2)은 같고, 트랜잭션마다 부가 명령(격리 수준 설정·조회·복원, autocommit 전환, COMMIT)이 약 6개 붙었다. 나눈 구성은 접수도 커넥션을 써서 워커를 늘릴수록 접수가 커넥션을 기다렸다
- 나눈 구성의 장점은 잘못된 주문을 즉시 400으로 알리는 것 하나였고, 검증과 저장 사이(큐 대기 최대 약 24초)에 바뀐 상태를 다시 확인하지 않는 틈이 있었다. 하나로 합친 대가는 잘못된 주문도 202를 받은 뒤 `FAILED`가 된다는 것이다

**3. 거절 응답: 503 → 429**
- 발견: 초당 4,000건에서 서버가 응답을 1~5초씩 멈추며 무너졌다. CPU·GC(멈춤 최대 82ms)로는 설명되지 않았다
- 원인: Tomcat은 503 응답 뒤 연결을 끊는다. 거절이 초당 약 1,000건이면 거절된 클라이언트가 전부 새 연결을 맺어, 서버가 주문 대신 연결 수립에 매달렸다
- 확인: 부하·설정은 그대로 두고 응답 코드만 바꿔 쟀다

| 거절 응답 (초당 4,000건) | 새 TCP 연결/s | TCP 재전송/s | 결과 |
|---|---|---|---|
| 503 (연결 대기열 1,000 포함) | 824~1,051 | 1,163~1,264 | 3회 모두 붕괴 (p95 약 1.2초, p99 약 4.8초) |
| **429** | **44~45** | 79~538 | **2회 모두 버팀** (저장 2,894~2,914건/s) |

- 적용: 앱은 연결을 유지하는 429로 거절한다. 앞에 Nginx·게이트웨이를 두면 클라이언트에 보일 코드(503)는 거기서 바꿔 준다(`error_page 429 =503`). 이 경우에도 앱이 503을 보내면 프록시↔앱 연결이 끊기므로 앱은 429가 맞다(설계 판단, 측정하지 않음)

| 항목 | 값 |
|---|---|
| 장비 | 데스크탑 k6(부하기) → 유선 100Mbps → 노트북 Spring Boot + MySQL 8.0.37 (i7-1165G7, RAM 16GB) |
| 통제 | 회차마다 직전 부하 후 15분 휴식, 충전기 연결 확인, 노트북 클럭·CPU 5초 기록. 부하기 CPU 평균 80% 미만 |
| 절차 | 서버 재시작 → 워밍업 1분(버림) → 큐 소진 → 주문 테이블 초기화 → 측정 → 큐 소진 → DB 건수 대조 |
| 계측 | k6: 응답 종류별 지연, 스파이크 구간 태그. 서버: 제출→커밋 누적 히스토그램, 거절·실패 카운터, 큐·커넥션·스레드 5초 폴링 |
| 대조 | 접수(202) = 저장 + 저장 실패, 거절(429) = 서버 거절 카운터 증가분 |

|---|---|---|---|
| **S-20만** (헤드라인) | 초당 40건 → 5초 만에 3,373건 → 55초 유지 → 40건, 관찰 5분 | 동기 용량을 넘는 이벤트를 받아 30초 안에 저장하는가 | 동기·동기 + 빠른 거절·비동기 각 3회 |

| B. 평상시 | 초당 40건 15분 | 비동기가 평소에 치르는 비용(확정 시간) | 방식별 3회 |
| A. 용량 | 저장 처리량의 0.6~1.4배 계단 | 목표 대비 여유 | 1회 |

**비교군 "동기 + 빠른 거절":** "동기도 넘치는 요청을 빨리 거절하면 되지 않나"에 답하려고 넣었다. 동시에 처리하는 동기 주문이 120개(동기 처리량 약 2,360건/s × 허용 대기 50ms)를 넘으면 트랜잭션 전에 즉시 429로 거절한다. 커넥션 대기 시간(Hikari `connection-timeout`)으로는 거절이 일어나지 않았다. 동기 요청은 Tomcat 스레드(200개)를 먼저 잡고 들어오므로 커넥션을 기다리는 요청이 많아야 180개이고, 그 줄은 약 76ms에 빠져 최솟값 250ms에 닿지 않는다.

### 한계 및 후속 개선

- 작업과 상태가 프로세스 메모리에 있어 재시작 시 접수한 주문이 유실될 수 있다. 운영 전 영속 큐(메시지 큐·Outbox) 전환이 전제 조건이다
- 검증이 저장 단계에 있어 잘못된 주문도 202를 받고 나중에 `FAILED`가 된다. 클라이언트는 SSE·폴링 결과로 실패를 안내해야 한다
- 저장 처리량이 회차마다 약 8% 흔들린다(커밋 묶음). 여러 주문을 한 트랜잭션으로 저장하는 배치 저장은 편차와 처리량을 개선할 수 있지만, 목표 대비 여유가 커서 보류했다
- 재시도 시 중복 주문을 막는 멱등 키가 없다. 클라이언트는 `Retry-After`에 무작위 지연을 더해 재시도가 한순간에 몰리지 않게 해야 한다
- 429는 4xx라 서버 오류율(5xx) 대시보드에 과부하가 안 보인다. 거절 카운터를 따로 본다
- 노트북 한 대에 앱과 MySQL이 함께 있고, 부하기는 VU 4,000개가 상한이다. 단일 인스턴스 전제라 다중 인스턴스에서는 상태 저장소와 SSE 연결이 인스턴스에 묶인다

### 느낀 점

- 빠른 접수는 빠른 확정이 아니다. 비동기는 속도를 높이는 도구가 아니라 순간 유입을 받아 두는 도구이고, 받아 둘 양은 허용 지연과 처리량으로 계산해야 한다
- 측정은 설계를 확인하는 단계가 아니라 설계를 바꾸는 단계였다. 거절 경로 결함, 트랜잭션 비용, 503의 연결 종료는 모두 코드만 봐서는 보이지 않았고, 원인을 가설로 세운 뒤 한 가지만 바꾼 비교로 확인했다

# OMP 포트폴리오 검토

검토일: 2026-09-20

## 판단

포트폴리오의 주제와 문제 해결 흐름은 적절하다. 특히 락 충돌, 통계 정합성, 비동기 접수의 의미를 설명하는 소재는 백엔드 설계 역량을 보여주기에 좋다. 다만 현재 원본에는 서로 다른 시기의 구현이 섞여 있고, STEP1에는 테스트로 확인한 범위를 넘어선 완료 표현이 있다. **수정 방향은 타당하지만, 현재 문구 그대로 제출하는 것은 권하지 않는다.**

가장 설득력 있는 방향은 ‘비동기로 바꿔 처리량을 늘렸다’보다 ‘락 충돌의 원인을 구분하고, 저장 완료와 접수를 분리하며, 실패까지 검증했다’이다. 성능 수치는 동일 조건의 재측정 결과가 확보된 뒤 이 설명을 뒷받침하도록 배치하면 된다.

## 1. 원본 포트폴리오에서 반드시 고칠 부분

### 1-1. 낙관적 락과 통계 테이블 분리는 서로 다른 구현 단계다

원본 1-1은 `shop_review_stats`의 `version` 컬럼과 `@Version + Spring Retry`를 현재 구현으로 함께 설명한다. 현재 `ShopReviewStats`에는 version이 없고, 평점 합계·개수·평균을 하나의 UPDATE로 갱신한다. Spring Retry 의존성도 제거되어 있다.

다만 낙관적 락과 재시도를 **구현한 적이 없다는 뜻은 아니다.** `8ab9199`에는 `Shop.@Version`, 낙관적 락 조회, `ReviewUpdateService`의 `@Retryable`과 `REQUIRES_NEW`가 존재한다. 당시 락 대상은 현재의 별도 통계 엔티티가 아닌 Shop이다.

수정 방향:

- 최종 구현: ‘통계 테이블 분리 + DB 원자 증가 UPDATE’로 기술한다.
- 과거 시도: 필요하면 ‘이전에는 Shop에 낙관적 락·재시도를 사용했으며, 이후 모델과 갱신 방식을 변경했다’고 구분한다.
- 현재 스키마 표: `version`을 빼고 실제 저장 중인 `average_rating`을 반영한다.
- 원자 증가 UPDATE는 DB의 행 락을 사용하는 방식이다. ‘락 없이 처리’로 표현하면 안 된다.

근거: `src/main/java/com/omp/shop/ShopReviewStats.java:18`, `ShopReviewStatsRepository.java:17`, `build.gradle`; 과거 커밋 `8ab9199`.

### 1-2. ‘통계 분리 후 데드락이 없다’는 범위를 좁혀야 한다

리뷰 INSERT의 FK 검사로 shops 행에 공유 락을 잡고, 같은 행을 UPDATE하려다 두 트랜잭션이 서로 기다리는 설명은 타당하다. FK 검사 시 참조 레코드에 공유 락을 설정한다는 점은 [MySQL 공식 문서](https://dev.mysql.com/doc/refman/8.0/en/innodb-locks-set.html)에 부합한다.

통계 UPDATE 대상을 별도 행으로 옮기면 **설명한 shops 행의 S→X 승격 경로**가 사라진다. 하지만 다른 트랜잭션과의 락 순서까지 포함해 모든 데드락이 불가능하다고 말할 수는 없다. 통계 행의 UPDATE 경합도 남는다.

더구나 `ReviewStatsSyncModeTest`는 리뷰 두 건을 순서대로 요청한 뒤 값을 확인한다. 동시 실행을 제어하는 테스트가 아니므로 데드락 부재의 실측 근거로 쓸 수 없다.

권장 표현: ‘통계 갱신 대상을 분리해 기존 FK 공유 락에서 배타 락으로 승격하던 충돌 경로를 제거했다. 동기 모드의 통계값은 검증했으며, 동시 요청 재현과 부하 검증은 후속 단계로 진행한다.’

근거: `benchmark/STEP1-2026-09-19.md:64`, `src/test/java/com/omp/review/ReviewStatsSyncModeTest.java:33`.

### 1-3. ‘반영 지연’과 ‘반영 누락’을 구분해야 한다

비동기 통계 갱신이 큐에서 대기하다 성공하면 지연이다. 제출이 거절되거나 UPDATE가 실패하고 복구 경로가 없으면 누락이다. 현재 `ShopReviewStatsUpdater`는 거절·실행 예외를 로그와 카운터로 남기지만 다시 처리하지 않는다.

따라서 원본의 ‘최종 실패하면 반영이 지연될 수 있음’은 부족하다. **‘재처리하지 않으면 통계가 계속 불일치할 수 있음’**이 현재 동작에 맞다. 정상 두 건의 최종 일치 테스트로 장애 상황의 eventual consistency까지 보장할 수 없다.

또한 원자 UPDATE는 동시 read-modify-write의 덮어쓰기를 막지만, 이벤트 누락이나 중복 적용을 막지는 않는다. 나중에 재처리를 붙인다면 reviewId 등에 기반한 중복 방지 또는 원본 리뷰 기준 재집계가 필요하다.

실패 관측 자체는 동기 방식에서도 가능하다. 비동기 선택의 고유한 근거는 ‘통계 처리 대기를 리뷰 응답에서 분리할 가치가 있는가’이며, 그 대가로 반영 지연과 전달 신뢰성 관리가 생긴다.

근거: `src/main/java/com/omp/shop/ShopReviewStatsUpdater.java:39`.

### 1-4. ‘DB 커넥션 풀 분리’는 현재 구현과 다르다

현재는 Hikari 최대 20개의 **단일 DB 커넥션 풀**을 공유한다. 분리한 것은 INSERT 작업을 실행하는 스레드 풀이다. 요청 스레드의 대기를 줄이더라도 조회와 INSERT가 공유 DB 커넥션을 두고 경쟁할 수 있다.

권장 표현: ‘INSERT 전용 스레드 풀로 저장 작업을 분리했다. DB 커넥션 풀은 공유하므로 별도로 포화와 대기를 관측했다.’ 마지막 ‘관측했다’는 실제 측정 자료가 생긴 뒤 쓴다.

근거: 원본 1-2 ‘커넥션 풀 조정’, `src/main/resources/application.properties:17`, `AsyncThreadPoolConfig.java:15`.

### 1-5. 기존 성능 수치를 새로운 구현의 성과로 연결하면 안 된다

원본이 268만 건을 DB 저장량이 아닌 접수량으로 한정한 점은 적절하다. 다만 동기의 359ms는 저장 완료까지, 비동기의 172ms는 접수까지이므로 서비스가 보장하는 완료 시점이 다르다. ‘주문 저장 속도 개선’이나 ‘완료 처리량 두 배’로 확장할 수 없다.

리뷰 2.5만→3.8만 건도 어떤 구현 단계와 측정 기준의 결과인지 분리해야 한다. 이후 통계 모델·검증·풀 거절 정책이 달라졌으므로 현재 설계의 수치로 자동 승계되지 않는다.

권장 조치:

- 과거 기록은 ‘당시 nGrinder에서 관측한 접수 성능, 저장 완료량 미측정’으로 별도 표시하거나 본문의 핵심 성과에서 잠시 뺀다.
- 재측정에서는 같은 데이터·설정·부하 조건에서 접수 지연과 커밋 완료량을 각각 기록한다.
- 반복 측정의 중앙값과 범위를 사용하고, 한쪽만 ‘최대’ 결과를 대표값으로 선택하지 않는다.
- 프로젝트 기간에는 초기 개발과 2026년 재검증·개선 시기를 구분한다. 커밋 날짜만으로 원래 개발 기간이 틀렸다고 단정할 수는 없다.

### 1-6. Jitter의 효과는 여러 캐시 키의 만료 분산으로 한정한다

코드에는 캐시 생성 시 기본 TTL에 0초 이상 3초 미만의 무작위 값을 더하는 구현이 있다. 여러 키의 동시 만료를 분산하는 설명은 적절하다.

하지만 한 인기 키가 만료되었을 때 여러 요청이 동시에 DB를 읽는 상황을 Jitter만으로 막지는 못한다. 현재 `@Cacheable`에는 `sync=true`가 없다. 동일 키의 중복 로딩을 합치는 처리는 별도 고려 사항이다. [Spring Cacheable 공식 문서](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/cache/annotation/Cacheable.html)는 sync 옵션을 같은 키에 대한 동시 로딩 조정으로 설명한다.

‘Cache Stampede 해결’보다는 ‘TTL Jitter로 다수 캐시 키의 만료 시점을 분산’이 정확하다. 아직 부하 측정이 없다면 ‘완화 효과를 확인’ 대신 ‘집중 가능성을 낮추도록 설계’로 적는다.

근거: `src/main/java/com/omp/config/CacheConfig.java:26`, `src/main/java/com/omp/shop/ShopController.java:26`.

## 2. STEP1의 완료 판단에 영향을 주는 남은 코드 문제

### 2-1. 주문 상태 객체의 JSON 직렬화 실패 — 재현 확인

`OrderJobState`는 일반 클래스인데 조회 메서드가 `status()`, `orderId()`이고 JavaBean getter가 없다. `OrderIdentifier`에도 getter가 없다. 프로젝트에서 별도 Jackson 가시성 설정은 찾지 못했다.

프로젝트의 Spring/Jackson 버전으로 기본 JSON 매퍼를 구성해 두 객체를 직렬화하자 모두 `InvalidDefinitionException: No serializer found ... no properties discovered`가 발생했다.

폴링 응답과 SSE의 data가 이 객체들을 사용하므로 ‘메모리에 상태가 남는다’는 테스트만으로 ‘클라이언트가 상태를 정상 조회할 수 있다’고 판단할 수 없다. getter, 명시적 JSON 프로퍼티 또는 응답용 record 등으로 직렬화 계약을 만든 뒤 HTTP/SSE 응답을 검증해야 한다.

이번에 실행한 것은 직렬화 최소 재현이며, 실제 서버 HTTP 요청의 상태코드를 측정한 것은 아니다.

근거: `src/main/java/com/omp/order/async/OrderJobState.java:3`, `OrderIdentifier.java:6`, `src/main/java/com/omp/order/OrderController.java:55`, `OrderSseEmitterMap.java:28`.

### 2-2. SSE 연결 전에 실패한 주문의 재조회 분기 누락 — 재현 확인

연결 시 `checkOrderStateThenSend()`는 COMPLETED만 따로 처리한다. FAILED도 나머지 경로로 들어가 `orderCreateNotComplete`를 보내고 연결을 유지한다. 이미 실패한 뒤 연결했다면 새로운 실패 콜백이 반드시 다시 발생하는 것도 아니다.

FAILED 상태를 먼저 만든 뒤 연결 시 처리 메서드를 실행한 최소 재현에서 전송 1회, 연결 완료 false, emitter 유지 true를 확인했다. 상태 보관 수정과 별개로 FAILED를 재전달하고 종료하는 처리가 필요하다.

근거: `src/main/java/com/omp/order/OrderSseEmitterMap.java:28`.

### 2-3. COMPLETED와 orderId를 하나의 일관된 상태로 공개하지 않는다 — 코드 분석

`AsyncOrderManager.complete()`는 먼저 `jobComplete()`로 상태를 COMPLETED로 바꾸고 다음 줄에서 orderId를 넣는다. 두 필드가 volatile이어도 두 번의 대입 전체가 하나의 원자적 변경이 되지는 않는다. 이미 객체 참조를 얻은 조회 스레드는 COMPLETED와 null orderId의 조합을 관측할 수 있다.

상태와 결과 ID를 함께 가진 불변 객체로 교체하는 방식 등을 검토할 수 있다. 이번 검토에서 이 스레드 간 타이밍을 실제 HTTP 요청으로 재현한 것은 아니다.

근거: `src/main/java/com/omp/order/async/AsyncOrderManager.java:29`, `OrderJobState.java:4`.

### 2-4. 처리 중 TTL 만료는 완료 상태 복구로 이어지지 않는다 — 동작 확인

TTL은 접수 상태에도 적용된다. 작업이 TTL보다 오래 걸려 엔트리가 만료되면 `computeIfPresent()`로 수행하는 완료·실패 갱신은 아무것도 저장하지 않는다. 따라서 ‘완료 후 무조건 5분간 조회 가능’이라고 보장할 수 없다.

Caffeine 3.1.8에서 동일 객체를 반환하는 computeIfPresent가 만료 전 실행되면 쓰기 TTL이 갱신되는 것은 확인했다. 문제는 그 전에 이미 만료된 경우다. 처리 중 보관 정책과 종료 후 보관 기간을 구분할 필요가 있다.

근거: `src/main/java/com/omp/order/async/AsyncOrderManager.java:19`.

### 2-5. 통계 행이 없으면 실패 카운터와 검증 SQL이 동시에 놓친다 — 코드 분석

`ShopReviewStatsWriter.apply()`는 UPDATE 영향 행 수가 0이어도 로그만 남긴다. 예외가 없으므로 `omp.review.stats.failed`는 증가하지 않는다. sync 모드에서도 리뷰 INSERT는 커밋될 수 있다.

더구나 `verify.sql`은 통계 테이블을 기준으로 LEFT JOIN한다. 리뷰는 있는데 통계 행이 아예 없는 가게는 결과에서 빠진다. 평균 컬럼의 정확성도 검증하지 않는다. 정상 가게 생성은 통계 행을 함께 만들지만, 누락된 기존 데이터 등의 조건에서는 이 감시 공백이 드러난다.

따라서 ‘카운터 0 + verify.sql 결과 0행 = 완전한 정합성’은 현재 기준으로 성립하지 않는다. 영향 행 수 검증, 누락 행 탐지, 평균·반올림 규칙 검증을 추가해야 한다.

근거: `src/main/java/com/omp/shop/ShopReviewStatsWriter.java:20`, `benchmark/sql/verify.sql:9`.

### 2-6. 검증 통일은 완료됐지만 주문 도메인 검증 전체가 완료된 것은 아니다

두 주문 경로가 같은 validateOrder 쿼리를 사용하는 것은 확인했다. 하지만 장바구니가 주문자와 요청 가게에 속하는지 확인하는 조건은 여전히 주석이다. 현재 테스트는 메뉴가 빈 배열이며 주문 행 수 위주로 검증한다.

또한 sync는 검증과 저장이 한 트랜잭션이고 async는 접수와 저장 사이에 큐 대기가 있다. 같은 READ_COMMITTED를 지정했다고 검증 이후 상태 변경까지 동일하게 다루는 것은 아니다. 동기 경로의 일반 SELECT 또한 후속 변경을 자동으로 차단하지 않는다.

‘검증 쿼리·규칙을 통일했다’는 맞지만 ‘주문 유효성을 완전히 보장했다’나 ‘동기·비동기의 의미가 완전히 같다’로 확대하지 않는다. 상태 변경을 접수 시점 기준으로 허용할지, 저장 시 다시 확인할지도 결정해야 한다.

## 3. STEP1에서 맞는 내용과 표현만 다듬을 내용

| 항목 | 판단·수정 방향 |
| --- | --- |
| MySQL UPDATE 평균 대입 순서 수정 | 맞다. 원래 sum·count를 먼저 올리고 다시 증가분을 더하면 잘못된 평균이 된다. 현재 평균을 먼저 계산하는 순서는 설명과 일치한다. |
| `||` → `&&` | 의도한 세 조건의 결합을 바로잡은 수정이다. 별도 도메인 검증의 누락과는 구분한다. |
| insert 포화 시 503 + Retry-After | 코드와 저장된 테스트 결과가 뒷받침한다. 모든 장애에서 주문 유실이 없다는 보장은 아니다. |
| AFTER_COMMIT 리스너 예외의 비전파 | 해당 트랜잭션 이벤트 경로에 대한 설명은 맞다. 일반 동기 이벤트 리스너나 TransactionSynchronization.afterCommit()의 예외까지 같은 동작이라고 하면 안 된다. |
| ‘이벤트 리스너에서는 불가능’ | ‘현재 AFTER_COMMIT 리스너에서 예외를 던지는 방식으로는 거절을 HTTP 오류로 전파할 수 없다’로 한정한다. |
| ‘REVIEW의 B안 + A안’ | 정확히는 다르다. 원래 B안은 서비스 트랜잭션 종료·커넥션 반납 뒤 제출이다. 실제 코드는 @Transactional 서비스 메서드 안에서 제출한다. ‘직접 제출 + 명시적 거절’이 정확하다. |
| ‘REQUIRES_NEW가 워커 스레드를 보장’ | 트랜잭션 전파와 스레드 선택은 별개다. 새 트랜잭션은 해당 애너테이션, 워커 실행은 Executor가 담당한다. |
| ‘격리 + 실패 관측이 비동기 근거’ | 요청 지연의 격리와 관측 보완을 구분한다. 로그·카운터는 동기 방식에도 가능하다. DB 자원은 공유한다. |
| ‘모든 결함을 실패 테스트로 먼저 재현’ | 저장된 성공 결과만으로 과거 실패 과정을 독립적으로 확인할 수는 없다. 특히 CallerRuns에서 실제 커밋 유실을 재현했는지와 인라인 실행·202 응답만 확인했는지를 분리해 기록한다. |
| ‘로컬 값은 코드에 두지 않는다’ | 환경변수 미지정 시 사용할 기본 비밀번호가 설정에 남아 있다. 환경변수로 덮어쓸 수 있게 했다고 표현하거나 기본값 자체를 없앤다. |
| ‘1단계 완료’ | 정의한 테스트 17건 통과는 맞다. 포폴에서 상태 전달까지 해결됐다고 쓰려면 위 추가 결함을 반영해야 한다. |

MySQL 설명은 [UPDATE 공식 문서](https://dev.mysql.com/doc/refman/8.0/en/update.html)에 부합한다. AFTER_COMMIT에서 커밋이 끝났더라도 자원이 남아 있을 수 있다는 경고는 [Spring 6.2.1 TransactionalEventListener](https://docs.spring.io/spring-framework/docs/6.2.1/javadoc-api/org/springframework/transaction/event/TransactionalEventListener.html)에 있다. 이벤트의 AFTER_COMMIT과 afterCommit() 콜백은 [TransactionPhase](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/transaction/event/TransactionPhase.html)에서 구분하며, 예외 전파 차이는 [TransactionSynchronization](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/transaction/support/TransactionSynchronization.html)에 명시되어 있다. current 링크는 현재 공개 문서이며 프로젝트 버전과 구분한다.

## 4. 재측정 전에 정리해야 할 벤치마크 논리

선행 REVIEW에는 이미 올바른 보완 방향이 적혀 있지만 실행용 README와 스크립트에 모두 반영되지는 않았다.

| 현재 문제 | 필요한 보완 |
| --- | --- |
| reset → 워밍업 → 본측정 | 워밍업 쓰기가 DB에 남는다. 워밍업 작업 종료까지 확인하고 reset한 뒤 본측정하거나 회차 식별자로 분리한다. |
| `orders_accepted == COUNT(orders)`만으로 유실·중복 판정 | 한 요청 누락과 다른 요청 중복은 총합에서 상쇄될 수 있다. 회차별 요청 식별자와 저장 결과의 일대일 대조가 필요하다. 단순 건수는 기본 점검으로 유지한다. |
| queued=0이면 완료로 취급 | 이미 실행 중인 작업은 큐에 없다. active, 성공·실패 상태, DB 커밋 결과까지 확인한다. |
| 503이 없으면 용량 조건 통과 | 지연 목표, 다른 오류, dropped_iterations, 작업 적체와 최종 결과를 함께 본다. ‘측정 조건에서 거절 없이 유지한 유입률’로 범위를 한정한다. |
| 별도 측정한 API p95 − ping p95 = 서버 시간 | 서로 다른 분포의 백분위수를 빼서 구간 처리 시간을 분해할 수 없다. 서버 내부 구간 계측이 필요하다. |
| iterations를 접수량으로 사용 | 시도량·유효 성공 응답량·202 접수량·커밋 완료량을 구분한다. |
| 오류 0건 목표인데 threshold는 1% 미만 | 정상 동작 회차와 의도적 포화·데드락 재현 회차의 판정 기준을 구분해 설정한다. |
| 주문 부하는 POST와 응답 헤더만 확인 | 이 결과는 SSE 연결·폴링이 포함된 전체 사용자 흐름의 성능을 대표하지 않는다. 측정 범위에 명시하거나 별도 시나리오를 둔다. |
| 리뷰 개선 전→후에 모델과 비동기를 동시에 변경 | ① shops 통계+동기 ② 별도 통계+동기 ③ 별도 통계+비동기를 구분하면 모델 분리 효과와 비동기 효과를 나눠 설명할 수 있다. |

동기 두 요청 테스트, 동시 락 재현 테스트, 장시간 부하 테스트는 서로 다른 질문에 답한다. 숫자를 많이 모으는 것보다 주장별로 필요한 증거를 연결하는 것이 우선이다.

## 5. 권장하는 포트폴리오 구성

### OMP 1-1: 리뷰 통계의 락 충돌과 갱신 정합성 개선

1. 문제: 리뷰 저장과 가게 통계 갱신에서 어떤 락 충돌과 잘못된 값이 관찰됐는가.
2. 원인: FK 공유 락→동일 행 UPDATE, 애플리케이션 read-modify-write, 평균 UPDATE 대입 순서를 각각 구분한다.
3. 설계: 통계 모델을 분리하고 원자 증가 UPDATE를 채택한다. 과거 낙관적 락은 이전 단계로 배치한다.
4. 검증: 현재 확보된 순차 통계값 검증과 앞으로 필요한 동시성 재현을 구분한다.
5. 선택: 별도 통계 모델에서 sync/async를 비교한다. 비동기는 락 대기를 응답에서 분리하는 선택으로 설명한다.
6. 한계: 실패 시 통계 누락, 중복 반영, 복구 수단을 명시한다.

### OMP 1-2: 주문 접수·저장을 분리하고 포화와 상태 전달을 설계

1. 목표: 빠른 접수가 어떤 사용자 경험에 필요한지, 저장 완료는 어떻게 확인하는지 정한다.
2. 구조: 검증 → 작업 제출 → 202 + Location → 워커 저장 → 상태 조회/알림.
3. 보호: 입력 검증 통일, 명시적 거절, 실패 상태, 보관 기간을 설명한다.
4. 검증: 접수 시간과 완료 결과를 나눠 제시한다. 상태 객체의 실제 응답과 SSE 실패 재전달부터 보완한다.
5. 한계: 인메모리 작업 유실, 멱등성, 다중 인스턴스 상태 공유, 검증 후 상태 변경.

SSE 그림은 저장 완료가 SSE 연결보다 먼저 올 수 있는 분기도 보여줘야 한다. UUID는 현재 응답 본문이 아니라 Location 경로에 포함되어 반환되므로 실제 API 계약에 맞춰 표시한다.

### OMP 1-3: 캐시 적용과 만료 분산

적용 위치, TTL·Jitter, 여러 키와 동일 키의 차이, 측정 여부만 간결하게 적는다. 정량 근거가 생기기 전에는 리뷰·주문과 같은 비중의 대표 성과로 확대하지 않아도 된다.

각 사례에서 긴 ‘느낀 점’을 반복하기보다 **결정 이유와 확인한 결과**를 앞에 놓으면 읽는 사람이 판단하기 쉽다. 미구현 Outbox·MQ·Redis는 현재 성과에서 제외하고, 실제 확인한 실패와 연결된 후속 과제로만 적는다.

## 6. WalkiePaw에 대한 문서 수준의 의견

전체적으로 문제→변경→결과→한계의 구성이 일관적이다. 특히 인메모리 페이징 제거와 실제 메모리 감소량 미측정을 구분한 서술은 적절하다. 이번에는 해당 저장소 코드를 확인하지 않았으므로 아래는 확정 결함이 아닌 추가 검증 후보다.

- 커서 페이징: PK 커서와 created_date 정렬의 관계를 실제 WHERE·ORDER BY 쿼리로 설명하면 좋다. 동률뿐 아니라 커서 기준과 정렬 기준이 일치하는지 확인한다.
- 검색: LIKE 검색과 n-gram Full-Text 검색의 결과 집합이 요구사항상 같은지, 토큰 길이·검색 모드와 관련도 정렬 쿼리가 무엇인지 보여준다.
- 좋아요 집계: AtomicReference로 Map 참조를 바꿔도, 바꾸기 전에 옛 Map을 얻은 작성 스레드까지 자동으로 차단되는지는 코드 검증이 필요하다. ‘참조 교체가 원자적’과 ‘쓰기 유실 없음’을 구분한다.
- ‘레코드당 락 획득 시간’ 500ms→58ms: 락 대기 시간인지, 락 보유 시간인지, 한 트랜잭션 전체 시간인지 측정 정의를 명시한다.

## 7. 제출 전 우선순위

1. 현재 구현과 과거 구현을 분리하고, 커넥션 풀·데드락·정합성 표현을 정정한다.
2. 주문 JSON 응답과 늦은 SSE 실패 연결을 보완하고 실제 API 응답까지 검증한다.
3. 통계 누락 행 탐지와 실패 관측 공백을 보완한다.
4. 결정적 동시성 재현과 벤치마크 절차를 정리한다.
5. 재측정 결과에 따라 리뷰 sync/async를 선택하고 성능 수치를 갱신한다.

이 순서면 ‘많은 기술을 적용한 프로젝트’보다 ‘원인과 보장 범위를 설명하고 결과로 검증한 프로젝트’로 읽힐 수 있다.
